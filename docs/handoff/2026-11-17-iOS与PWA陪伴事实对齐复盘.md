# iOS 与 PWA 陪伴事实对齐复盘

核对基线为 `58591cb` 和本地 `local/shortcut-hosted-trace` 的在途改动。范围是识别后用于生成 AI 陪伴的事实和候选。PWA 侧列的是代码可以产出的候选，实际是否选中还受样本、配置、资格和排序影响。

## 为什么卡了这么久

最初用 Swift 实现轻量 Planner，是为了在未登录或未开启云同步时，仍能从设备上的记录挑出有依据的观察。这个目标应保留。后来接通 Hosted，iOS 复用了 PWA 的文案生成，但主要沿用 Swift 选出的候选。PWA 已打磨过的历史聚合、对照和排序规则没有随生成入口一起接入。

验收时检查了识别成功、第二轮有返回、文案能落库展示。漏掉的一步是用同一笔记录和同一份历史，检查两端到底算出了什么、选中了什么、最后送给模型什么。第二轮即使成功返回，也可能用了规则反馈。这让排查在 Prompt、记忆量和兜底话术之间来回打转。

记账复现用两笔同商户的模拟支出，旧 iOS 候选只能表达近期重复，PWA 能算出当天两笔合计 7 元。本地分支已验证每日合计和距上次间隔的复用路径。类别变化、个人基线和候选排序仍需要逐项对照。

## 其他域差异

| 域 | PWA 可计算的观察 | 当前 iOS 陪伴路径的差异 |
| --- | --- | --- |
| 睡眠 | 入睡和起床时刻、和常态作息的偏差、时长和质量对比、睡眠阶段构成 | 睡眠页面已有自己的时刻比较。陪伴路径缺少上述候选，Hosted 接收层还会过滤入睡、起床和阶段字段 |
| 饮食 | 同餐次历史中位数、餐食构成、重复出现的菜品 | 有本次餐食和近期记录，缺少同餐次对照与菜品复现计算。账单的餐饮分类不能作为实际用餐证据 |
| 运动 | 本次时长和个人历史中位数的差异 | 本次时长和近期记录可用，缺少历史基线候选 |
| 阅读 | 本次阅读时长和个人历史中位数的差异 | 本次时长和近期记录可用，缺少历史基线候选 |
| 收入 | 月内累计金额、笔数、同来源复现 | 通知可以单独显示本月已入。Swift 候选可以识别同来源近期出现，缺少把月累计和次数作为陪伴证据的路径 |
| 钱包 | 同一账户、同类资产或负债与上一份快照的余额差 | 有本次快照，缺少可比较快照的变化候选。余额变化本身无法证明消费或还款 |
| 跨域 | 在时间接近、存在共同对象并达到门槛时生成可能关联 | iOS 当前从同域取近期事实。跨域关联需先定义可读取和可传输的最小证据，以及不作因果断言的边界 |

本地模拟睡眠记录带七个字段。Hosted 规范化后只保留 `sleep_minutes` 和 `quality_score`，丢掉 `sleep_start_at`、`wake_at`、`deep_sleep_minutes`、`light_sleep_minutes`、`rem_minutes`。同一记录直接进入 PWA 候选生成器并提供常态作息后，可以产出入睡起床、常态对比和睡眠阶段等候选。这个实验验证了代码层的字段过滤和候选生成，尚未覆盖真机请求、线上模型或最终选中结果。

## 下一次怎么验

1. 每个域用同一个场景编号和同一份模拟数据。包含本次记录、可信的历史记录、时区、比较窗口，以及适用的偏好和记忆开关。
2. 先对照两侧纳入了哪些记录、接收层保留了哪些字段，再对照最终候选的观察类型、数值、单位、时间窗口和证据来源。证据不足、重复导入、不同对象不可比都要有反例。
3. 核对模型实际收到的内容，并记录最终展示采用的是模型文案、规则反馈还是空结果。用同一模型和同版 Prompt 做小样本人工对照，验收句子是否有具体依据、是否读出同一层意思。
4. 单独记录本地对照、真实模型和真机的验证结果。每个阶段分别留证，避免用一次成功回包代替后续验收。

下一轮先做睡眠的最小样例，用同一份模拟数据验证字段保留、跨午夜和常态对照。然后按同样的方法核对饮食。设备仍是本机记录的来源，Hosted 只在现有授权范围内接收该观察所需的最少字段。

用户随后确定七个域和跨域关联均属于核心功能。本地实现及验证记录见 [全域共享 Planner 接入](../spec/执行记录/LOCAL-AI-003-全域共享Planner接入.md)。
