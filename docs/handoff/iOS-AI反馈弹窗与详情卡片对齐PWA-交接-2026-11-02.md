## 1. 一句话结论

AI 反馈**数据早就到手了**，iOS 只是没用。

后端 `recognize_only` 已经把 `payload.ai_feedback` 和 `payload.companion_message` 返回给 iOS（`supabase/functions/ingest-receipt/index.ts:6484-6485`），iOS 也解析并塞进了 payload（`LocalImageRecognition.swift:90-99`）。

断点在两处：
1. **提示文案写死**，UI 层根本没读反馈；
2. **记账域没有存 `ai_feedback` 的列**，详情页读不回来。

所以不是识别问题，是"有数据、没消费"。

**PWA 口径（本次复核确认，决定方案边界）：**

| 页面 | PWA 现状 | 证据 |

| 待确认弹窗 | **有** AI 反馈卡片，且 companion 存在时压制 legacy feedback | `src/components/ModalPending.vue:297-305`、`:405-418` |

## 2. PWA 侧口径（要照搬的就是这一套）

全部在 `supabase/functions/ingest-receipt/`，三段纯文本逻辑，与 UI 无关，可以直接移植成 Swift 纯函数。

### 2.1 三个基础函数

**`uniqueNotificationLines`**（`notification-text.ts:48`）——按行去重，比较时把连续空白压成一个空格：

```ts
const key = line.replace(/\s+/g, " ");
if (seen.has(key)) continue;
```

**`compactFeedbackText`**（`index.ts:2215`）——压成单行，超长在标点处收尾：

```ts
max 默认 42；调用点传 34
正文里 \r\n 压成空格
超过 max 时：在 。！？；，, 处切，切口位置 ≥ max/2 才用，否则硬截 max-1 加 …
```

**`feedbackNotification`**（`index.ts:2232`）——把结构化反馈拼成多行：

```ts
if (!feedback || feedback.confidence < 0.5) return fallback;

lines = uniqueNotificationLines([
  `${feedback.icon} ${feedback.badge}`,              // 第 1 行：图标 + 徽标
  compactFeedbackText(feedback.emotion_line, 34),    // 第 2 行：情绪句
  compactFeedbackText(feedback.utility_line, 34) ?? fallbackLines[0], // 第 3 行：实用句，缺则用兜底首行
  ...fallbackTail                                     // preserveFallbackAll ? 全部 : preserveFallbackTail ? 除首行 : 无
]);
```

### 2.2 companion 与 feedback 的优先级（`index.ts:2266`）

```ts
const companionLine = compactFeedbackText(companionMessage, 34);
if (!companionLine) {
  return feedback
    ? feedbackNotification(feedback, fallback, { preserveFallbackAll: true })
    : fallback;
}
return uniqueNotificationLines([companionLine, ...fallback 的所有行]).join("\n");
```

**结论：companion_message 存在时，它单独占第一行，后面的 fallback 行照旧；此时 `feedbackNotification` 完全不参与。** 这就是用户要的"companion 优先、feedback 补充、中间去重"。

注意一个细节：companion 分支并没有把 `emotion_line` / `utility_line` 追加进去，它只做了"companion 行 + fallback 行"的拼接。所谓"补充"指的是 fallback（域摘要行）仍然保留，不是把 feedback 的行拼上去。移植时不要自作聪明加料。

### 2.3 三个域的 fallback 文案

| 域 | fallback（`_xxxNotif`） | 位置 |
|---|---|---|
| 通用域（food/sleep/sport/reading/…） | `${emoji} 已归档到${domainNameFromKey(key)}`<br>emoji：sport 🏃 / sleep 🌙 / reading 📚 / food 🍱 / 其他 ✓ | `index.ts:7200-7202` |
| 收入 | `💰 +${fmtYuan(amount)}${source ? " · "+source : ""}`<br>`本月已入 ${fmtYuan(月累计)}` | `index.ts:7518-7520` |
| 支出 | `💸 -${fmtYuan(amount)} · 商户 · 分类`<br>`今日已花 ${fmtYuan(今日累计)}（N 笔）`<br>未完成时：`⚠️ -¥x · 商户 · 请打开 App 补全` | `index.ts:7806-7820` |

金额格式 `fmtYuan`（`index.ts:1906`）：`¥` + 两位小数。

汇总行（`index.ts:1948-1955`）：
- `todaySpendLine`：count 为 0 → `今日尚无支出记录`，否则 `今日已花 ¥X（N 笔）`
- `monthIncomeLine`：`本月已入 ¥X`

`domainNameFromKey`（`index.ts:718`）：expense→消费记账 / income→收入记录 / sport→运动记录 / sleep→睡眠记录 / food→饮食记录 / reading→阅读记录。

### 2.4 反馈本身长什么样

`AIFeedback`（`index.ts:628`）关键字段：`icon / badge / band(positive|neutral|watch|recover|ritual) / emotion_line / utility_line / detail_reason / confidence / source`。

在 `recognize_only` 分支（`index.ts:6474-6482`）：
- 仅当 `companionSettings.enabled && aiOk` 才构造（默认 enabled = true，iOS 不传设置，走默认）
- expense → `buildExpenseAIFeedback`：**置信度 < 0.7 返回 null**
- income → `buildIncomeAIFeedback`：**金额为空或置信度 < 0.7 返回 null**
- 内置域 → `buildBuiltinAIFeedback`：要求 `missingFields 为空` 且 `confidence >= 0.75`

也就是说 iOS 拿到的 feedback 已过一道门槛，客户端只需要再判 `confidence >= 0.5`（对齐 `feedbackNotification` 的入口条件）。

## 4. 改动方案

分三组，**执行顺序：B1/B2 → A → B3/B4 → C**（B1/B2 只建列加字段、不改行为，先落地才能让 A2 的幂等路径读到数据）。每组可独立验证。

### A 组：文案生成 + 两种呈现

**A1. 新增纯函数文件 `ios/SnapCount/Features/Records/LocalIntakeNotificationText.swift`**

按第 2 节逐条移植，不引 UI 依赖：

```swift
enum LocalIntakeNotificationText {
    // 输入：域、companion、feedback、金额/商户/分类、今日支出、本月收入
    // 输出：多行文案（2~3 行）
    static func compose(...) -> String
}
```

内部需要四个私有函数，与后端一一对应：
- `uniqueLines(_:) -> [String]`
- `compactText(_:max:) -> String?`（默认 34）
- `clipAtNaturalBoundary(_:max:)`
- `domainFallback(domainKey:amount:merchant:category:todaySpend:monthIncome:)`

**A2. 让结果把文案带出来**

`LocalImageIntakeOutcome` 增加 `notificationText: String?`（默认 nil）。等价于：
- `.archived` / `.financialArchived` → 走 A1 的归档文案
- `.staged` / `.financialPending` → 走"请补全"文案（金额 + 商户 + `请打开 App 补全`）

幂等路径（同一张图重传）也要产出同样文案，需要从锚点行读回 `companion_message` / `ai_feedback` —— **所以 B1/B2 必须先做**（只建列 + 模型字段，不改行为），A2 才有数据可读。

**A1 的数据来源要说清**：`compose` 的入参含 `todaySpend` / `monthIncome`，但纯函数自己不查库。由 `LocalImageRecognitionUseCase` 负责查，它当前的依赖只有 `pendingRepository`（`:117`）。需要新增 `LocalExpenseRepository` 注入，在 `makeDefault`（`:135`）里一并构造。快捷指令后台运行时这是额外一次 DB 打开 + 两次月度查询，接受；不做单条 SQL 聚合优化。

**A3. 快捷指令（横幅）**

`UploadScreenshotIntent.swift:74-89`：把写死的两句换成 `outcome.notificationText`，`route` 逻辑不动。**`displayText` 也要一起换**——`:102` 在结果卡开关打开时返回的是 `result.displayText`，目前同样写死，漏改则卡片仍是旧文案。

`SnapCountUploadService.swift:268` 的 `notificationBody`：**保留换行**，改成按行裁剪而不是拍平：

```swift
var notificationBody: String {
    let lines = notificationText.split(whereSeparator: \.isNewline).prefix(3)
    return lines.map { String($0) }.joined(separator: "\n")
}
```

（iOS 通知折叠态通常只显示 2 行，展开 4 行；PWA 本身也是 2~3 行，最多 3 行即可。）

### C 组：收入口径（用户已放行，但要按下面这个口径）

PWA 的收入通知是两行：

```
💰 +¥500.00 · 某某公司
本月已入 ¥12,345.00
```

云端 `summarizeMonthIncome`（`index.ts:1936`）查的是 `income_records` 里 `income_date >= 月初` 的全部行，**没有过滤删除**。

iOS 本地对应能力已存在：`LocalExpenseRepository.incomes(profileID:monthKey:)`（`:888`），SQL 带 `deleted_at IS NULL`。

**决策：照搬文案，聚合走本地口径。** 即 `+金额 · 来源` + `本月已入 ¥X`，其中 X 用本地 `incomes(monthKey:)` 求和。理由：本地删过的记录不该再计入，本地口径比云端更准；金额与来源的展示格式与 PWA 完全一致。

支出同理照搬 `今日已花 ¥X（N 笔）`，用本地 `expenses(monthKey:)` 过滤当天求和。

**需要你确认的一点**：本地月度收入目前没有单条 SQL 聚合，是查整月数组再求和。数据量在千级以内没问题，先这么做，不做额外优化。
