> 计划编号：CLEAN-001
>
> 状态：试行
>
> 基线：`origin/main@076d256`
>
> 目标：在不覆盖现有 WIP、不误删历史成果、不改变生产行为的前提下，完成 Git 工作区治理和渐进式架构收拢。

## 1. 计划边界

本文把“清洗”拆成两条互相依赖但不得混做的线路：

| 线路 | 处理内容 | 第一条硬约束 |
|---|---|---|
| Git 清洗线 | worktree、分支、根目录 WIP、文档归属和历史引用 | 先登记和保全，后决定归档或删除 |
| 架构收拢线 | 依赖方向、共享规则核心、PWA、iOS、Edge 模块边界 | 先 Spec 和特征测试，后渐进迁移 |

本计划不授权以下操作：

- `git reset --hard`、`git checkout --`、`git clean -fd`、强推或删除远端分支；
- 未经确认的 worktree 删除、历史提交改写或 WIP 归类；
- 生产迁移、生产部署、Edge 热更新或 TestFlight 上传；
- 以“清理重复”为理由删除 Planner fallback、Repository Protocol 或已有兼容门面。

## 2. 共同阶段门禁

每个阶段必须有且只能有一个明确状态：`待开始`、`进行中`、`阻塞`、`已完成`。阶段索引只允许一个阶段处于“进行中”。

进入下一阶段前必须满足：

1. 当前阶段的验收证据已经写入执行记录或交接快照。
2. 当前阶段的未验证项和剩余风险已经列出。
3. 相关 Spec、ADR 和测试映射已经更新。
4. Fresh-agent 接续演练能够恢复当前阶段、冻结范围、任务范围、验证基线和下一步。
5. 没有跨越冻结范围的未解释改动。

任何一项不满足，阶段保持“进行中”，不得顺手进入下一阶段。

## 4. Git 清洗线实施细则

### C1：Worktree 与分支处置矩阵

每个 worktree 必须记录：路径、分支、HEAD、upstream、领先/落后数、是否 clean、未提交文件、负责人、PR、建议处置和阻塞原因。

处置只能从以下集合选择：

```text
保留进行中 / 导出补丁 / 等待负责人 / 合并后归档 / 明确授权后删除
```

没有负责人或无法确认 WIP 来源的对象不得删除，只能标记为“等待确认”。

### C2：根 WIP 分簇保全

根工作区按关注面分为：

1. personal-context 与 prompt 契约；
2. security contract 与迁移 fixture；
3. 演示数据和测试账号；
4. iOS 设计和推广素材；
5. 其他无法归类内容。

每个分簇必须先和 `origin/main` 逐文件比较，标记“上游已覆盖”“本地独有”“内容不同”。只有本地独有或内容不同的文件才进入保全分支。上游已相同的文件不得重复复制成新的权威版本。

### C4：历史对象收口

只有同时满足以下条件，才可以提出删除或归档：

- 分支已合并或补丁已导出；
- worktree clean；
- 没有未关闭 PR、交接引用或本地唯一文件；
- 负责人确认处置方式；
- 处置动作和恢复方式已记录。

删除是最后一步，不是盘点动作的默认结果。

2026-08-17 首批归档只移除精确清单中的 clean、main ancestor 且无开放 PR worktree checkout，保留所有 branch/ref；已完成 55/62，剩余 7 个因 ignored `node_modules` 保留。dirty、未合并、开放 PR、当前实现和审计 worktree 均不处理。执行记录见 `docs/handoff/C4-首批worktree归档清单-2026-08-16.md`。

## 5. 架构收拢线实施细则

### A1：架构依赖基线

只读检查以下不变量：

- 生产代码不得新增依赖 `tools/`；
- Domain 不依赖 Vue、SwiftUI、HTTP 或 Supabase 客户端；
- 页面不新增 Supabase 直连；
- 时间、金额、状态和证据规则不得出现第二份实现；
- 新 RPC 必须有契约测试。

现有违规先记录为基线，不立即把所有历史问题变成硬门禁。检查脚本先采用“旧问题报告、新问题失败”的 ratchet 方式。

### A2：`expression-core` 试点

先写模块 Spec 和特征测试，再迁移最小的一组纯函数。生产 Edge、Planner Lab 和 fallback 共用生产拥有的 `_shared/expression-core/`，但保留不同的编排路径。

核心模块必须满足：零 Supabase I/O、零 Deno 专属 API、零 Node 专属 API，并使用同一份代码分别通过 `deno test` 和 `node --test`。

### A3-A5：端侧渐进收拢

- PWA：A3 已完成，后续进入维护模式；不继续进行本地优先重构或功能追平，只接受安全、关键缺陷和同步兼容工作。
- iOS：A4 已完成；保留 Repository Protocol 和既有 Use Case 边界，作为本地 Repository 与 Sync Engine 的接入点。
- Edge：在共享核心和契约稳定后，再按采集、候选、表达、反馈和持久化边界拆 `index.ts`。

每个端侧切片必须有特征测试、模块 Spec 和回归证据，不能以“文件变小”作为完成标准。

### L0-L5：iOS 本地优先产品线

- L0 只固化产品和架构契约，不引入数据库依赖或修改业务代码。
- LOCAL-SPIKE-001 使用可丢弃实验比较 GRDB/SQLite 与 SwiftData，不预先锁死选型。
- L1 只实现消费记录完整垂直切片，必须先证明免登录、断网、重启、导出恢复和网络闸门。
- L2-L5 依次处理老用户迁移、同步、AI Provider 和其他数据域，前一阶段未完成不得并行铺开。
- PWA 保持现有云端架构，已同步数据继续遵守跨端共享契约。

任务完成不能只以聊天回复为证据。

## 7. 终止与回滚条件

遇到以下任一情况，立即停止当前阶段，不继续扩展范围：

- 无法确认文件或分支归属；
- 发现本地 WIP 可能覆盖线上唯一版本；
- 需要修改生产配置、数据库或部署状态但没有授权；
- 共享规则出现第二份实现且无法确定权威来源；
- 测试失败原因无法区分业务、环境和基线问题；
- 阶段索引、Spec、ADR 和代码状态互相矛盾。

回滚优先使用可恢复的补丁、独立分支或 revert，不使用破坏性 Git 操作。

## 8. 完成标准

本计划全部完成需要同时满足：

1. 所有 worktree 和历史分支都有明确处置记录。
2. 根工作区没有未登记的 WIP。
3. 生产代码不再反向依赖 `tools/`。
4. 共享规则核心通过 Deno 和 Node 双运行时测试。
5. PWA、iOS、Edge 的模块边界和跨端契约有测试证据。
6. 最新 fresh-agent 能在新会话中恢复当前阶段和后续路线。
7. 线上部署版本、迁移状态和发布提交可追溯。
