# 芥子 TDD 实施与交接规范

> 规范编号：QUALITY-TDD-001
>
> 文档版本：0.1
>
> 状态：试行
>
> 适用范围：PWA、iOS、Edge Function、Supabase 数据库及跨端核心业务变更
>
> 关联约束：[系统总览规格说明](00-系统总览规格说明.md)、[跨端一致性契约](01-跨端一致性契约.md)、[测试策略与验证门禁](测试策略与验证门禁.md)

## 1. 规范目的

本规范约束芥子如何从中文规格进入测试和实现，确保每次开发开始前有明确边界，开发过程中有可验证证据，结束后能被下一位开发者或 AI 接续。

TDD 在本项目中的目标不是追求测试数量或覆盖率，而是保护高风险业务不变量：用户隔离、金额和时间口径、状态出口、幂等、账户影响、删除级联及 PWA/iOS 一致性。

## 2. 核心原则

1. **规格先于代码**：没有场景编号、输入、动作和预期结果，不开始业务实现。
2. **一个切片一次闭环**：一轮只处理一个可验收场景或一组不可拆分的紧密场景。
3. **权威层优先**：事务、权限、金额和删除级联先由数据库或 Edge 测试证明，客户端不重复模拟服务端事实。
4. **先证明测试有效**：新增行为必须看到测试因目标行为缺失而失败，再写最小实现。
5. **已有系统先做特征测试**：现有正确行为先被测试固定；这类测试第一次通过是正常的，不伪装成“先红后绿”。
6. **跨端统一业务，不统一组件**：PWA 和 iOS 共享场景与预期，可以采用不同交互和测试工具。
7. **证据优于改动量**：新增或删除多少行不能证明质量；必须说明改动对应哪个规则、由哪个测试保护。
8. **范围扩张先暂停**：实际需要修改的模块超出开始前声明的范围时，先解释原因并重新确认，不顺手扩大重构。

## 3. 适用与不适用范围

### 3.1 必须使用本规范

- 新增或改变业务状态、状态出口和状态显示分类。
- 金额、账户余额、账户流水、收入、支出和还款影响。
- 日期、时区、统计口径和记录归属。
- 重复识别、幂等、并发、重试和失败恢复。
- 登录、用户切换、RLS、图片权限和缓存隔离。
- 保存、确认、归档、丢弃、删除及其级联影响。
- PWA 与 iOS 共享的核心闭环。
- 已发生回归问题的修复。

### 3.2 不要求严格先写自动化测试

- 纯文档、注释和不改变行为的命名修正。
- 设计 Token 的机械生成产物；生成器本身仍应验证。
- 纯视觉颜色、间距、字体和动画调整。
- 一次性诊断脚本且不会进入产品运行路径。

视觉变更虽然不要求像素测试先行，但必须先固定页面行为、信息层级、加载、空、错误、保存、删除、导航和无障碍要求，并在实现后做截图或真机验收。

## 4. 术语

| 术语 | 含义 |
|---|---|
| Spec 场景 | 带稳定编号的 Given/When/Then 业务要求，例如 `REC-009` |
| 特征测试 | 固定现有系统真实且应保留的行为，避免重构时误改 |
| 红灯 | 测试因目标行为尚未满足而失败，不是因为语法、环境或凭据错误 |
| 绿灯 | 最小实现使目标测试及相关回归测试通过 |
| 重构 | 在测试保持通过的前提下改善结构，不新增未声明行为 |
| Fixture | 脱敏、稳定、可版本化的测试输入和预期结果 |
| 垂直切片 | 一个场景从权威层、客户端到验证门禁的完整小闭环 |
| 门禁 | 失败时阻止合并或交付的自动化验证 |

## 5. 开始前门禁

每轮 TDD 开始前必须完成以下检查：

1. 读取当前 worktree 的 `AGENTS.md`、相关领域 Spec 和本规范。
2. 运行 `git status --short --branch` 和 `git worktree list --porcelain`。
3. 确认只在当前任务 worktree 工作，不清理根工作区或其他 worktree 的 WIP。
4. 选择本轮场景编号，说明用户价值、风险和不做的范围。
5. 列出预计新增或修改的文件类别，不要求预知精确行数。
6. 找到该场景的服务端权威层和现有测试入口。
7. 运行相关基线测试；已有失败必须记录，不能混入本轮成果。
8. 明确是否需要数据库、Edge、PWA、iOS 或端到端验证。
9. 未经用户确认，不执行生产迁移、生产部署、TestFlight、提交、推送或 PR。

在上述信息向用户说明并获得当前实现范围确认前，不修改业务代码。

## 6. 场景执行记录

每个垂直切片应保留一份简短执行记录。可以写入领域 TDD 清单，也可以放在 `docs/spec/执行记录/` 下，文件名使用中文并包含场景编号。

执行记录至少包含：

```markdown
# REC-009 TDD 执行记录

- 目标行为：
- 当前行为：
- 权威来源：
- 本轮范围：
- 非范围：
- 预计修改文件：
- 基线测试结果：
- 红灯测试及失败原因：
- 最小实现：
- 绿灯结果：
- PWA/iOS 差异：
- GitHub CI 结果：
- 未解决风险：
- 对应提交：
```

“对应提交”只有在用户授权并实际提交后填写。不得为了填满模板虚构测试、CI 或提交结果。

## 7. 标准 TDD 流程

### 7.1 确认现状

先阅读服务端、PWA 和 iOS 的相关实现，判断本轮属于哪一种情况：

- 行为已正确但没有测试：先写特征测试，固定现状。
- 行为缺失：进入标准红灯、绿灯、重构。
- 行为错误：先写能复现错误的回归测试。
- 规格与实现冲突：暂停实现，先裁决并更新 Spec。
- 无法从代码判断真实数据：设计只读审计，不猜测生产现状。

### 7.2 准备 Fixture

- Fixture 使用虚构 UUID、邮箱、金额、时间和图片 hash。
- 不保存真实访问令牌、生产响应、用户截图或可识别个人信息。
- 生产问题可以提炼为回归 fixture，但必须先脱敏并裁剪为复现规则所需的最小字段。
- 同一跨端场景尽量共享业务输入和预期结果，不要求 Swift 与 JavaScript 直接读取同一文件。
- Fixture 必须包含版本和场景编号；规则改变时明确升级版本，不静默覆盖历史预期。
- 时间场景必须包含上海日期边界、UTC 跨日或旧字段降级中的相关样本。

### 7.3 建立红灯

1. 写最小测试，只断言当前场景的核心结果。
2. 运行测试并确认它失败。
3. 检查失败原因确实是目标行为缺失，而不是编译错误、测试数据错误、网络不通或环境变量缺失。
4. 记录测试名称、命令和关键失败信息。
5. 红灯未被证明前，不进入业务实现。

对于 Windows 无法执行的 iOS XCTest，经用户授权后使用独立分支和 GitHub macOS CI 证明红灯。最终可合并状态必须恢复为绿色，不把失败门禁留给主分支。

### 7.4 最小实现

- 只修改使当前测试通过所必需的代码。
- 优先复用现有 Repository、AppState、RPC、设计系统和状态模型。
- 不借机更换框架、重写整个页面或统一无关命名。
- 若发现必须跨越声明的模块边界，暂停并向用户说明新增范围和原因。
- 服务端写入成功与客户端刷新失败必须分开处理，不能通过重复写入掩盖读取失败。

### 7.5 绿灯与回归

1. 运行新增测试，确认通过。
2. 运行该模块原有测试。
3. 运行受影响平台的构建或静态检查。
4. 检查测试在移除关键实现后会重新失败，避免无效断言。
5. 记录通过命令和结果，不用“应该通过”代替真实证据。

### 7.6 重构

只有绿灯后才能重构。重构应减少重复或改善边界，不改变本轮 Spec。重构后重新运行相同测试和受影响回归集合。

### 7.7 跨端收敛

- 先证明权威层结果，再验证 PWA 与 iOS 如何调用和展示。
- 两端测试使用相同场景编号。
- 允许一端标记“无需重复验证”，但必须说明业务事实已在哪一层证明，以及该端仍需验证什么。
- 平台特有交互通过平台测试验证，不能写入共享业务规则。

## 8. 测试层职责

| 测试层 | 主要职责 | 不应替代 |
|---|---|---|
| Node 纯逻辑测试 | 日期、金额、状态映射、动作权限、聚合 | 数据库事务和真实 UI |
| Vue 组件测试 | 加载、错误、禁用、确认门禁和用户操作 | RPC 原子性 |
| Deno Edge 测试 | 鉴权、识别分支、阈值、去重、错误分层 | 数据库级联完整性 |
| PostgreSQL fixture | RLS、行锁、幂等、账户影响、删除级联和迁移重复执行 | 客户端导航与文案 |
| iOS XCTest | Model、Presenter、Repository 参数、AppState 刷新和用户切换 | macOS 编译以外的平台事实 |
| Playwright/XCUITest | 少量关键用户闭环 | 全量状态组合和底层事务 |
| 截图/真机验收 | 视觉层级、布局、长文本、动态字体和系统交互 | 业务正确性 |

测试应放在最低且最权威的合理层级。能够用纯函数或数据库 fixture 稳定证明的规则，不优先使用慢且脆弱的端到端测试。

### 8.1 生成式 AI 与表达类 TDD

生成式表达遵循“代码负责算，模型负责说”。TDD 固定事实、候选、证据和边界，不把某一句文案固定为唯一答案。

- **代码负责**：实体归一化、金额解析、时间语义、统计口径、候选生成、候选排序、证据摘要、置信度和禁止断言。
- **模型负责**：在允许边界内选择是否表达候选，并生成自然、非固定的语言。
- **测试输入**：使用脱敏记录、冻结模型输出或可控 stub；核心门禁不得依赖在线模型随机返回。
- **测试断言**：优先断言候选编号、来源字段、语义区间、允许/拒绝结果和是否包含未经授权的硬事实。
- **不测试固定文案**：除协议字段、错误提示等产品明确要求的稳定文本外，不要求模型逐字输出某句话。
- **允许合理模糊**：时间和程度词按自然语义区间验证，例如 `17:43` 可以写“快六点”，`17:13` 不能写“快四点”。
- **关系保持候选性**：跨记录或跨域关系由代码提供证据和置信度；模型可以不表达，但不得把“可能相关”说成已经确认。
- **逐层抢救**：同一模型响应中的一个字段违规时，优先只拒绝该字段；只有共享事实基础失效时才整体回退。

生成式场景的红灯应证明某个确定性门禁缺失或错误，例如“错误时间文案被放行”，而不是证明在线模型这一次没有生成理想措辞。

## 9. 追踪与命名

- 测试名称、Fixture、执行记录和 PR 描述至少有一处包含场景编号。
- 推荐测试名称表达行为，例如 `REC-009 达到重试上限后仍保留人工出口`。
- 不以函数名、文件名或组件内部结构作为唯一测试描述。
- 一个测试只验证一个主要失败原因；多个不可拆分断言必须共同描述同一业务结果。
- Spec 变化时先更新场景，再更新测试，不通过删除断言来迁就实现。

完整追踪链为：

```text
中文 Spec 场景
→ 脱敏 Fixture
→ 红灯或特征测试证据
→ 最小实现
→ 绿灯和回归证据
→ PWA/iOS 对应验证
→ GitHub 门禁
→ 交接记录
```

## 10. 改动范围与差异说明

### 10.1 修改前

开始编辑前向用户说明：

- 本轮场景编号和目标行为。
- 预计涉及的模块和文件类别。
- 为什么这些文件必须改变。
- 明确不改的范围。
- 预计先出现哪一条失败测试。

### 10.2 修改中

- 每完成一个阶段汇报红灯、绿灯或阻塞状态。
- 发现改动范围扩大时先停止新增编辑并解释。
- 不用新增行数衡量进度，不为了降低 diff 人为压缩可读代码。
- 生成文件与手写源文件分开说明；设计系统产物由生成器产生，不手改 `dist/`。

### 10.3 修改后

交付时说明：

- 实际修改文件及用途。
- `git diff --stat` 所反映的增删规模。
- 与开始前预期相比是否扩大范围。
- 新增测试抓住了什么错误。
- 实际运行过哪些命令，哪些因环境限制未运行。
- 尚未关闭的风险和下一步。

行数对不上不自动代表错误，因为回退、移动、格式化和重新实现会改变 Git 的逐行统计；但任何超出声明范围的大幅变化都必须能用场景和测试解释。

## 11. Git 与 CI 规范

- 每轮核心 TDD 使用独立 `codex/` 分支和专用 worktree，除非用户指定其他位置。
- 不进入根工作区清理、重置或吸收用户 WIP。
- 不使用 `git add -A`；获得暂存授权后逐文件确认。
- 红灯可以保留在本地执行记录；需要 GitHub 验证 iOS 红灯时，必须先获得推送授权。
- PR 的最终提交必须通过适用门禁，不允许以“测试稍后补”为完成条件。
- PWA/Edge/数据库使用 `release-validation.yml` 及相关专项命令。
- iOS 使用 `ios-build.yml` 的 macOS Simulator Build 和 `SnapCountTests`。
- Windows 不能作为 Swift 编译结论。
- TestFlight 只能从通过 iOS Build/测试的固定提交手动触发，且需要用户当前任务明确授权。

## 12. 失败处理

| 失败类型 | 处理方式 |
|---|---|
| 新测试按预期失败 | 记录红灯，进入最小实现 |
| 新测试意外通过 | 判断行为是否已存在；改为特征测试或加强无效断言 |
| 测试因环境失败 | 修复环境或标记阻塞，不能当作业务红灯 |
| 原有测试在修改前已失败 | 记录为基线问题，不冒充本轮回归 |
| 无关测试在修改后失败 | 分析是否存在隐藏影响；未解释前不交付 |
| GitHub 与本地结果不同 | 以日志和实际平台为准，尤其 iOS 以 macOS CI 为准 |
| 生产数据现状未知 | 只读审计，未经授权不修复、不迁移 |

为了让测试通过而降低断言、扩大 mock、跳过测试或删除门禁，视为未完成。

## 13. 交接包

每轮 TDD 结束后，下一位接手者应能仅凭仓库内容知道：

1. 本轮遵守哪份中文 Spec 和哪些场景编号。
2. 当前分支、worktree、基线提交和工作区状态。
3. 哪些测试是特征测试，哪些经历过红灯、绿灯。
4. 测试命令、Fixture 位置和 GitHub CI 结果。
5. 修改了哪些业务边界，哪些明确没有修改。
6. 仍未处理的失败、风险、待裁决项和环境限制。
7. 是否涉及迁移、部署、真实数据、TestFlight，以及这些操作是否实际执行。

禁止在交接文档中写入凭据、真实用户数据、临时签名 URL 或未经脱敏的生产日志。

## 14. 完成定义

一个 TDD 场景只有满足以下全部条件才算完成：

1. 场景已在中文 Spec 中定义且没有未裁决的核心语义。
2. 特征测试或有效红灯证据已记录。
3. 最小实现和相关重构均有测试保护。
4. 权威层、受影响客户端和跨用户边界得到适当验证。
5. 相关本地测试、构建及 GitHub 门禁通过。
6. 加载、错误、重试、删除或空态中的适用状态完成验收。
7. 实际 diff 没有未说明的范围扩张。
8. 执行记录和交接信息完整。
9. 未经授权没有执行发布性或破坏性操作。

完成一个场景不代表整个领域完成。领域完成度以场景矩阵中所有必选项的状态为准。

## 15. 禁止做法

- 先完成大段实现，再补只会通过的测试。
- 只验证 mock 被调用，不验证用户可观察的业务结果。
- 在 PWA 和 iOS 分别发明同一状态的不同含义。
- 用快照测试覆盖金额、权限、账户或删除事务。
- 用端到端测试代替数据库幂等和 RLS 验证。
- 为通过测试读取生产数据、真实图片或真实凭据。
- 把 CI 未运行写成“已验证”。
- 在视觉重构中删除保存、确认、删除、导航或失败恢复门禁。
- 因为测试难写就把业务规则留在大型页面或 AppState 中继续堆叠。
- 未经说明修改与当前场景无关的文件。

## 16. 规范维护与领域执行

- 本文只保存跨领域长期有效的 TDD 规则，不保存某个功能的当前分支、worktree、批次状态或临时门禁。
- 场景顺序、产品决策、红灯/绿灯证据和未解决风险写入对应领域 Spec、评审记录或 `docs/spec/执行记录/`。
- 通用规范变更必须说明影响范围；不能为了让某一项实现通过而降低所有领域的门禁。
- 领域执行发现通用规则不适用时，先记录例外和证据，再单独评审是否升级本规范。
- 试行期间每完成一个领域切片，复盘测试价值、维护成本、跨端差异和遗漏风险。
