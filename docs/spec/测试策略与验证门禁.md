# 芥子测试策略与验证门禁

> 规格编号：QUALITY-TESTING-001
>
> 文档版本：0.1
>
> 状态：试行
>
> 适用平台：PWA、iOS、Edge Function、Supabase
>
> 实施流程：[TDD 实施与交接规范](02-TDD实施与交接规范.md)

## 1. 目标

测试的目标不是追求一个漂亮的覆盖率数字，而是证明：

- 个人数据不会跨用户泄露。
- 金额、日期、状态和账户影响稳定一致。
- AI 识别失败和网络失败有可恢复出口。
- PWA 与 iOS 在共享业务规则上不会产生矛盾。
- 视觉重构不会破坏保存、删除、确认门禁和导航。
- iOS 的 Swift 编译和 XCTest 在真实 macOS 环境通过，而不是把 Windows 静态检查当成编译结论。

## 2. 测试分层

### 2.1 PWA 和纯 JavaScript 逻辑

- 日期、金额、聚合、状态和 planner 规则优先使用 `node:test`。
- Vue 组件测试在需要验证交互状态时引入 Vitest + Vue Test Utils；当前仓库还没有统一的 Vue 组件测试入口。
- 页面关键路径使用少量 Playwright，覆盖登录、采集、待处理确认和删除等高价值流程。

### 2.2 Edge Function

- 使用 Deno Test 验证鉴权、去重、提示词输入、事实提取、时间语言、状态恢复和错误分层。
- 不使用真实生产凭据作为测试输入。
- AI 供应商响应使用脱敏 fixture 或可控 stub，避免测试受模型随机性影响。

### 2.3 数据库和迁移

- 用临时 PostgreSQL fixture 执行安全、幂等、权限和迁移升级路径。
- 迁移至少验证首次执行、重复执行和旧数据升级。
- 账户、还款、记录归档、图片清理和账号删除的事务边界必须有数据库级证据。

### 2.4 iOS

- Model、Presenter、统计和日期转换使用 XCTest。
- Repository 使用协议 Stub 验证参数、错误和刷新行为。
- AppState 使用 `@MainActor` 测试验证用户切换、导航重置、保存后刷新和失败恢复。
- XCUITest 只覆盖少量关键用户闭环，不把所有状态组合都放进端到端测试。
- 首页和其他视觉页面使用人工真机/模拟器检查或后续截图测试；视觉测试不能替代业务测试。

### 2.5 生成式 AI 与表达

- 商户归一化、金额解析、时间语义、候选生成、证据门禁和状态选择使用确定性测试证明。
- 模型调用使用脱敏 fixture、冻结输出或可控 stub；测试不依赖在线模型每次生成同一句话。
- 表达测试断言事实来源、语义边界、候选编号和禁止断言，不把某一句固定文案作为唯一正确答案。
- 允许自然语言的合理模糊区间。例如 `17:43` 可以表达为“快六点”，但 `17:13` 不能表达为“快四点”。
- 跨记录关系先由代码生成带证据和置信度的候选；模型可以选择不表达，但不能把低置信候选升级为确定事实。
- 从生产问题提炼 fixture 时必须脱敏，只保留复现规则所需的最小字段，不保存真实图片、令牌或完整用户日志。

## 3. TDD 工作循环

本节描述测试顺序；开始门禁、红灯证据、范围控制、交接记录和失败处理以 [TDD 实施与交接规范](02-TDD实施与交接规范.md) 为准。

每个详细规格场景按以下顺序实现：

1. 写一个能表达业务规则的失败测试。
2. 写最小实现使测试通过。
3. 重构实现和测试，保持行为不变。
4. 在另一平台执行对应契约测试。
5. 执行视觉或真机验收（如果涉及 UI）。
6. 将测试、fixture、文档和 CI 结果绑定到同一个变更。

视觉页面不采用像素级测试先行，而采用“行为规格先行、实现后截图验收”。

## 5. GitHub 验证门禁

### 5.1 PWA/Edge 门禁

现有 `release-validation.yml` 已执行：

- `npm ci` 和 `npm run build`。
- 待处理队列、财务选项、财务时间、表达展示等 Node 检查。
- Edge Function `deno check` 和指定 Deno 测试。
- Expression Planner Node 测试。
- 迁移版本、重复识别、安全契约和 PostgreSQL fixture。

后续应逐步增加统一入口，例如 `npm run test:unit`，但不能为了统一命令删除已有的专项门禁。

### 5.2 iOS 门禁

现有 `ios-build.yml` 在 PR 修改 `ios/**` 或相关 workflow 时：

1. 在 macOS runner 安装 XcodeGen。
2. 从 GitHub Secrets 生成 `GeneratedAppConfig.swift`。
3. 使用 `project.yml` 生成 Xcode 工程。
4. 编译 iOS Simulator 目标。
5. 运行 `SnapCountTests`。
6. 由 `iOS Build Gate` 阻断相关 PR 的合并。

Windows 可以执行 Markdown、Node generator、静态检查和 diff 检查，但不能替代 macOS 的 Swift 编译和模拟器测试。

### 5.3 发布边界

- 视觉分支和测试分支不执行生产迁移、生产部署或 TestFlight 上传。
- TestFlight 只能从通过 iOS Build/单测的固定提交手动触发，并需要用户明确授权。
- CI 失败时根据当前提交日志修复，不通过重置或覆盖其他 worktree 恢复。

## 6. 完成定义

### 6.1 核心业务功能

- 有中文详细规格和成功、空态、失败、重试、删除场景。
- 关键规则拥有先失败后通过的自动化测试。
- PWA 构建和相关专项测试通过。
- Edge Function 和数据库 fixture 通过（若受影响）。
- iOS Build 和 XCTest 通过（若受影响）。
- PWA/iOS 差异已记录且不违反跨端契约。

### 6.2 视觉和交互功能

- 行为契约和数据来源已固定。
- 保留 AppState、Repository、导航、保存、删除和确认门禁。
- 加载、缓存、错误、空态、长文本和权限状态均有明确表现。
- 完成真机/模拟器截图或人工验收。
- 视觉变更不引入新的业务事实或统计口径。

## 7. 第一轮跨端 TDD 试点

首个领域试点为 [记录生命周期规格说明](10-记录生命周期规格说明.md)。具体批次、产品决策、执行状态和工作树信息属于领域执行文档，不写入本通用策略。

每个试点场景都应至少关联一项权威层或客户端测试，并为 PWA、iOS、Edge 和数据库逐项说明“需要验证”或“无需重复验证”的理由。

## 8. 测试命名和追踪

- 系统级：`SYS-*`、`CROSS-*`、`QUALITY-*`。
- 记录领域：`REC-*`。
- 账户领域：`ACC-*`。
- 数据域领域：`DOM-*`。
- 每条详细规格场景在测试名称、fixture 或 PR 描述中保留规格编号。
- 测试描述使用用户行为和业务结果，不使用实现细节作为唯一断言。
