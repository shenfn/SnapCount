## 1. 文档目的

本文档固定一条记录从采集、识别、去重、待处理、确认或归档，到查看、删除和关联清理的跨端业务含义，并把关键规则写成可直接转化为自动化测试的验收场景。

本文档首先描述当前数据库、Edge Function、PWA 和 iOS 已经共同依赖的契约，再标出 TDD 试点需要补强但尚未实现的验证要求。现有代码行为与本文档冲突时，不直接修改实现，应先确认冲突是历史兼容、实现缺陷还是规格需要调整。

## 2. 范围与非范围

### 2.1 本规格覆盖

- PWA、iOS、快捷指令、相机、相册和文件上传产生的图片记录。
- 支出、收入和动态数据域的识别与正式入库。
- 手动创建记录与图片识别记录在正式记录阶段共享的保存、查看和删除规则。
- 精确重复、疑似重复和幂等重试。
- `transactions.status` 与 `staging_records.status` 两套待处理机制。
- 待补全支出的确认、转收入、账户影响和刷新。
- 中转记录的重试、人工修正、归档和丢弃。
- 正式记录删除后的账户流水、图片、AI 表达产物和客户端缓存清理。
- 用户切换、会话失效、网络失败和局部刷新失败。

### 2.2 本规格不覆盖

- 账户余额、负债和还款的完整领域规则；这里只规定记录操作直接造成的账户影响。
- 每个动态数据域的字段 schema 和指标口径。
- AI 提示词、模型选择和陪伴文案的具体生成策略。
- 首页、记录页或待处理页的最终视觉方案。
- 生产迁移、生产部署、TestFlight 上传和历史数据批量修复授权。
- 为旧状态补数据的具体迁移脚本。

## 3. 术语与实体边界

### 3.1 正式记录

正式记录是可以进入事实列表的业务实体：

| 类型 | 权威表 | 正式状态 | 统一引用 |
|---|---|---|---|
| 支出 | `transactions` | `status = done` | `expense/<uuid>` |
| 收入 | `income_records` | 成功写入即为正式记录 | `income/<uuid>` |
| 通用数据 | `data_records` | 成功写入即为正式记录 | `data/<uuid>` |

只有符合各页面统计口径的正式记录才可进入首页、记录、账户和分析统计。删除后的记录不再是事实，客户端不得继续展示旧详情或旧表达。

### 3.2 待补全支出

`transactions.status = pending` 表示一条已经识别为财务记录、但必要字段或置信度不足的待补全交易。它仍位于 `transactions`，但不是已确认支出，不进入确认统计。

它的用户出口是：

- 补全并确认为支出，原行转为 `done`。
- 改判为收入，创建 `income_records` 后删除源 `transactions` 行。
- 用户明确删除该待补全交易。

### 3.3 中转记录

`staging_records` 用于保存无法自动完成归档的图片识别结果，包括识别失败、无法路由、字段结构异常、低置信度和疑似重复。

中转记录不是正式记录，不进入确认统计。`archived`、`discarded` 等状态描述的是中转任务的处理结果，不等同于正式记录自身的状态。

### 3.4 AI 识别日志

`ai_recognition_logs` 是识别过程、模型结果、错误和目标关联的审计记录。它不是正式记录，也不能作为余额或统计事实。日志可关联 `staging_record_id` 或正式记录，但关联关系不赋予其业务状态。

### 3.5 展示分类不是数据库状态

iOS 当前把多种 `staging_records.status` 汇总为以下展示分类：

| 展示分类 | 原始状态 |
|---|---|
| 识别失败，可重试 | `ai_error`、`failed`、`extraction_failed` |
| 需要修复 | `schema_failed` |
| 待分类 | `routing_failed`、`unrouted`、`unassigned` |
| 待确认 | `pending_review`、`routed`、`extracted` |
| 已解决，默认不进入待处理列表 | `confirmed`、`archived`、`discarded`、`assigned` |

PWA 和 iOS 可以使用不同分组名称，但不能把展示分类写回数据库，也不能据此改变原始状态含义。

## 4. 记录采集入口

### 4.1 图片采集

图片可以来自快捷指令、PWA 文件选择、iOS 相机或相册。上传请求必须绑定当前有效会话；服务端以已认证用户为数据归属，不信任客户端单独提交的 `user_id`。

一次图片采集至少携带图片内容。可选上下文包括来源应用、采集方式、客户端采集时间和 OCR 文本。重试中转记录时，客户端只需提交 `staging_record_id`；服务端按当前用户读取原图，不要求用户再次选择图片。

### 4.2 手动采集

手动创建不经过 AI 去重和中转状态机，直接走对应正式记录的保存契约。手动支出和收入仍须遵守金额、时间、账户影响、统一引用和删除规则；手动通用数据仍须使用有效数据域。

### 4.3 鉴权失败

- 未登录或令牌失效时，不创建图片、日志、中转记录或正式记录。
- 客户端结束加载状态，提示重新登录，并阻止用旧用户缓存伪装成功。
- 用户切换期间返回的旧请求结果必须被丢弃，不能写入新用户的内存状态。

## 5. 去重与幂等契约

### 5.1 用户作用域

图片 hash、感知 hash、源中转记录和目标记录的重复检查全部限制在当前用户内。同一图片属于不同用户时，不得互相命中、暴露记录存在性或共享签名 URL。

### 5.2 精确重复

当图片内容 hash 与当前用户已有数据相同时：

1. 若已存在正式记录，返回重复结果和已有目标引用，不创建第二条正式记录。
2. 若不存在正式记录但存在尚未解决的中转记录，返回已有中转记录，不创建第二条中转记录。
3. 若命中已解决中转记录，应以其有效 `target_record_id` 和正式目标为准，不重新入账。
4. 重复响应必须可被客户端当作已处理结果，而不是无休止重试的系统错误。

### 5.3 疑似重复

感知 hash 只代表图片相似，不能证明业务记录相同。当前财务图片命中疑似重复时：

- 不静默丢弃，也不自动创建正式记录。
- 创建 `staging_records.status = pending_review`。
- 保存被比对记录的引用、距离或等价证据。
- 用户可以确认是新记录并归档，也可以丢弃。

非财务动态域是否启用同一感知重复规则，当前未形成统一契约，见第 18 节。

### 5.4 操作幂等

- `archive_staging_record` 锁定当前用户的中转行；已 `archived` 且有 `target_record_id` 时，重复调用返回同一目标并标记 `idempotent_retry = true`。
- 中转归档还使用用户级图片 hash 和 `staging_record_id` 唯一关系避免重复目标。
- `confirm_pending_transaction_with_account` 锁定待补全交易；重复确认支出返回同一 `done` 交易，重复转收入通过 `source_pending_transaction_id` 返回同一收入。
- 客户端超时后不得先本地创建替代记录；应以相同业务 ID 重试或刷新服务端事实。

## 6. 识别与自动入库判定

### 6.1 支出

识别结果同时满足以下条件时自动写入 `transactions.status = done`：

- 金额有效。
- 平台、分类和支付方式完整。
- AI 置信度不低于 `0.70`。

否则写入 `transactions.status = pending`，供用户补全。`pending` 不进入已确认支出统计。

### 6.2 收入

识别为收入、金额有效且置信度不低于 `0.70` 时，直接写入 `income_records`。不满足自动入库条件的财务结果进入中转或待补全路径，具体取决于是否已经可靠识别为财务记录及现行 Edge 分支。

### 6.3 内置数据域

运动、睡眠、阅读、饮食、钱包等内置域满足以下条件时自动归档到 `data_records`：

- 找到当前用户可用的 active 数据域定义。
- 结构化 payload 的必填字段完整。
- AI 置信度不低于 `0.75`。

缺字段或置信度不足时创建 `staging_records.status = pending_review`。已识别域但 schema 构建失败时进入 `schema_failed`；无法找到或可靠选择域时进入 `routing_failed`。

### 6.4 识别与路由失败

- AI 供应商或识别过程失败：`ai_error`。
- 财务结果缺少金额、记录类型不确定或无法路由：`routing_failed`。
- 旧实现可能保留 `failed`、`extraction_failed`、`unrouted` 或 `unassigned`；客户端必须提供与其语义一致的恢复出口。

## 7. 待补全交易状态机

### 7.1 状态流转表

| 当前状态 | 含义 | 合法后续结果 | 触发操作 | 终态 |
|---|---|---|---|---|
| `pending` | 已识别财务记录，尚未确认 | `done` | 补全并确认为支出 | 否 |
| `pending` | 同上 | 创建收入并删除源交易 | 改判并确认为收入 | 对源行是终止 |
| `pending` | 同上 | 行被删除 | 用户确认删除 | 对源行是终止 |
| `done` | 已确认支出 | 保持 `done` 或行被删除 | 幂等确认、编辑、确认删除 | 业务有效终态 |

### 7.2 确认为支出

确认请求必须包含有效金额和 `entry_type = expense`。服务端通过 `confirm_pending_transaction_with_account` 和账户保存 RPC 更新同一交易：

- 状态转为 `done`。
- 保留源图片、图片 hash、伴随文案和原发生时间。
- 使用上海时区解释发生日期；`occurred_at` 优先于旧 `transaction_date`。
- 有有效 `account_id` 时产生规定的账户流水；无账户时保留记录但不伪造余额影响。
- 重复请求返回同一交易，不产生第二笔账户流水。

### 7.3 改判为收入

确认请求使用 `entry_type = income`：

1. 服务端以源交易的 `occurred_at` 和上海日期创建收入。
2. 收入记录写入 `source_pending_transaction_id`。
3. 成功后删除源 `transactions` 行。
4. 整个操作必须保持事务性；失败时不能同时留下可统计的支出和收入。
5. 重复请求通过 `source_pending_transaction_id` 返回同一收入。

## 8. 中转记录状态机

### 8.1 当前允许的原始状态

数据库当前允许：`unassigned`、`assigned`、`discarded`、`failed`、`unrouted`、`routed`、`routing_failed`、`extracted`、`pending_review`、`confirmed`、`archived`、`extraction_failed`、`schema_failed`、`ai_error`。

### 8.2 完整出口表

| 当前状态 | 当前语义 | 用户可见出口 | 可能结果 | 出口完整性 |
|---|---|---|---|---|
| `ai_error` | 当前 AI 识别失败 | 重试、人工修复/归档、丢弃 | 新失败态、`pending_review`、`archived`、`discarded` | 完整 |
| `failed` | 历史通用失败 | 重试、人工修复/归档、丢弃 | 同上 | 完整 |
| `extraction_failed` | 历史提取失败 | 重试、人工修复/归档、丢弃 | 同上 | 完整 |
| `schema_failed` | 已识别但结构不满足 schema | 修正字段并归档、丢弃 | `archived`、`discarded` | 完整 |
| `routing_failed` | 无法可靠选择目标域 | 选择域、人工修复/归档、重试、丢弃 | 新失败态、`pending_review`、`archived`、`discarded` | 完整 |
| `unrouted` | 历史未路由 | 选择域、人工修复/归档、重试、丢弃 | 同上 | 完整 |
| `unassigned` | 历史未分配 | 选择域、人工修复/归档、重试、丢弃 | 同上 | 完整 |
| `pending_review` | 低置信、缺字段或疑似重复 | 核对/修正后归档、丢弃 | `archived`、`discarded` | 完整 |
| `routed` | 历史已路由未完成 | 核对/修正后归档、丢弃 | `archived`、`discarded` | 完整 |
| `extracted` | 历史已提取未完成 | 核对/修正后归档、丢弃 | `archived`、`discarded` | 完整 |
| `archived` | 已创建或关联正式目标 | 打开目标、删除正式目标 | 保持 `archived`；正式目标可独立删除 | 中转终态 |
| `discarded` | 用户明确放弃 | 无再次归档入口 | 保持 `discarded` | 中转终态 |
| `assigned` | 历史已分配/已解决 | 默认隐藏 | 保持 `assigned` | 历史终态，目标完整性待审计 |
| `confirmed` | 历史已确认/已解决 | 默认隐藏 | 保持 `confirmed` | 历史终态，目标完整性待审计 |

表中的“人工归档”表示用户选择目标域并补齐该目标所需字段，不表示绕过金额、域或权限校验。客户端是否已经为每个失败分类提供全部入口，需要在 TDD 实施前做差异测试。

### 8.3 重试规则

> 已确认决策（2026-08-09）：达到三次重试上限后，PWA 与 iOS 都必须保留人工归档、人工修复和丢弃出口。

- 重试通过原 `staging_record_id` 和当前用户的原图调用 `ingest-receipt`。
- 最多允许 3 次；达到上限后服务端拒绝继续 AI 重试。
- `retry_count` 只统计重试尝试，不把首次识别计入三次重试。
- 达到上限后仍必须保留人工选择域、编辑/修复和丢弃出口，界面不能只留下禁用的“重试”按钮。
- 达到上限后不再显示可点击的重试入口，改为“已达重试上限，请人工处理”的状态说明。
- 原图不存在或无法下载时，重试失败但记录不得消失；用户仍可根据已保存字段人工处理或丢弃。
- 重试产生的正式目标必须复用原中转关系，并最终把源中转记录置为 `archived`。

### 8.4 归档规则

`archive_staging_record` 是中转归档的权威原子操作：

- 锁定 `id + auth.uid()` 对应中转行。
- `expense` 和 `income` 要求金额大于 0。
- 支出调用账户支出保存 RPC，收入调用账户收入保存 RPC。
- 其他域必须找到 active 且对当前用户可见的数据域，再写入 `data_records`。
- 以中转图片 hash 和中转关系查找已有目标，避免重复创建。
- 成功后设置 `status = archived`、`target_record_id`、`target_domain_id`（适用时）、`resolved_action = archived` 和 `resolved_at`。
- 返回统一目标引用；客户端刷新正式列表、待处理计数、账户和相关页面。

### 8.5 丢弃规则

`discard_staging_record` 是中转丢弃的权威操作：

- 锁定当前用户的中转行。
- 已 `archived` 的中转记录不能再丢弃，避免把正式记录的来源关系改写为放弃。
- 对云端原图先验证路径所有权，再加入 `image_cleanup_queue`；外部 URL 不作为本系统对象删除。
- 成功后设置 `status = discarded`、`discard_reason`、`resolved_action = discarded` 和 `resolved_at`。
- 清理队列异步失败不回滚“用户已丢弃”的业务结果，但必须保留可重试的清理状态。

## 9. 时间、金额与字段契约

### 9.1 时间

- `occurred_at` 是跨端首选发生时间。
- 面向用户的日期 key 按 `Asia/Shanghai` 解释。
- 旧财务记录缺少 `occurred_at` 时，使用业务日期字段；再缺失时才使用服务端当前上海日期。
- 确认、归档和重试不得把原发生时间静默改为操作时间。
- `created_at` 表示系统创建时间，不替代业务发生时间。

### 9.2 金额

- 支出和收入正式入库金额必须大于 0。
- 客户端展示格式不能改变数据库金额值；业务计算不以格式化字符串或二进制浮点显示值作为权威。
- 未识别到金额的财务图片不得自动进入正式财务统计。
- 本轮不新增多币种换算规则；币种能力需另立规格。

### 9.3 字段与来源

- 原始图片路径、图片 hash、AI 摘要、结构化 payload 和用户修正值应保持可追溯关系。
- 用户修正后的正式字段优先于 AI 候选；后续表达不得再次用旧候选覆盖用户确认。
- 动态域未知字段应保留在 `payload_jsonb`，客户端以通用降级展示，不因不认识字段而删除数据。

## 10. 正式记录删除

### 10.1 权威入口

PWA 和 iOS 都通过后端 `delete_record` action 调用 `delete_record_with_cleanup`，不得只从本地数组移除。支持的规范类型为 `expense`、`income`、`data`；后端可接受兼容别名。

### 10.2 删除级联

| 被删除记录 | 必须同步处理 |
|---|---|
| 支出 | 先作废该记录对应账户流水，再删除 `transactions` 行 |
| 收入 | 先作废该记录对应账户流水，再删除 `income_records` 行 |
| 通用数据 | 删除 `data_records` 行；若该域另有账户语义，应由账户领域规格补充，不能由客户端猜测 |
| 任一正式记录 | 清理相关表达偏好信号、反馈、曝光、投递快照和 shadow run |
| 任一正式记录 | 仅在原图属于当前用户且不再被其他业务记录引用时加入图片清理队列 |
| 任一正式记录 | 清除详情、列表、统计、图片 URL 和表达计划等客户端缓存，并退出已删除详情 |

删除触发表达偏好或反馈变化时，应废弃旧偏好快照并推进偏好 revision，避免后续表达继续引用已删除事实。

### 10.3 删除失败与重试

- 权限不足或记录不存在时，客户端不得假装删除成功。
- 账户流水作废或主记录删除失败时，事务应失败，不留下余额已恢复但记录仍在的半状态。
- 主记录删除成功而图片异步清理尚未完成时，业务删除视为成功；清理队列独立重试。
- 客户端收到超时但结果未知时，先按记录 ID 刷新；若服务端已不存在该记录，则按删除成功收敛。

## 11. 缓存、刷新与并发

- 保存、确认、归档或删除期间，同一记录的重复提交控件应禁用或合并请求。
- 服务端成功后，本地乐观更新只能作为体验优化；随后至少刷新受影响的待处理、正式列表和账户事实。
- 局部刷新失败时保留服务端操作成功的提示，并标记页面需要重试刷新，不得重新执行会产生业务影响的写操作。
- 详情页正在展示的记录被另一端删除时，刷新结果应关闭详情并提示记录已不存在。
- 旧用户请求通过 generation、user ID 或等价令牌检查失效，不能覆盖新用户状态。

## 12. PWA 与 iOS 行为契约

### 12.1 必须一致

- 同一原始状态的业务含义、是否进入统计和合法出口。
- 精确重复、疑似重复、重试上限和幂等结果。
- 金额、发生日期、账户影响和删除级联。
- 归档、确认、丢弃和删除的确认门禁与错误反馈。
- 用户切换后的缓存隔离。

### 12.2 允许差异

- PWA 可以提供批量归档或批量丢弃；每一项仍须遵守同一 RPC 和失败结果，不能把部分成功显示为全部成功。
- iOS 可以用 Sheet、NavigationStack、相机、相册和触觉反馈；PWA 可以用页面、弹窗和文件选择。
- 两端可以使用不同的展示分类、图标和布局，但必须能够看到加载、空、失败、重试上限、保存中和部分刷新失败状态。
- XCUITest 和 Playwright 只覆盖关键闭环，状态组合主要由单元、Edge 和数据库测试验证。

## 13. 可执行验收场景

以下场景中的“存在”均限定在同一已认证用户内。

### REC-001：已认证图片采集

- **Given** 用户会话有效，提交一张未见过的图片
- **When** 服务端完成鉴权、上传、识别和路由
- **Then** 只创建一个符合判定规则的正式记录或中转记录，并返回可追踪 ID；客户端结束加载并刷新相应列表

### REC-002：精确重复

- **Given** 同一用户已存在相同图片 hash 的正式记录或未解决中转记录
- **When** 再次提交相同图片
- **Then** 返回已有目标或中转记录，不创建第二条业务记录，不产生第二笔账户流水

### REC-003：疑似重复人工确认

- **Given** 财务图片感知 hash 与已有记录相似，但内容 hash 不同
- **When** 服务端完成识别
- **Then** 创建 `pending_review` 中转记录并保存对比证据，不自动入账；用户可以归档为新记录或丢弃

### REC-004：完整支出自动确认

- **Given** 支出金额、平台、分类、支付方式完整且置信度不低于 `0.70`
- **When** 识别成功
- **Then** 创建一条 `transactions.status = done` 的支出；有账户时只产生一次账户影响，并进入确认统计

### REC-005：不完整支出补全

- **Given** 支出缺少必要字段或置信度不足，已创建 `transactions.status = pending`
- **When** 用户补全字段并确认为支出
- **Then** 原交易变为 `done`，保留原发生时间和图片关系；待处理计数减少，正式列表和账户刷新

### REC-006：待补全支出改判收入

- **Given** 一条 `pending` 交易实际是收入
- **When** 用户选择收入并确认
- **Then** 创建一条带 `source_pending_transaction_id` 的收入、删除源交易、只产生收入账户影响；重复确认返回同一收入

### REC-007：内置数据域自动归档

- **Given** 内置域存在、必填字段完整且置信度不低于 `0.75`
- **When** 识别成功
- **Then** 创建一条 `data_records`，使用有效域和原发生时间，不在待处理队列保留第二个开放任务

### REC-008：路由或 schema 失败

- **Given** 无法可靠选择数据域，或结构化字段不满足已选域 schema
- **When** 自动归档不能安全完成
- **Then** 分别进入 `routing_failed` 或 `schema_failed`；用户可以选择域/修正字段后归档，也可以丢弃

### REC-009：重试上限与人工出口

- **Given** 中转记录已使用原图重试 3 次仍失败
- **When** 用户再次请求 AI 重试
- **Then** 服务端拒绝第四次重试，记录仍可见；客户端隐藏可点击重试，显示人工处理说明，并保留人工归档、修复和丢弃出口

### REC-010：归档与确认幂等

- **Given** 第一次归档或确认已在服务端成功，但客户端在收到响应前超时
- **When** 客户端使用相同中转 ID 或待补全交易 ID 重试
- **Then** 返回同一正式记录并标记或表现为幂等成功，不创建重复记录或重复账户流水

### REC-011：删除与账户撤销

- **Given** 一条已绑定账户的支出或收入
- **When** 用户通过确认门禁删除记录
- **Then** 服务端先作废相关账户流水再删除记录；账户余额、正式列表、统计和详情缓存收敛到删除后的事实

### REC-012：删除表达与图片清理

- **Given** 正式记录存在表达产物和属于当前用户的原图
- **When** 记录被删除
- **Then** 删除触发器清理关联表达产物；原图仅在无其他业务引用时进入清理队列，异步清理失败不恢复业务记录

### REC-013：用户隔离与会话切换

- **Given** 用户 A 的上传或刷新仍在进行，应用切换到用户 B
- **When** 用户 A 的响应晚到
- **Then** 响应不得进入用户 B 的列表、详情、图片缓存或统计；用户 B 不能通过 A 的记录 ID 操作 A 的记录

### REC-014：归档后刷新部分失败

- **Given** 中转归档已成功，随后账户或 Dashboard 刷新失败
- **When** 客户端处理结果
- **Then** 不重复归档；显示“已保存但部分数据未刷新”的可恢复状态，并允许只重试读取

### REC-015：共享原图的删除

- **Given** 两条当前用户业务记录仍引用同一路径
- **When** 删除其中一条
- **Then** 删除该业务记录和自身关联产物，但不清理仍被另一条记录引用的原图

## 15. TDD 实施顺序

第一轮不追求一次覆盖所有 UI，按风险从服务端事实向客户端收敛：

1. 用共享脱敏 fixture 固定 REC-002、REC-004、REC-005、REC-006、REC-007、REC-009、REC-010 和 REC-011。
2. 先补 PostgreSQL 和 Deno 失败测试，证明幂等、事务、阈值、用户隔离和删除级联。
3. 再补 PWA 的状态映射、刷新和错误恢复测试。
4. iOS 使用 Repository Stub 与 AppState XCTest 复现相同场景编号。
5. 业务测试稳定后，选采集、确认和删除各一条关键路径做 Playwright/XCUITest。
6. iOS 变更只以 GitHub Actions macOS Build 和 XCTest 为编译结论；Windows 只做文档、fixture 和静态检查。

## 16. 完成定义

记录生命周期 TDD 试点完成必须同时满足：

- 本规格与评审记录的阻断项已处理并复评。
- 每个纳入试点的 REC 场景至少有一个服务端权威测试和一个客户端契约测试，或有明确的不重复验证理由。
- PWA 构建、相关 Node/Deno 测试和 PostgreSQL fixture 通过。
- iOS Build 与相关 XCTest 在 GitHub macOS runner 通过。
- 失败、空、重试上限、部分刷新失败和删除后的 UI 状态完成验收。
- 未执行生产迁移、生产部署或 TestFlight 上传。

## 17. 可观测性与隐私要求

- 日志可以记录 trace ID、状态、耗时、错误类型和脱敏目标引用，不记录访问令牌或完整原图内容。
- 重复命中不得向另一个用户暴露“该图片已存在”。
- 原图留存遵循用户设置；关闭原图留存不应删除已提取的结构化事实。
- 关键漏斗至少能区分：采集、自动归档、进入待处理、重试、人工归档、丢弃和删除。是否新增埋点及留存周期需单独评审，不能在本轮文档阶段直接上线采集。

## 18. 待裁决事项

以下事项在进入完整实现前必须明确，不在本文档中擅自定案：

1. `assigned`、`confirmed` 等历史中转终态缺少 `target_record_id` 时，是只做数据审计，还是提供用户可见的恢复入口。
2. PWA 与 iOS 对 `schema_failed` 是否都已具备字段级修复表单；缺失时先支持最小人工归档还是补完整 schema 表单。
3. 感知 hash 疑似重复是否扩展到非财务数据域，以及误报时的产品阈值。
4. 三次重试上限是否按中转记录永久累计，还是在模型/提示词版本变化后允许重置；现行实现按记录累计且不自动重置。
5. 共享跨端 fixture 的最终目录、版本字段和脱敏审查责任人。
6. REC-001、REC-005、REC-011 中哪些路径进入合并必跑端到端门禁，哪些先作为手动或夜间验证。

在这些事项未裁决前，可以先编写不会锁定产品选择的服务端事实测试，但不能把某一客户端临时行为提升为永久跨端契约。
