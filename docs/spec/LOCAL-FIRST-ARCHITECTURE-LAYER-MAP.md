# Count L0-L3 架构分层覆盖映射与缺口审计

> 状态：只读审计草案，待评审
>
> 更新：2026-09-19
>
> 审计范围：`docs/arch-design-methodology/skills/arch-design-spec/references/spec-L0-L1.md`、`spec-L2.md`、`spec-L3.md`，以及 Count 当前的系统总览、Local-First Spec、ADR、执行记录和交接快照。
>
> 本文只判断现有设计产物的层级覆盖和缺口，不批准业务实现，不改变既有同步冻结范围。

## 1. 结论摘要

当前仓库已经有较多 L0-L3 设计材料，但它们是按历史任务线和实施切片积累的，不是按一套当前架构分层组织的：

- **L0：部分存在，但缺少当前 Phase 1 的唯一权威版本。** 系统总览、Local-First 边界评估和 ADR 已覆盖本地权威、平台职责、AI 正交和同步边界，但五域、图片、导出和当前 Release Blocker 尚未在同一份 L0 中收敛。
- **L1：存在碎片，缺少主领域清单和依赖图。** 当前文档能看出平台和能力，但没有一份按主领域回答“谁管什么、为什么这样聚合、谁依赖谁”的当前设计。
- **L2：局部较完整，覆盖集中在消费 / 账户、本地生命周期、登录绑定和表达核心。** 饮食、睡眠、运动、阅读、图片输入、AI Popup Local-First、跨域 Analysis Local-First 和本地导出尚未形成同构的 L2 领域设计。
- **L3：有不少技术片段，但没有按 L2 对齐的完整技术详设集合。** GRDB/SQLite、消费记录、账户流水、Outbox、同步和 BYOK 已有局部详设；五域本地模型、图片生命周期、AI 结果与反馈持久化仍缺完整 L3。

因此，下一份架构产物应先补一份当前有效的 **L0/L1 系统全景与主领域划分**，而不是直接进入某个页面或某个 AI 模块的代码改造。

## 2. 分层覆盖映射

### 2.1 L0：系统全景与逻辑分层

| 现有证据 | 已覆盖内容 | 覆盖判断 |
|---|---|---|
| `docs/spec/00-系统总览规格说明.md` §2~§8 | 产品定位、系统范围、平台职责、核心闭环、事实 / 候选 / 表达分层、跨端不变量 | L0 主体已有 |
| `docs/spec/模块/iOS本地优先/边界评估.md` | 本地事实、云端副本、PWA 维护模式、AI Provider 和主要风险 | L0 边界补充 |
| `docs/decisions/ADR-036-本地优先数据权威与AI能力正交.md` | 本地数据权威与 AI 能力正交 | 全局决策已确认 |
| `docs/decisions/ADR-037-iOS本地业务数据库选择GRDB.md` | 本地事实库技术方向和安全边界 | L3 前置约束，不替代 L0 |
| `docs/decisions/ADR-038`、`ADR-039` | 免登录安全壳、统一页面、本地权威和可选同步 | L0/L1 过渡边界已确认 |

对照 L0/L1 规格的缺口：

- 缺少一份同时回答系统“管什么 / 不管什么 / 分几层”的当前文档；
- 当前五域范围、图片正式生命周期、本地导出、BYOK、AI Popup、Analysis 和最终真机验收尚未在 L0 统一收敛；
- 平台职责已有表格，但 iOS、PWA、Supabase、Hosted AI、BYOK 在断网 / 弱网 / AI 不可用时的隔离方式没有形成统一视图；
- 缺少从主领域归纳逻辑分层的明确依据；
- 全局约束已有散落决策，但“默认策略 + 特例处理方式”尚未按 L0 Q7 统一列出。

### 2.2 L1：主领域划分

现有材料提供了主领域候选，但没有形成当前权威 L1：

| 现有证据 | 能提供的内容 | 层级判断 |
|---|---|---|
| `docs/spec/00-系统总览规格说明.md` §4、§6 | 平台职责和核心实体 | L1 输入材料，尚非主领域设计 |
| `docs/spec/06-iOS本地优先与PWA维护模式实施计划.md` | 本地优先、迁移、同步、AI Provider 和逐域发布的路线 | 项目路线，不是 L1 领域划分 |
| `docs/spec/模块/iOS本地优先/统一页面与云端同步规格说明.md` | 本地页面、同步和账户边界 | 一个能力域的设计材料 |
| `docs/spec/模块/表达核心/` | 候选、评分、门禁、选择、渲染和反馈等表达能力 | 表达能力域的模块规格 |
| `docs/decisions/ADR-036`～`ADR-040` | 本地权威、数据库、页面、绑定和同步约束 | L1 的约束来源 |

待在正式 L1 中回答：

- 主领域到底按“本地记录事实、输入与媒体、账户与余额、AI 能力、数据生命周期、可选同步”如何划分；
- 五个记录域在 L1 是并列主领域，还是先归入一个记录事实主领域再在 L2 拆分；
- 图片和截图输入属于独立主领域还是记录事实域的子域，依据是什么；
- AI Popup 与跨域 Analysis 的事实来源、输出和反馈由谁负责；
- 主领域之间的依赖如何保持单向，反向读取如何通过快照、事件或查询模型表达；
- iOS 本地事实与云端同步副本之间属于什么关系，如何避免把同步误归为业务主领域。

### 2.3 L2：领域 / 子领域与能力说明

已有 L2 相关材料：

| 范围 | 现有材料 | 判断 |
|---|---|---|
| 本地数据生命周期 | `本地优先数据生命周期规格说明.md` | 跨域不变量较完整，但未覆盖五域对象拆分 |
| 消费 / 账户 | `消费记录垂直切片规格说明.md`、`消费记录本地优先边界评估.md`、`统一记录详情编辑删除规格说明.md` | 最接近可进入 L3 的领域材料，但部分内容已下沉到 L3 |
| 登录、绑定、同步状态 | `统一页面与云端同步规格说明.md`、`登录绑定与同步状态规格说明.md` | 能力切片较完整，属于本地事实域与同步域的交界材料 |
| AI Provider / BYOK | `AI供应方与BYOK安全契约.md` | 能力边界和安全契约清楚，仍缺与本地五域事实的完整输入输出关系 |
| 表达核心 | `docs/spec/模块/表达核心/` | 规则模块规格完整，但不等于 AI Popup Local-First 的领域 L2 |
| PWA 业务边界 | `docs/spec/模块/PWA业务边界/` | 历史维护端能力规格，不应直接作为 iOS Local-First L2 |

主要缺口：

- 饮食、睡眠、运动、阅读尚未各自形成领域边界、对象拆分、主链路和跨域依赖；
- 图片本地保存、读取、删除、导出和记录关联尚未形成统一 L2；
- 截图 / 快捷输入尚未形成从输入资产到候选再到本地正式事实的 L2；
- AI Popup 和跨域 Analysis 尚未形成“读取谁、产生什么、谁消费输出、失败如何隔离”的 Local-First L2；
- 本地导入导出、重启恢复和数据生命周期尚未作为可复用领域能力统一描述；
- 现有若干模块 Spec 混合了 L2 边界、L3 schema 和实现切片，需要在后续整理时按层归档，而不是简单复制。

### 2.4 L3：技术实现详设

已有 L3 片段：

- `LOCAL-SPIKE-001` 与 `ADR-037`：GRDB/SQLite、迁移、事务、唯一性、导入恢复和文件保护的技术依据；
- `消费记录本地优先边界评估.md`：本地 profile、账户、消费、账户流水和 Outbox 的 schema 方向；
- `统一记录详情编辑删除规格说明.md`：本地记录详情、编辑、删除、流水投影和失败出口；
- `登录绑定与同步状态规格说明.md`：workspace、绑定状态、代次、checkpoint 和冲突状态；
- `LOCAL-003D` 及远端同步执行记录：同步协议的部分技术详设，但属于冻结 / 非 Phase 1 主线材料；
- `AI供应方与BYOK安全契约.md`：Keychain、网络隔离、失败隔离和日志边界。

L3 尚未收敛的内容：

- 消费 / 账户的完整主对象、用例、表结构、接口、一致性和 NFR 仍分散在多份切片文档中；
- 五个记录域的本地对象、迁移、查询模型和删除 / 导出语义尚未完成；
- 图片实体或等价主对象的本地存储、引用、重启恢复、删除级联和导出尚未完成；
- AI 候选、表达结果、真实曝光和反馈的本地持久化边界尚未完成；
- AI Popup / Analysis 读取本地事实时的快照、失败、降级和隐私最小化路径尚未完成；
- 本地导入导出的版本、幂等、冲突和恢复技术详设尚未完成；
- 现有同步 L3 不能被当作 Phase 1 的实现前置，也不能覆盖本地事实设计。

## 3. 需要避免的层级混用

### 3.1 “L0-L5”与“L0-L3”不是同一套编号

现有项目文档中的 L0-L5 更接近**实施路线 / 阶段编号**：

- L0：本地优先架构规格与 Spike 准备；
- L1：消费记录首个本地垂直切片；
- L2-L5：迁移、同步、AI Provider 和逐域发布。

本次采用的 L0/L1/L2/L3 是**设计产物层级**：

- L0：系统边界与逻辑分层；
- L1：主领域划分；
- L2：领域 / 子域能力设计；
- L3：技术实现详设。

后续文档必须同时写清“设计层级”和“实施阶段”，不能用一个编号代替另一个编号。

### 3.2 现有文档不直接判定为废弃

已有文档仍可能承担测试场景、历史决策或实现证据。整理时采用：

- 能回答当前 L0-L3 问题的内容：登记为证据并复用；
- 只服务历史任务的内容：保留为执行记录，不上升为当前架构权威；
- 同一内容跨层混合的内容：在新文档中按层引用，不直接复制整篇；
- 与最新用户决策冲突的旧路线：标记为历史或冻结，不删除。

## 4. 目标文档结构

本审计之后建议形成以下最小结构：

| 目标产物 | 建议路径 | 当前状态 |
|---|---|---|
| L0/L1 当前架构总览 | `docs/spec/LOCAL-FIRST-L0-L1-ARCHITECTURE.md` | 待补，优先级最高 |
| L2 领域设计 | `docs/spec/模块/Local-First/` 下按领域拆分 | 待 L0/L1 收敛后补 |
| L3 技术详设 | 对应领域下按主对象 / 垂直切片拆分 | 复用现有片段，逐步收敛 |
| 实施交接与测试记录 | 现有 `docs/spec/执行记录/`、`docs/handoff/` | 保持现行体系 |

`LOCAL-FIRST-L0-L1-ARCHITECTURE.md` 应至少回答 L0/L1 规格的 Q1~Q7，并显式判断 Q8 部署与集成视图是否适用；它不应下沉到表字段、具体接口或代码实现。

## 5. 下一步

下一步不是修改业务代码，而是基于本审计补齐 `LOCAL-FIRST-L0-L1-ARCHITECTURE.md`：

1. 固化 Count 的系统边界和明确不做事项；
2. 从业务职责而不是历史任务编号聚合主领域；
3. 明确五域、图片 / 输入、AI、账户 / 余额、导出和可选同步的归属；
4. 画出单向主领域依赖，并说明反向读取的快照 / 事件 / 查询模型；
5. 把全局约束集中到 L0/L1，供下层 L2/L3 引用；
6. 通过 L0/L1 自检后，再进入具体 L2 领域设计。

本审计未对上述主领域划分做最终拍板；在 L0/L1 文档评审前，不据此开始 L2/L3 实现。
