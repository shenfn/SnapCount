> 更新：2026-09-19

## 1. 权威顺序

涉及当前产品范围、Local-First 边界或 Release Blocker 时，按以下顺序解释冲突：

1. 当前用户明确决策。
2. 根目录 `AGENTS.md`。
3. 最新的 `docs/spec/LOCAL-FIRST-PHASE1-HANDOFF.md`。
4. 当前功能对应的中文 Spec、ADR、测试策略和执行记录。
5. 本适配约束。
6. `docs/arch-design-methodology` 中的通用规格与知识。
7. 历史交接、旧原型和旧同步路线。

`docs/spec/03-阶段与任务索引.md` 中与最新 Phase 1 交接冲突的旧同步口径，不得覆盖本文件和最新交接记录。

## 2. Count 的产品架构边界

Count 当前按 Local-First Personal AI Memory 产品理解：

- 本地数据库是本设备上的正式业务事实，不是云端缓存。
- Phase 1 的正式范围包含消费、饮食、睡眠、运动、阅读五个域。
- iOS 是当前主产品；PWA 维持既有维护边界，不能反向定义 iOS 的本地事实。
- 不登录、不联网仍应能创建、查看、编辑、删除本地记录，并使用基础账户和余额能力。
- 图片是正式记录的一部分，需要本地保存、重启可恢复，并与记录删除、导出等生命周期一致。
- 截图 / 快捷输入、手动创建和编辑属于记录入口；语音输入暂不进入 Phase 1。
- 登录、BYOK、Hosted AI 和 Cloud Sync 是彼此独立的能力。登录不自动等于同步，AI Provider 不决定业务数据存储位置。
- Cloud Sync、多设备同步和云端换机恢复不属于 Phase 1 前置条件；已有同步实现冻结，不能因其存在而扩大当前主线。
- AI Popup 与跨域 Analysis 保留为两套不同能力：前者回答“刚记录后此刻最值得说什么”，后者回答“一段时间的多域数据有什么变化或关系”。

## 3. 方法论规格的使用方式

原方法论的规格层级可以复用，但必须按 Count 的业务边界解释：

| 原规格 | Count 中的用途 | 额外约束 |
|---|---|---|
| L0/L1 | 明确 Local-First 系统边界、平台职责和五域划分 | 不把云端同步或公司平台能力当作系统根边界 |
| L2 | 描述本地记录域、图片、输入、AI Popup、Analysis、账户与导出的领域边界和能力 | 不写表字段、DDL、缓存 key 或事件 schema |
| L3 | 在具体切片获准后，说明 GRDB/SQLite 数据模型、生命周期、时序、一致性、失败出口和 NFR | 不脱离对应中文 Spec，不把未来同步设计提前混入本地事实实现 |

适用的产物原则：

- 规格回答“必须说明什么”和“怎样算合格”，不强制照搬原方法论的阶段流程或输出模板。
- 设计必须区分正式事实、派生候选、模型表达、展示结果和用户反馈。
- 数值型 NFR 必须有业务输入、计算假设和验证方法；没有依据时写明未决，不拍脑袋补数字。
- 层级越界视为不合格：L2 不下沉到数据库实现，L3 不直接替代代码和测试。

## 4. 知识库启用矩阵

### 默认可按需启用

- 幂等性：用于本地写入、图片归档、导入导出和 AI 结果持久化的重复执行边界。
- 跨领域概念归属：用于五域共享概念、派生视图、业务快照和避免半闭环。
- 数据模型规则：仅在 L3 设计中参考，并以 GRDB/SQLite 和现有 ADR 为准。
- NFR 推导：仅在存在可追溯业务量和性能目标时使用。
- 占位符规则：用于记录尚未拍板的产品或技术决策。
- AD Gate：在新的跨模块架构设计开始前，用于确认关键场景、质量场景和硬约束是否齐全。

### 非默认，仅在明确出现对应需求时启用

- 多租户 / 多组织隔离：Count 当前是个人本地数据模型，不默认增加 `tenant_id`、组织共享值或跨租户查询规则。
- 全局定时任务分片：本地应用没有默认的租户批处理和集群调度模型。
- SPI / 插件能力启动校验：除非未来明确引入动态插件或可独立部署的能力提供方，否则不作为启动门禁。
- 服务端消息入口管道：不能把 HTTP、消息队列和定时任务的路由模式套到 iOS 本地命令或 SwiftUI 页面。

## 5. 明确排除的来源内容

以下内容属于原方法论仓库的来源背景或公司接入流程，Count 不执行、不继承：

- 雁游 3.0、公司项目路径、公司内网 GitLab 和公司项目模板。
- `router_rule`、`common_rules`、`thinAgent` 以及公司旧模式文件的退役或回填流程。
- `INSTALL.md` 中从公司内网获取源仓库、群发安装提示和目标项目复制安装的协议。
- 原目录 `PLAN.md`、`PROGRESS.md`、`CHANGELOG.md` 中关于方法论独立仓库阶段、公司项目回填和公司提交状态的记录。
- 租户表前缀、等保、混合部署、公司服务峰值和其他未在 Count Spec / ADR 中确认的项目约束。

原目录不删除、不重写；它们只是来源快照，不是 Count 的运行规则。

## 6. Count 项目的实现与验证门槛

涉及业务行为、数据事实、权限、图片生命周期、AI 结果或跨端契约时：

1. 先明确场景编号、冻结范围、事实来源、失败出口和测试层映射。
2. 先固定已有行为，再按红灯、最小实现、绿灯和回归顺序推进。
3. 生成式 AI 只固定事实、候选、证据和语义边界，不把某一句模型文案当成唯一正确答案。
4. 本地数据、图片、AI 结果和反馈的删除、重启、导出及重试语义必须分别说明。
5. Windows 不作为 Swift 编译通过的证据；iOS 编译和最终发布验收以 macOS CI 与真机证据为准。
6. 不执行生产迁移、生产部署、TestFlight 上传或远端清理，除非当前用户明确授权。

本适配层本身不批准任何 Release Blocker 的实现，也不改变已有同步冻结范围。

## 7. 当前下一步

适配层建立后，下一项工作是对 AI Popup / Planner 做只读依赖分析：

- 追踪本地事实、云端汇总、历史明细、画像、曝光、表达结果和反馈的真实来源；
- 区分可复用的表达核心算法与必须替换的数据读取、调用和持久化边界；
- 产出 Local-First 依赖矩阵、风险、未决问题和最小完整切片建议；
- 在方案获批准前不修改业务代码。
