# Jiezi Local-First Phase 1：第一个开发切片

> 状态：开发前收口材料
>
> 目的：把已有产品行为迁移到本地正式事实，验证一条完整 Local-First 链路后，再扩展到其他数据域。
>
> 本文不重新定义产品，不包含 Cloud Sync、多设备同步或同步协议设计。

## 1. 切片目标

完成一条从输入到本地正式记录的闭环：

```text
已有输入
→ 结构化结果 / AI 候选
→ 高置信度自动归档，或低置信度进入中转站
→ 用户确认 / 修改
→ 本地正式记录
→ Today / Records 查看
→ 编辑 / 删除
→ App 重启后恢复
```

如果输入包含图片，还必须验证：

```text
图片本地保存
→ 与记录关联
→ 重启后仍可查看
→ 删除记录时图片随之处理
→ 导出时可选择是否包含图片
```

## 2. 既有产品行为基线

以下行为已经由现有云端、PWA 和历史产品实现确认，不在本切片中重新设计：

- 五个数据域已有日常记录和查看能力；本地化不能将 Phase 1 缩减为 Expense + Account。
- AI 识别具有置信度和路由判断。
- 高置信度结果可以自动归档到对应数据域。
- 低置信度结果进入中转站，由用户确认、编辑或归档。
- 用户确认后的内容才是正式业务记录。
- 正式记录可以继续编辑和删除。
- 图片属于用户数据，应与记录保持本地生命周期。
- AI Popup / Expression Planner 是已有产品能力，需要保留。
- 跨域 AI Analysis 是已有产品能力，需要保留。

## 3. 本切片需要核对的本地缺口

本切片只处理以下差距：

- 当前本地数据库主要覆盖 Profile、Account、Expense 和账户流水，其他四域尚未形成对应的本地正式记录能力。
- 当前本地没有与中转站对应的完整本地记录状态。
- 当前本地图片主要是远端 URL 的缓存，不是正式本地附件生命周期。
- 当前通用记录创建在非 Expense 情况下仍走远端路径。
- Today、Records、Account 仍存在本地与远端混读边界。
- AI Popup 和跨域 Analysis 仍主要读取 Supabase 的记录、历史和汇总。
- 本地导出尚未覆盖五域和可选图片。

## 4. 验收场景

### 场景 A：无登录、无网络、手动记录

1. 用户打开 App。
2. 不登录、不联网。
3. 选择一个 Phase 1 数据域并手动创建记录。
4. 在 Today 和 Records 中看到该记录。
5. 修改记录并再次查看。
6. 删除记录。
7. 重启 App，确认结果保持一致。

### 场景 B：图片输入与确认

1. 用户拍照或选择图片。
2. AI 返回结构化候选和置信度。
3. 高置信度结果自动归档，低置信度结果进入中转站。
4. 用户可以确认、修改或放弃候选。
5. 确认后正式记录写入本地。
6. 图片在本地可查看，并与记录关联。

### 场景 C：记录和图片生命周期

1. App 重启后，正式记录和图片仍可查看。
2. 编辑记录不丢失图片关联。
3. 删除记录时执行既定的图片删除规则。
4. 导出时可以选择是否包含图片。

### 场景 D：AI Provider 与本地事实

1. 使用 BYOK 或 Hosted AI 完成识别 / 表达。
2. AI 只产生候选或表达结果。
3. 用户确认后的正式数据仍写入本地数据库。
4. AI Provider 改变时，本地正式记录来源不改变。

### 场景 E：既有 AI 能力的边界

1. 已确认的本地记录可以作为 AI Popup 的当前事实。
2. 本地五域记录可以作为跨域 Analysis 的事实来源。
3. 无 Cloud Sync 不应使已有本地记录消失或变成云端唯一数据。

## 5. 不属于本切片

- Cloud Sync、多设备同步、云端换机恢复。
- Outbox、Cursor、冲突协议、CRDT 和批量同步优化。
- 重新设计 AI Popup、Expression Planner 或跨域 Analysis 算法。
- 语音输入。
- 一次性完成所有五域的全部 UI 细节。

## 6. 进入开发的判断

满足以下条件即可进入第一个实现任务：

- 本文行为基线被视为当前验收基准；
- 本地事实、中转站、图片关联和 AI 候选的缺口按代码逐项登记；
- 第一个切片的具体数据域和现有入口已选定；
- 验收至少覆盖无登录、无网络、重启、编辑、删除和图片生命周期。

**当前阶段结论：产品和现状分析已收口，下一步进入第一个 Local-First 垂直切片的实现准备。**
