## 1. 总体判定

**结论：有条件通过。**

主流程、失败出口、两套待处理实体、幂等、账户影响和删除级联已经可以转化为测试，可以进入 TDD 试点。生产上线或历史数据修复前仍需处理 1 个阻断项；三次重试后的人工出口已经完成产品决策，转为首轮 TDD 必须验证的既定规则。

## 2. 通过条件与不可实施条件

### 2.1 进入 TDD 试点的条件

1. 首批测试只验证规格中已经由现行服务端契约固定的行为。
2. 把 `assigned`、`confirmed` 历史终态的只读审计列为准备项；审计前不做历史数据修复，但不阻塞不涉及历史修复的 REC-009 试点。
3. REC-009 首先验证两端达到重试上限后仍存在人工归档、修复和丢弃出口。
4. 任何账户影响、删除或跨用户场景都有数据库级验证。
5. iOS 实现通过 GitHub macOS Build 与 XCTest；不使用 Windows 结果替代 Swift 编译。

### 2.2 不可进入上线验证的情况

存在以下任一情况时，不进入生产发布或 TestFlight：

1. 历史成功类中转状态存在无目标孤儿数据，且没有审计或处置结论。
2. 任一失败态在达到重试上限后只剩禁用操作，形成用户数据死锁。
3. 支出/收入删除未验证账户流水作废，或图片清理可能删除仍被引用的原图。
4. 用户切换后仍可能展示上一用户的记录、图片或缓存。
5. 只通过页面演示，未通过服务端事务、RLS 和 iOS macOS CI。

## 5. 六角色评审意见

### 5.1 产品经理

**判定：有条件通过。**

- 两种待处理实体已经区分，避免把“待补全支出”和“中转失败”做成一个含混状态。
- 核心用户价值明确：可靠收下、能修正、不会重复入账、可以彻底删除。
- 需优先裁决历史成功态异常和低置信收入的归属，否则两端信息架构仍可能漂移。
- 首轮 TDD 应以核心闭环可靠性为目标，不把首页视觉重构或全量埋点带入范围。

### 5.2 研发工程师

**判定：有条件通过。**

- 现有原子 RPC、唯一关系、行锁和删除触发器提供了可执行基础。
- 必须用数据库 fixture 证明转收入、重复确认、账户流水作废和共享图片引用，不能只测 Repository 调用参数。
- `assigned`、`confirmed` 历史数据需先只读审计，避免直接迁移造成来源关系丢失。
- 粗略工作量：规格裁决与 fixture 设计 2 至 4 人日；服务端/PWA 首轮 TDD 5 至 9 人日；iOS XCTest 与 GitHub 验证 4 至 7 人日。此估算不含历史数据修复、完整组件测试框架引入和视觉重构。

### 5.3 测试工程师

**判定：有条件通过。**

- 15 个 REC 场景均可转为 Given/When/Then 测试，阈值、重试上限和用户隔离边界明确。
- 状态枚举已完整列出；B-01 仍需只读审计，D-01 已完成产品决策但必须由 REC-009 运行证据证明两端出口真正可用。
- 必须增加超时后幂等重试、成功写入后刷新失败、原图缺失和共享图片删除测试。
- UI 端到端只负责证明串联路径，事务和级联必须留在数据库测试层。

### 5.4 UI/UX 设计师

**判定：有条件通过。**

- 页面必须区分待补全、待分类、待确认、识别失败和结构修复，不应只显示一个模糊“异常”标签。
- 达到重试上限时，主操作应转向人工处理，不能只把唯一按钮禁用。
- 保存中、空、读取失败、写入成功但刷新失败、图片不可用和权限失效都需要独立反馈。
- 设计工作量：待处理信息架构与关键状态稿约 2 至 4 人日；不含首页整体视觉重构和完整视觉标注。

### 5.5 运营

**判定：有条件通过。**

- 自动归档率、待处理率、重试后成功率、人工归档率和丢弃率可衡量闭环质量。
- 在新增埋点前，应优先复用服务端状态和脱敏日志，避免为统计重复采集个人内容。
- 首轮不建议依据少量样本调整 `0.70`、`0.75` 和三次重试阈值；先积累脱敏分布再评估。
- 发布应按现有 CI 门禁逐步验证，不包含自动生产发布或 TestFlight。

### 5.6 法务/合规

**判定：有条件通过。**

- 用户隔离、原图所有权检查、共享引用保护和用户删除权已纳入规格。
- fixture 和日志不得包含真实令牌、完整邮箱、真实财务图片或可识别个人信息。
- 原图留存设置、异步删除状态和外部 URL 不可删除的边界应在用户可理解的隐私说明中保持一致。
- 新增行为埋点前需明确目的、字段、留存期限和退出机制；本轮不得借 TDD 名义扩大数据采集。

## 6. 角色冲突与裁决建议

| 议题 | 冲突 | 建议 |
|---|---|---|
| 历史成功态异常 | 产品希望用户无感修复；研发担心自动迁移误关联 | 先只读审计，按有无可靠 hash/目标关系分层，不直接批量猜测目标 |
| 重试上限 | 产品希望可恢复；运营可能希望模型升级后再试 | 当前保持三次硬上限，同时保留人工出口；是否按模型版本重置另立变更 |
| 新增漏斗埋点 | 运营需要衡量；合规要求最小采集 | 先用现有服务端状态聚合，确有缺口再提交字段级埋点方案 |
| 跨端 UI 一致 | 产品希望统一理解；设计希望遵循平台范式 | 统一状态含义、动作和结果，不要求组件或页面结构相同 |

## 8. 评审边界

本评审只授权继续完善规格和测试设计，不授权修改生产数据库、部署 Edge Function、改动 PWA/iOS 业务代码、上传 TestFlight 或处理真实用户数据。后续每一轮实现仍需按用户确认的范围单独开始。
