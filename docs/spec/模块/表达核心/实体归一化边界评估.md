# 表达核心实体归一化边界评估

> 任务：CLEAN-001/A2
>
> 评估对象：`tools/ai-validation/expression-planner/lib/entity-normalizer.mjs` 与 `configs/entity-aliases.public.v0.1.json`
>
> 日期：2026-08-15

## 结论

entity-normalizer 适合作为 CORE-009 独立迁移，但必须把“规则代码”和“别名配置数据”分开归属：

- `normalizeEntityText` 继续复用已经位于生产 `expression-core/index.mjs` 的实现，不创建第二份；
- `compileMerchantAliases`、`resolveMerchant`、`summarizeMerchantObservation` 迁入生产 `expression-core/entity-normalizer.mjs`；
- `entity-aliases.public.v0.1.json` 移到生产共享配置目录（建议 `supabase/functions/_shared/expression-config/`），由 Edge 调用方加载后注入 Map；
- Planner Lab 原路径改为兼容 wrapper，Lab 测试仍可使用同一份生产配置 fixture；
- 核心模块不读取 JSON、环境变量、数据库或文件系统。

只迁移 `.mjs` 而保留 Edge 对 `tools/.../configs` 的 import，会让生产仍然反向依赖实验室，不能作为完成方案。

## 边界证据

| 项目 | 只读结果 |
|---|---|
| 规则依赖 | entity-normalizer 只依赖已经生产拥有的 `normalizeEntityText` adapter；其余代码为纯函数 |
| 配置依赖 | Edge 当前直接加载 `tools/.../configs/entity-aliases.public.v0.1.json`；当前文件为空 merchants 列表，但它仍是反向依赖 |
| 规则职责 | 文本归一、配置别名编译、精确别名匹配、唯一历史工商变体合并、多实体歧义门禁和首次/别名状态 |
| 输出 | 保留 raw_name、normalized_key、entity_id、canonical_name、resolution、confidence、match_basis 与记录计数 |
| 测试 | 现有 7 项 Node 测试覆盖配置别名、空配置 fallback、唯一变体、歧义和非行政前缀反例 |
| 调用 | Edge 只在 Planner 中装配一次 alias Map；候选、统计和周期模块消费已归一化结果 |

## 已知边界与风险

1. `normalizeEntityText` 已是 CORE-001 的生产事实来源，CORE-009 不得复制或修改其归一规则。
2. 配置文件是公开业务配置，不包含凭据；迁移配置路径时必须保留 JSON 版本和字段结构，不能把配置加载逻辑塞进纯函数。
3. 唯一历史工商变体匹配和多实体歧义是实体事实边界，不得为了提高命中率放宽行政前缀或尾缀规则。
4. `summarizeMerchantObservation` 会把唯一高置信变体归入历史实体，但对多个历史实体只返回歧义，不合并统计；该行为必须由共享 fixture 固定。
5. 当前生产配置为空，不能据此删除配置契约；后续别名维护仍需要稳定的生产共享路径。

## 处置建议

建立 CORE-009 Spec 后，先新增 Node/Deno 共享 fixture 和有效红灯，再迁移规则模块、共享配置和 Edge import。迁移后生产 `tools/` 依赖预计至少减少规则文件和配置文件两条；最终数量由 CI 静态检查确认。
