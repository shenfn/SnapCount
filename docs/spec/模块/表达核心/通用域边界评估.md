# 表达核心通用域边界评估

> 任务：CLEAN-001/A2
>
> 评估对象：`tools/ai-validation/expression-planner/lib/generic-domain-candidates.mjs`
>
> 日期：2026-08-15

## 结论

`generic-domain-candidates.mjs` 具备生产共享核心的纯函数边界，但不应作为一个 575 行的领域混合文件原样迁移。它应被定义为一个**稳定兼容门面**，内部按职责拆成共享基础、收入、食品、睡眠和钱包模块：

- 门面继续公开 `prepareDomainRecords`、`generateIncomeCandidates` 和 `generateBuiltinDomainCandidates`，先保持 Planner 调用方不变；
- 共享基础模块承载数值、时间、记录读取、候选构造、证据和领域指标的公共逻辑；
- `income`、`food`、`sleep` 保留独立候选生成边界；`sport`、`reading` 继续使用通用指标路径；
- `wallet` 必须拥有独立实现和契约组，不能与普通健康/生活域共用“历史中位数”比较规则；
- `domainProfile` 只是调用方注入的纯数据，不由核心读取、计算或持久化；
- 核心模块零数据库、HTTP、文件系统、环境变量和运行时专属 API；Planner 继续拥有查询、用户过滤和编排。

因此 CORE-010 的目标是确定归属和行为边界，不在评估阶段改变候选语义。实现阶段应先建立兼容门面和共享 fixture，再按模块最小迁移。

## 边界证据

| 观察项 | 只读结果 | 结论 |
|---|---|---|
| 外部依赖 | 仅从 `expression-core-adapter.mjs` 引入 `parseFiniteNumber` | 可迁入生产核心；应改为直接依赖生产数值核心 |
| IO | 无数据库、HTTP、文件、环境变量或 Supabase 调用 | 纯函数边界成立 |
| 公共入口 | `prepareDomainRecords`、`generateIncomeCandidates`、`generateBuiltinDomainCandidates` | 作为兼容门面保留 |
| 共享基础 | `candidate`、`evidence`、数值/时间/记录读取、`domainMetric` | 抽为内部共享模块，避免各域复制 |
| 领域逻辑 | income、sleep、food、sport、reading、wallet 混在同一文件 | 不宜原样成为生产权威文件 |
| 钱包规则 | 金额来源冲突、asset/liability 类型、账户 ID/名称身份、快照时间严格先后 | 独立钱包模块和独立契约组 |
| 配置输入 | `domainProfile` 仅读取 `meal_baseline` 和 `chronotype` | 保持调用方注入，核心不拥有 profile 生成 |
| 调用方 | Edge Planner 负责 records 装配和领域路由；Lab 测试通过 wrapper 调用 | 迁移不改查询和编排 |

## 职责拆分建议

| 目标文件 | 归属 | 允许职责 | 明确不做 |
|---|---|---|---|
| `generic-domain-candidates.mjs` | 生产门面 | 兼容导出、领域路由、候选结果拼接 | 不新增领域规则，不读取外部资源 |
| `generic-domain-shared.mjs` | 生产核心内部 | 数值、时间、payload、证据、candidate 工厂和普通指标 | 不包含钱包身份比较或领域 profile 生成 |
| `income-candidates.mjs` | 生产核心 | 月度累计、来源重复模式 | 不推断工资周期或收入原因 |
| `food-candidates.mjs` | 生产核心 | 餐次上下文、菜品组成、餐次基线、重复菜品 | 不把缺失热量当作零，不越权推断健康因果 |
| `sleep-candidates.mjs` | 生产核心 | 睡眠时间、质量、阶段和 chronotype 比较 | 不改变跨日时间归属，不读取设备 API |
| `wallet-candidates.mjs` | 生产核心 | 金额来源、账户身份、资产/负债和上一快照比较 | 不推断消费、还款、转账或因果关系 |

## 已知风险

1. `prepareDomainRecords` 同时处理因果可见性和睡眠事件去重。拆分时必须把它视为共享输入预处理，不能让各领域重新实现一份“只看历史”的过滤。
2. 钱包记录可能同时存在多个金额字段；任一来源无法解析或数值冲突都必须保留当前事实但阻断变化比较。
3. 钱包比较要求同用户、同账户身份、同资产/负债类型和严格更早的快照时间；缺少两侧关联 ID 时只能使用双方均具体且完全相同的账户名回退。
4. `meal_baseline` 当前要求 `n >= 5`，但 `chronotype` 只检查典型时间能否解析、未读取 `n`；迁移必须保留这个现状，不能顺手统一或增删门槛。
5. 现有完整 Planner 测试依赖 `esbuild`；Windows 环境失败应标记为环境限制，不能改写业务断言。

## 处置建议

建立 CORE-010 Spec 和 ADR 后，先添加共享 Node/Deno fixture，至少覆盖六个领域的当前事实、历史比较、缺失字段和钱包阻断规则。实现 PR 分两层验证：

1. 纯函数模块和门面兼容测试；
2. 完整 Planner 集成回归和 Edge 静态依赖检查。

完成前不得进入 PWA、iOS 或 Edge `index.ts` 的结构拆分。
