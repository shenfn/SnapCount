## 1. 目标

将表面容量、候选排序、覆盖排除、容量限制、多样性、周期冷却和两类 fallback 选择逻辑迁移到生产拥有的纯函数目录：

```text
supabase/functions/_shared/expression-core/plan-selection.mjs
```

Planner Lab 保留原有导入路径作为兼容 wrapper，Edge 生产入口直接依赖 `_shared`。迁移只改变规则归属和依赖方向，不改变 `expression-plan-v0.1` 的结构化输出。

## 2. 场景与不变量

| 场景 | 固定不变量 | 测试层 |
|---|---|---|
| CORE-008 | 同一候选集合在相同 surface/profile 下选择顺序、容量和覆盖排除保持不变 | Node + Deno 共享 fixture |
| CORE-009 | `surface_fallback` 与 `exact_fact_fallback` 保持不同的 `selection_mode`，且 `fallback_used` 只标记后者 | Node + Deno 共享 fixture |
| CORE-010 | 多样性组和周期冷却仍阻止重复候选，排除原因可审计 | Node + Deno 共享 fixture + Planner 回归 |
| CORE-011 | 未知 surface 仍失败，不静默降级为默认 surface | Node + Deno 纯逻辑 |
| CORE-012 | Planner Lab wrapper 与生产核心输出字节等价，生产 `tools/` 依赖减少 1 条 | 边界检查 + 架构 ratchet |

## 3. 输入输出契约

### 3.1 `SURFACE_CAPACITY`

保留四个现有 surface：`shortcut_notification`、`pwa_pending_ai_card`、`record_detail`、`weekly_report`。每个 surface 的 `max_candidates`、`allow_exact_fact_fallback`、`fixed_slots` 和 `covered_semantic_keys` 必须保持现有值。

### 3.2 `buildSurfacePlan(candidates, surface, overrides)`

- 只消费候选的 `scoring.surfaces[surface]`、`claim`、`selection_hints` 和结构化字段；不重新计算候选事实、资格或分数。
- 先按分数和 tie-break 排序，再应用固定内容覆盖、surface fallback 保留、周期冷却、阈值、多样性和容量规则。
- 没有普通候选时，先尝试 `surface_fallback`，再按 profile 允许情况尝试 `exact_fact_fallback`。
- 输出保持 `surface`、`plan_version`、`fixed_slots`、`covered_semantic_keys`、`capacity`、`selected`、`fallback_used`、`silent` 和 `excluded` 字段。

### 3.3 `buildExpressionPlans` 与 `summarizePlans`

继续按 `SURFACE_CAPACITY` 的稳定键顺序构造各 surface 计划；摘要只保留容量、选择数量、候选 ID、语义键、分数、选择模式、fallback 和静默状态，不生成新事实。

## 4. 非目标

- 不迁移候选生成：事实候选、周期候选、比较候选、跨记录关系和通用域候选仍留在 Planner Lab 基线。
- 不迁移资格门、确定性评分或 render contract；它们仍由现有编排层调用。
- 不修改 Prompt、模型供应商、数据库、PWA、iOS、通知文案或生产部署配置。
- 不删除 fallback，不把两类 fallback 合并成一个布尔路径。
- 不改变候选分数、候选证据或 exposure 数据的生产来源。

## 5. 纯函数与依赖约束

- `plan-selection.mjs` 零 IO、零环境 API、零 Supabase/HTTP 依赖，不读取 `tools/` 或配置文件。
- 生产入口从 `_shared/expression-core/plan-selection.mjs` 导入；Lab 的 `expression-plan.mjs` 仅做 re-export wrapper。
- 共享 fixture 只保存合成候选和结构化预期，不保存模型文案、用户数据或真实标识。
- Node 与 Deno 对同一 fixture 输出字节等价 JSON。

## 6. 迁移顺序

1. 写共享 fixture、Node/Deno runner 和红灯；先固定迁移前 `expression-plan-v0.1` 行为。
2. 将现有纯函数实现放入 `_shared/expression-core/plan-selection.mjs`，保持函数体和输出字段最小变化。
3. 将 Planner Lab 原文件改为 wrapper，Edge 入口改为 `_shared` 导入。
4. 运行核心、兼容、Planner Lab、Edge 类型检查和架构 ratchet。
5. CI 双运行时通过后，保留独立提交和回滚点，再评估下一组规则。
