# 表达核心渲染契约边界评估

> 任务：CLEAN-001/A2
>
> 评估对象：`tools/ai-validation/expression-planner/lib/render-contract.mjs`
>
> 日期：2026-08-15

## 结论

`render-contract.mjs` 适合作为 CORE-011 整体迁移到生产共享核心。当前文件约 129 行、无外部 import、无数据库/HTTP/文件 IO，四个导出共同描述“候选如何投影到表面、如何形成曝光事件、哪些真实曝光进入新颖度历史”，职责内聚，不需要为了拆文件而拆分。

实现时还必须收敛一个跨 Edge 的重复事实：`surface-render-contract-v0.1` 目前同时硬编码在 render contract、`expression-delivery.ts` 和 `expression-shadow.ts`。生产核心应导出 `SURFACE_RENDER_CONTRACT_VERSION`，三处运行时代码引用同一常量；SQL fixture 中的历史持久化值继续保留字面量，不属于 JavaScript 规则权威。

## 边界证据

| 观察项 | 只读结果 | 结论 |
|---|---|---|
| 外部依赖 | 无 import | 可直接迁入生产核心 |
| IO | 无数据库、HTTP、文件或环境变量 | 运行时边界成立 |
| 配置 | 4 个 surface 的固定槽位、可见/展开/仅持久化字段和发送状态 | 属于生产渲染契约，不是 Lab 配置 |
| 计划投影 | `buildRenderPlans` 将 selected candidate 投影为表面渲染计划 | Edge 生产已直接调用，应归生产核心 |
| 曝光模拟 | `buildExposureEvents` 生成 preview/real 事件 | 当前只有 Lab 测试使用，迁移仅保兼容，不接入生产写入 |
| 历史编译 | `compileExposureHistory` 只接受真实、计数且生命周期有效的事件 | 规则可双运行时验证，保留原语义 |
| 版本 | 同一版本字符串在 3 个运行时文件重复 | 迁移时导出共享常量并替换重复硬编码 |
| 测试 | 4 项直接 Node 测试覆盖投影、preview 排除、真实曝光和双 key | 可转为共享 Node/Deno fixture |

## 已知边界与风险

1. `buildExposureEvents` 在未传 `occurredAt` 时使用 `new Date().toISOString()`。这是既有 Lab 兼容行为，CORE-011 不改成必传时钟；共享 fixture 必须显式传时间以保持双运行时确定性。
2. `buildExposureEvents` 和 `compileExposureHistory` 当前不被 Edge 生产调用。迁移不等于授权把它们接入 `persistPlannerExposureEvents` 或替换数据库编排。
3. 未知 surface 当前抛出 `Missing render contract for surface`，不能改成静默忽略，否则新表面会绕过字段可见性契约。
4. preview、`simulation_only`、`counts_for_novelty` 和生命周期白名单共同决定是否进入历史，不能只检查其中一个字段。
5. exposure key 与 dedupe key 不同时必须各自产生 scoped history；去重成一个 key 会改变评分的新颖度输入。
6. SQL 安全迁移 fixture 中的版本字面量是历史数据验证，不应导入 JavaScript 常量，也不应在 CORE-011 中修改。

## 处置建议

建立 CORE-011 Spec 后，先将四类行为固定为共享 Node/Deno fixture，再迁移整个模块并把 Lab 原路径改为薄 wrapper。Edge Planner 直接导入生产 `buildRenderPlans`，Delivery/Shadow 直接导入共享版本常量，架构 ratchet 的最后一条 `tools` 例外随后删除。

CORE-011 CI 全绿后，A2 的“生产不依赖 tools + expression-core 双运行时”目标才可标记完成；此前不进入 A3/A4。
