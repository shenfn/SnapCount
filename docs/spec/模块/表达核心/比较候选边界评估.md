# 表达核心比较候选边界评估

> 任务：CLEAN-001/A2
>
> 评估对象：`tools/ai-validation/expression-planner/lib/comparison-candidates.mjs`
>
> 日期：2026-08-15

## 结论

comparison 保持为一个生产模块，内部保留两个公开候选入口：

- `generateComparisonCandidates`：商户日活跃中位数与商户周同期候选。
- `generateCategoryComparisonCandidates`：分类周同期候选。

测试契约分为“商户比较”和“分类比较”两组，但本次迁移不强行拆成两个生产文件。

## 依据

1. 两个入口共享本地周起点、日期加减、金额汇总、变化方向、百分比、证据结构、候选壳和 weekly-report 路由等 12 个内部 helper。
2. 强行拆文件会复制金额/时间规则，或者把内部 helper 暴露成跨模块公共 API，均不利于单一事实源。
3. Git 历史显示商户比较、分类比较和共同 helper 持续由同一组提交共同演进，不是偶然同文件。
4. Edge 在同一规划步骤内同时消费两个入口，最终进入同一候选选择和周期摘要去重规则。
5. 现有 6 个直接测试与完整 Planner 测试已覆盖两组入口，适合用共享 Node/Deno fixture 固定迁移前行为。

## 风险控制

- 迁移只改变权威路径和导入方向，不重写统计公式或拆 helper。
- 商户比较与分类比较使用不同场景编号和 fixture 分组，任何一组失败都能独立定位。
- 后续只有出现第三个消费者或明确重复规则时，才评估抽取 `comparison-primitives`；当前不提前抽象。
- render contract、资格门和评分继续保持独立模块，不并入 comparison。

## 处置建议

CORE-007 将整个 `comparison-candidates.mjs` 机械迁入生产核心，Lab 原路径变为兼容 wrapper，Edge 直接引用生产核心。生产 `tools/` 依赖预计由 6 项降至 5 项。
