# iOS 账户补绑边界评估

> 任务：A4-IOS-007
>
> 阶段：A4 iOS 业务编排收拢
>
> 基线：`ebd1ad8`（A4-IOS-006 收口合并提交）
>
> 状态：只读评估完成；本文件不修改 iOS 业务实现

## 1. 结论

下一片选择“账户补绑动作编排”。PWA 已经建立了账户补绑的独立 Feature 和部分成功契约，iOS 仍由 `AppState` 直接持有单笔/批量循环、busy 状态、局部数组投影和三处刷新。这个边界具备明确的业务不变量，且可以复用现有 `UnboundRecordRepository` 的两个 canonical RPC，不需要修改数据库、PWA、Edge 或页面视觉。

本片不是重新实现账户推荐算法。`NativeAccountRecommendationEngine` 继续作为纯函数；Use Case 只消费已经生成的 `NativeUnboundBindingCandidate`，负责会话、并发、逐项结果、stale 和刷新失败分层。

## 2. 当前事实

| 位置 | 当前行为 | 风险 | 目标归属 |
|---|---|---|---|
| `AppState.loadUnboundRecords` | 获取月份记录并以 generation guard 写入 `unboundRecords` | 读取边界已有基础，但和绑定动作共享页面状态 | Unbound Record Read 保持现状 |
| `AppState.bindUnboundRecord` | 直接取 session、调用 Repository、移除本地记录、刷新账户/未绑定记录/dashboard | transport 成功后刷新失败仍返回 `true`；写后没有再次检查 user/generation | Account Binding Use Case |
| `AppState.batchBindUnboundRecords` | 顺序逐项调用 `bind`，只累计成功/失败计数 | 丢失逐项错误和 record identity；用户切换不能停止剩余项；部分成功与刷新失败不可区分 | Account Binding Use Case |
| `UnboundRecordRepository.bind` | 按 expense/income 调用 `save_*_with_account`，已解码 response 但丢弃 | Use Case 无法消费 canonical 绑定结果，只能猜测本地状态 | Repository 返回结构化绑定结果 |
| `NativeAccountRecommendationEngine` | 根据支付方式/默认账户生成推荐 | 纯函数边界清晰，不应随动作编排迁移 | 保持独立纯函数 |

## 3. 候选比较

| 候选 | 优点 | 主要风险 | 决定 |
|---|---|---|---|
| 账户补绑动作编排 | 有 PWA-063 对应契约；单笔/批量部分成功边界清楚；不需要新数据库契约 | 批量不是单一事务；必须定义逐项结果和停止条件 | **本片选择** |
| 收件箱丢弃/归档 | 用户入口明显，但同时涉及 staging 状态机、图片签名、正式记录和导航 | 范围比补绑宽，容易重新混入中转生命周期 | 后续独立评估 |
| 正式记录保存/删除 | AppState 代码量大，可能涉及表达计划、删除级联和缓存 | 业务风险和回归面最高，不适合作为下一窄片 | 后续独立评估 |
| 洞察/AI 生成 | 有缓存和异步结果问题 | 外部 AI 失败语义与记录域无直接共享契约 | 暂不选择 |

## 4. 范围

### 纳入

1. 建立 `AccountBindingUseCase` 或等价纯 Swift Feature，统一单笔和批量补绑入口。
2. Repository 返回至少包含原始记录 kind/id、目标账户 id 和服务端 accepted 事实的结构化结果；不得伪造完整正式记录 DTO。
3. 单笔动作支持输入校验、未认证拒绝、同命令复用、不同目标冲突、RPC 失败和 stale。
4. 批量动作逐项执行，每项返回 `accepted`、`failed` 或 `stale`；顶层明确全部成功、部分成功、全失败和会话失效。
5. accepted 先移除对应未绑定项或投影服务端结果，再进行一次写后刷新；刷新失败独立表达，不把 accepted 改成 failed。
6. 用户切换、reset 或 generation 变化后，旧结果不得更新当前账户、未绑定记录、dashboard、消息或继续启动后续项。
7. AppState 保留 `bindUnboundRecord`、`batchBindUnboundRecords` 公开入口，只做兼容投影和页面状态转换。

### 不纳入

- 不修改 `save_transaction_with_account`、`save_income_with_account`、账户流水、余额触发器、migration 或生产数据。
- 不重写 `NativeAccountRecommendationEngine`、月份过滤、未绑定读取或正式记录读取 Repository。
- 不把批量补绑包装成数据库原子批处理；每项仍是独立事务。
- 不修改 PWA、Edge、Planner、iOS 页面视觉、导航结构或 TestFlight 配置。
- 不顺手迁移收件箱归档/丢弃、待补全确认、正式记录保存/删除或 AI 洞察。

## 5. 行为契约

### 5.1 单笔

- 空记录、空账户、未认证在 transport 前 rejected。
- 同一用户、同一记录、同一目标账户的并发命令复用一个 Task；不同目标账户返回 conflict，不发送第二个 RPC。
- RPC accepted 后结果至少保留 `recordId`、`kind`、`accountId`；本地移除只针对同一记录，不按标题或金额模糊匹配。
- accepted 后刷新失败返回 `transaction=accepted` 与独立 `refresh=failed`，页面不得诱导重复补绑。
- reset、用户切换或 generation 变化返回 stale，不执行本地投影、消息更新或刷新。

### 5.2 批量

- 批量不是一个数据库事务；每个候选最多调用一次对应 RPC。
- 结果保留每个候选的 record identity、目标账户、accepted/failed/stale 和错误原因。
- 全部成功、部分成功、全失败和 stale/会话失效必须可区分；部分成功不得被压缩成一个布尔值。
- 用户切换或 reset 后停止启动剩余项；已经 accepted 的项可以保留事实，但不得把旧用户结果写入当前状态。
- 全部逐项 transport 完成后最多触发一次账户/未绑定记录/dashboard 刷新；刷新失败独立于逐项事务结果。

### 5.3 共享边界

```text
UnboundRecordsView
  -> AppState 兼容入口
      -> AccountBindingUseCase
          ├─ UnboundRecordRepositoryProtocol.bind
          └─ session/context provider
              -> save_transaction_with_account / save_income_with_account
```

Use Case 不依赖 SwiftUI、Supabase client、HTTP 或页面文案。Repository 负责参数传输、DTO 解码和稳定错误；推荐算法和月份读取不由 Use Case 接管。
