# iOS 账户读取与截图还款边界评估

> 任务：A4-IOS-005
>
> 阶段：A4 iOS 业务编排收拢
>
> 基线：`94698ce`（PR #126 合并提交）
>
> 状态：只读评估完成；本文件不修改 iOS 业务实现

## 1. 结论

下一片选择“账户读取副作用显式化”。先把 `ensure_liability_repayment_cycles` 从账户详情和截图候选的隐式读取前置步骤中分离出来，形成显式的周期准备命令；账户列表、账户详情分区和来源快照保持读取职责，`fetchDetail` 不再由调用方误认为会自动补齐账期。

截图还款候选与确认保留为下一片独立切片。它已经通过 `confirm_staging_repayment` 进入原子 RPC，但 AppState 仍同时管理 staging、账户/账期候选、收件箱导航和刷新，事务边界比本片更宽，不能和读取副作用拆分合并。

选择读取副作用作为 A4-IOS-005，不是为了先拆文件，而是为了固定一个跨端都已经识别的业务不变量：**读取 API 不隐藏写入；需要写入的周期准备必须有独立结果和失败出口。**

## 2. 当前事实

| 位置 | 当前行为 | 问题 | 目标归属 |
|---|---|---|---|
| `AppState.loadAccounts` | 调 `fetchAccounts`，本身是纯列表读取 | 读取边界清晰，可作为基线 | 账户列表读取状态 |
| `AppState.loadAccountDetail` | 负债账户先调用 `ensureRepaymentCycles`，随后调 `fetchDetail` | 打开详情会隐式写账期；ensure 失败被 `try?` 丢弃 | 显式周期准备 + 纯详情读取 |
| `AccountRepository.fetchDetail` | 并行读取流水、账期、还款记录，按 section 保留错误 | 聚合读取边界已经存在，不应顺手重写 | Account Repository 保留 |
| `AppState.loadInboxRepaymentCandidates` | ensure 周期，再读账户和开放账期，生成候选 | staging、账户、账期和候选状态混在一个加载动作 | 本片只显式化 prepare；候选 Feature 后续处理 |
| `InboxRepository.confirmStagingRepayment` | 调用 `confirm_staging_repayment` 原子 RPC | transport 已有权威，但 AppState 的 accepted/refresh/stale 未分层 | A4-IOS-006 独立截图还款切片 |
| `NativeRepaymentCandidateEngine` | 依据 staging、账户、账期生成确定性候选 | 纯函数边界可保留，不能被读取切片顺手迁移 | A4-IOS-006/跨端 fixture |

## 3. 两个候选比较

| 候选 | 优点 | 主要风险 | 范围 | 决定 |
|---|---|---|---|---|
| 账户读取副作用显式化 | 改动面小；直接修复“读接口写库”；复用已有分区错误和 generation guard；为后续候选读取提供明确前置结果 | 负债详情需要定义 prepare 与 read 的顺序和失败显示；不能把周期准备误报成详情读取失败 | Account Repository 窄协议、读取/准备 Use Case、AppState 兼容接线、专项 XCTest | **本片选择** |
| 截图还款候选与确认 | 用户价值直观；确认 RPC 已是原子事务；可复用 PWA-067 行为 | 同时涉及 staging、账户、账期、候选排序、导航、processed 状态和三处刷新；accepted/refresh/stale 尚未收拢 | 候选纯函数、Inbox/Account Repository、跨域 Feature、AppState 和页面回归 | 后续 A4-IOS-006 |

## 4. 本片范围

### 纳入

1. 明确 `ensureRepaymentCycles` 是写命令，不属于 `fetchAccounts`、`fetchDetail` 或 `fetchOpenRepaymentCycles` 的隐藏副作用。
2. 为账户详情和候选读取建立显式“周期准备”协作结果：成功、失败、未执行和 stale 可区分。
3. `fetchDetail` 继续并行读取 entries/cycles/payments，并保留 section 级错误；读取失败不得伪装成空数据。
4. 保留 `AppState.loadAccounts`、`loadAccountDetail`、`loadInboxRepaymentCandidates` 的公开入口，通过兼容投影接入新的读取编排边界。
5. 固定 user/generation/account identity：账户切换、用户切换和 reset 后的旧读取或准备结果不得写入当前状态。
6. 对负债账户详情定义顺序：周期准备结果先可观察，再进行纯详情读取；prepare 失败不得被 `try?` 静默吞掉。
7. 新增专项 XCTest、源边界检查、阶段执行记录和交接快照。

### 不纳入

- 不修改 `ensure_liability_repayment_cycles`、`account_repayment_cycles` 表、migration、触发器或生产数据。
- 不修改还款金额、最低还款、账期状态、溢缴或自动确认规则。
- 不实现截图还款候选 Feature、`confirm_staging_repayment` 编排、processed staging 目标或页面导航改造；这些进入 A4-IOS-006。
- 不把 staging、账户和账期 DTO 合并到任一 Repository；候选引擎继续保持纯函数。
- 不修改钱包快照、来源截图、PWA、Edge、Planner、视觉设计或生产配置。

## 5. 目标行为契约

### 5.1 读取与准备分离

```text
prepareRepaymentCycles(monthKey)
  -> accepted | failed | stale

fetchAccountDetail(account)
  -> section accepted/failed/unavailable + overall stale guard
```

- `ensureRepaymentCycles` 只能从显式 prepare 协作调用。
- 纯读取方法不发写 RPC；`fetchDetail` 不负责“顺手补账期”。
- prepare 失败仍允许展示已有账户和其他详情 section，但必须留下可重试的准备失败状态；不得把失败表现成“没有还款计划”。
- prepare 成功不等于详情读取成功；两者结果分别记录。

### 5.2 读取结果

| 结果 | 行为不变量 | AppState 投影 |
|---|---|---|
| `accepted` | 读取或准备完成，且身份仍有效 | 更新对应账户/账期状态 |
| `failed` | 请求失败，旧成功值不被清空 | 保留旧值并显示局部错误/重试出口 |
| `stale` | user、generation 或 account identity 已变化 | 不更新当前账户、消息或候选 |
| `partial` | entries/cycles/payments 中仅部分成功 | 成功 section 保留，失败 section 独立可见 |

### 5.3 并发

- 同一用户、同一账户、同一月份的 prepare 命令复用同一个 Task，不重复写 RPC。
- 同一 identity 的详情读取可复用；不同账户并行时，旧账户结果不得覆盖当前详情。
- reset/user switch 后，prepare、详情读取和来源快照读取全部只能返回 stale，不得更新新用户状态。
- prepare 的失败不能触发自动重试风暴；页面重试必须是显式动作。

## 6. 依赖方向

```text
AccountsView / DomainsView / InboxView
  -> AppState 兼容入口
      -> Account Read/Preparation Use Case
          ├─ AccountRepositoryProtocol.fetch*
          └─ AccountRepositoryProtocol.ensureRepaymentCycles（显式命令）
              -> SupabaseRemoteClient

Screenshot Repayment Feature（后续 A4-IOS-006）
  -> staging + account/cycle candidate snapshot
  -> confirm_staging_repayment transport
```

Use Case 不依赖 SwiftUI、HTTP、Supabase client 或页面文案。Repository 负责 transport、DTO 和结构化错误；不管理当前页面、导航、staging 数组或候选排序。

## 8. TDD 顺序与进入门禁

1. 本评估、ADR-032 和交接快照先合并。
2. 从最新 `origin/main` 建立 A4-IOS-005 红灯 worktree；先写纯读取/显式 prepare 的协议和 XCTest。
3. 红灯必须证明失败来自缺少边界，而不是 Windows 环境或 Swift 编译不可用。
4. 最小实现先固定 Repository 窄协议和结果模型，再接 AppState 兼容入口；不移动截图确认事务。
5. macOS GitHub Build/XCTest、PWA/Edge 回归、治理和架构门禁全部通过后，才进入 A4-IOS-006 截图还款评估/实现。

## 9. 当前限制

- Windows 不能编译 Swift 或运行 XCTest；本评估未执行 iOS 编译、生产查询、迁移、部署或真实账户操作。
- `ensure_liability_repayment_cycles` 的服务端幂等和权限仍以现有 migration/RPC 为事实来源，本片不重新裁决数据库语义。
- 若实现前账户周期 RPC 签名或 `NativeAccountDetail` 契约变化，必须重新核对本评估和场景映射。
