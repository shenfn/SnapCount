# iOS 中转生命周期动作编排边界评估

> 任务：A4-IOS-008
>
> 阶段：A4 iOS 业务编排收拢
>
> 基线：`09a5fefc`（A4-IOS-007 收口合并提交）
>
> 状态：只读评估完成；本文件不修改 iOS 业务实现

## 1. 结论

下一片建议收拢 iOS 中转生命周期的三个写动作：丢弃、重试、归档。当前三者都由 `AppState` 直接管理 session、全局 busy、页面导航、本地列表投影、提示文案和刷新；`InboxRepository` 只做极薄的 transport 转发，没有统一的动作结果、用户切换 stale 或写入成功后刷新失败语义。

这是一片比正式记录保存/删除和记录详情表达链更窄的边界：数据库 RPC、`ingest-receipt` 重试入口和 PWA 中转契约都已经存在，不需要新增 migration 或改变页面导航。实现时应保留 `AppState` 公开入口，由 Use Case 负责动作状态和结构化结果，AppState 只做兼容投影。

## 2. 当前事实

| 动作 | 当前实现 | 风险 | 建议归属 |
|---|---|---|---|
| 丢弃 | `AppState.discardStagingRecord` 取 session、调用 `discard`、立即移除本地项并异步刷新 | `discard` 返回 `Void`；用户切换或 reset 后旧响应仍可能改写队列/提示；刷新任务 fire-and-forget | Staging Lifecycle Use Case |
| 重试 | 调用 `ingest-receipt`，刷新 dashboard 后根据 `route` 和列表是否仍存在决定提示/导航 | `ShortcutUploadResult` 同时承载展示文本和路由；没有 accepted/failed/stale 分层；刷新失败与重试写入结果耦合 | Staging Lifecycle Use Case |
| 归档 | 校验和 payload 组装在 `NativeDataService`，RPC 返回 target reference；AppState 成功后移除本地项并异步刷新 | 返回值只有字符串；幂等重试事实未向上暴露；归档成功后本地投影/刷新失败不能独立表达 | Staging Lifecycle Use Case + Repository DTO |

现有共享门禁 `inboxActionRecordId` 会阻止同一时刻所有中转动作，而不是按记录/命令区分并发；这是兼容行为，是否细分应由红灯场景决定，不能在本片顺手扩大交互范围。

## 3. 候选比较

| 候选 | 优点 | 主要风险 | 决定 |
|---|---|---|---|
| 中转丢弃/重试/归档动作编排 | 三个动作共享同一页面状态和刷新出口；已有 PWA-028 至 PWA-046 契约可作为跨端含义参考；不需新数据库契约 | 重试是 Edge 入口，归档带完整 payload，结果模型不能简单合并为布尔值 | **建议作为 A4-IOS-008** |
| 待补全记录确认 | 涉及财务保存、账户流水、表达状态失效和异步词汇记录 | 与 PWA 财务保存及账户边界交叉，范围明显更大 | 后续独立评估 |
| 正式记录保存/删除 | 直接影响账户余额、缓存、表达计划和详情导航 | 回归面最高，删除级联与事实反馈不可在一片完成 | 后续独立评估 |
| 记录详情读取/图片签名 | 有缓存、预取、用户 generation 和表达规划器并发 | 读模型和算法反馈耦合，不能和中转写动作混做 | 后续独立评估 |

## 4. 建议范围

### 纳入

1. 建立中转生命周期动作 Use Case 或等价 Feature，统一丢弃、重试、归档的认证、busy、generation 和结果收敛。
2. Repository 保留现有 RPC/Edge 参数；将丢弃响应、归档 target reference/idempotent retry 和重试 route 映射为结构化结果，不在 iOS 复制数据库状态机或 Edge 规则。
3. 同一记录的重复命令共享或拒绝；不同记录的并发行为先由场景测试固定，不能因拆分自动改变页面交互。
4. 写入 accepted 后才允许本地移除、导航推进或成功提示；后续 dashboard/inbox 刷新失败独立表达，不重复发送写操作。
5. 用户切换、退出或 `resetUserScopedState` 使旧动作结果 stale；旧结果不得写入新会话的 dashboard、staging 列表、导航或消息，也不得启动后续刷新。
6. 保留 `discardStagingRecord`、`retryStagingRecord`、两个 `archiveStagingRecord` 公开入口，页面无需一次性重写。

### 不纳入

- 不修改 `discard_staging_record`、`archive_staging_record`、`ingest-receipt`、migration、Edge 或生产配置。
- 不收拢 `confirmPendingRecord`、`confirmStagingRepayment`、截图还款、账户补绑或财务保存。
- 不拆中转读取、图片签名、记录详情读取、表达规划器预取或 AI feedback。
- 不改变页面导航结构、批量交互设计或全局 busy 的可见文案，除非对应行为测试证明现有投影无法表达结构化结果。
- 不执行生产迁移、部署、真实数据写入或 TestFlight。

## 6. 依赖方向

```text
InboxView / ManualRecordSheet
  -> AppState 兼容入口
      -> StagingLifecycleUseCase
          └─ InboxRepositoryProtocol
              ├─ discard_staging_record
              ├─ ingest-receipt (staging_record_id)
              └─ archive_staging_record
```

- Use Case 不依赖 SwiftUI、Supabase client、HTTP 或页面文案。
- Repository 只负责 transport、DTO 解码和稳定错误映射；`NativeDataService` 不新增动作编排。
- 数据库 RPC 与 Edge 的状态、权限、清理排队、幂等和重试上限仍是服务端权威。
- AppState 负责 session 注入、公开 API 兼容、读模型刷新和旧页面状态投影。

## 8. 明确不确定项

- `discard_staging_record` 的 cleanup status 是否需要完整暴露给 iOS 页面，需在红灯前结合现有页面需求决定，不能凭字段存在就扩大 UI 契约。
- `retry` 的 `route` 只能说明当前 Edge 路由，不等于数据库最终状态；Use Case 必须保留该区别。
- 是否将全局 `inboxActionRecordId` 改为按记录/命令的并发键，需先盘点页面是否依赖全局互斥；本评估不预先改变它。
