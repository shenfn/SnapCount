## 1. 目标

把 iOS `confirmPendingRecord` 的认证、并发、结果解码、用户/代际隔离和写后刷新编排收拢到纯 Swift `PendingConfirmationUseCase`。页面公开入口保持兼容；数据库 RPC 继续作为 pending 转正式记录、账户流水、余额和幂等的唯一权威。

本片只处理待补全确认这一条写动作，不把它与中转归档、手动财务保存、正式记录编辑/删除或表达反馈合并。

## 2. 输入与依赖

Use Case 接收：

- `PendingConfirmationRepositoryProtocol`：执行 `confirm_pending_transaction_with_account`，返回结构化 accepted 事实；不依赖 `NativeDataService`、Supabase client 或页面。
- `NativePendingResolutionDraft`：由页面完成字段编辑和本地校验后传入；Use Case 不选择账户、不计算金额、不复制分类规则。
- session/context provider：提供 access token、当前 user id、generation 和 signed-in 状态。
- accepted projection callback：由 AppState 更新兼容读模型、失效表达计划和启动独立词汇副作用。
- refresh callback：在 accepted 后刷新账户和 dashboard；刷新失败不改变 transaction accepted。
- `reset()`：使进行中的旧确认结果 stale。

Repository 请求字段必须保持服务端语义：`pending_id`、`entry_type`、`amount`、商户/来源、平台、分类、支付方式、收入类型和账户 id。Repository 不发送客户端 `user_id`，不实现数据库事务。

## 3. 结果契约

```text
transaction: accepted(recordType, recordReference/DTO, idempotentRetry)
           | rejected(unauthenticated | invalidInput)
           | conflict(pendingConfirmationConflict)
           | failed(reason)
           | stale
refresh: notStarted | succeeded | failed(error)
```

- accepted 只表示服务端返回了可识别的支出或收入正式记录；空响应、未知 `record_type` 或缺少正式记录身份必须是 `failed(invalidResponse)`。
- 服务端 `idempotent_retry: true` 是 accepted 的事实属性，不得被压成普通成功或再次发送 RPC。
- accepted 后先执行 projection，再执行 refresh；refresh 失败不得重发确认、删除本地新记录或提示用户重复提交。
- stale 不执行 projection、refresh、导航、当前用户提示或词汇列表更新。

## 4. 并发与会话隔离

1. 命令身份至少包含 `userId + pendingId`；同身份同字段签名的 in-flight 调用复用一个 Task。
2. 同 pending id 的不同字段或不同 entry kind 命令返回 conflict，不发送第二次 RPC。
3. RPC 前、返回后、projection 前和 refresh 后都检查 user/generation。
4. `reset()` 清除本地 in-flight 引用并递增内部 generation；已发出的服务端请求不能取消，但旧结果只能成为 stale。
5. stale 结果不得启动后续账户/dashboard 刷新，也不得触发词汇学习或表达缓存失效。

## 6. AppState 兼容边界

保留 `confirmPendingRecord(_:preserveInboxNavigation:) async -> Bool`、页面校验、busy、消息和 `preserveInboxNavigation`。AppState 只负责把结构化结果投影为现有 UI 状态，并把 accepted 后的账户/dashboard 刷新、表达计划失效和词汇学习作为独立副作用。

移出 AppState：

- RPC 名称和 `p_*` 参数拼装；
- 同记录并发身份、Task 复用、冲突和 stale 判断；
- accepted/failed/idempotent/refresh 结果分类。

## 9. 完成定义

- A4-IOS-009A-H 均有有效 XCTest 或源边界证据。
- iOS 只调用既有 canonical RPC，不复制数据库 pending、账户流水、余额和幂等规则。
- accepted 正式记录事实、idempotent retry、refresh failure 和 stale 可观察且不诱导重复写入。
- 页面入口兼容；词汇学习和表达缓存失效不改变财务事务结果。
- macOS Build/XCTest、PWA/Edge 回归、治理和架构门禁通过；不执行生产迁移、部署、真实数据写入或 TestFlight。
