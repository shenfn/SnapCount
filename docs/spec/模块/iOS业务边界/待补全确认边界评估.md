# iOS 待补全确认动作编排边界评估

> 任务：A4-IOS-009
>
> 阶段：A4 iOS 业务编排收拢
>
> 基线：`a023885`（A4-IOS-008 收口文档合并提交）
>
> 状态：只读评估；本文件不修改 iOS 业务实现

## 1. 结论

下一片建议只收拢 iOS `confirmPendingRecord` 的待补全确认动作。当前动作由 `AppState` 直接管理表单校验、会话、全局 busy、服务端 RPC、账户/dashboard 刷新、导航、提示和消费词汇学习；`InboxRepository.confirmPending` 只返回 `Void`，丢失服务端 accepted、正式记录和幂等重试事实。

这不是普通财务保存的兼容别名，也不应并入 A4-IOS-008 中转生命周期：服务端 `confirm_pending_transaction_with_account` 负责 pending 行锁、支出原地转正式记录、收入新建并删除 pending、账户流水原子性和幂等重试。iOS 只应复用该 RPC，收拢结果解码、用户/代际隔离和写后刷新分层，不复制数据库状态机或词汇规则。

## 2. 当前事实

| 位置 | 当前行为 | 风险 | 建议归属 |
|---|---|---|---|
| `InboxView` / `NativePendingResolutionDraft` | 页面负责编辑金额、类型、商户/来源、平台、分类、支付方式、收入类型和账户，并提供本地校验 | 表单校验与动作编排没有明确边界，但不应把 UI 字段选择搬进 Use Case | 页面/兼容入口保留输入校验；Use Case 接收已校验命令 |
| `AppState.confirmPendingRecord` | 全局 `isConfirmingPendingRecord` 锁；取 session；调用 repository；成功后异步学习词汇、失效表达计划、刷新账户和 dashboard、导航和提示 | 没有 user/generation guard；旧请求可能更新新会话；刷新失败被吞掉；accepted 结果不可区分 | Pending Confirmation Use Case |
| `InboxRepository.confirmPending` | 校验金额后调用 `confirm_pending_transaction_with_account`，返回 `Void` | 丢失 `record_type`、正式记录、`idempotent_retry` 和服务端返回错误结构 | Pending Confirmation Repository DTO |
| `scheduleConfirmedExpenseVocabulary` | 财务确认 accepted 后 fire-and-forget 写三类词汇，并已有 generation guard | 词汇写入不是财务事务；不能因词汇失败把财务确认判为失败，也不能绕过当前会话 | AppState 回调或独立词汇用例；本片只保留调用边界 |
| `invalidateRecordExpressionPlanState` | 通过 `expense/<pendingId>` 失效表达计划缓存 | 这是客户端展示缓存副作用，不是服务端确认规则；应只在 accepted 且结果仍属于当前会话时执行 | AppState 兼容投影 |

## 3. 服务端权威与客户端边界

`confirm_pending_transaction_with_account` 当前签名为：

```text
(p_pending_id, p_entry_type, p_amount,
 p_merchant_or_source_name, p_platform, p_category,
 p_payment_method, p_income_category, p_account_id)
```

服务端负责：

- `auth.uid()` 认证和 pending 行锁；
- 支出复用 pending transaction id，通过 `save_transaction_with_account` 更新正式记录；
- 收入通过 `save_income_with_account` 创建正式收入，写入 `source_pending_transaction_id` 后删除 pending transaction；
- 账户绑定、流水和余额的原子更新；
- 已处理支出/收入的幂等重试结果；
- 不合法 `entry_type`、不存在记录、权限错误和已处理冲突的失败出口。

客户端不得重新实现上述状态机、余额方向、收入删除 pending 或幂等判断。Repository 只负责参数映射、响应 DTO 解码和稳定错误映射。

## 4. 候选比较

| 候选 | 优点 | 主要风险 | 决定 |
|---|---|---|---|
| 待补全确认动作编排 | 已有单一 canonical RPC；当前 AppState 直编排边界清晰；能直接验证 accepted/refresh/stale | 支出和收入响应 DTO 不同；词汇学习与表达缓存是额外副作用 | **建议作为 A4-IOS-009** |
| 正式记录保存/删除 | 可复用已有 RecordRepository，但涉及详情、账户影响、表达缓存和导航删除级联 | 回归面最高，容易把读取/反馈混进写入 | 后续独立评估 |
| 记录详情读取/图片签名 | 有明显缓存和并发问题 | 与表达规划器、签名和预取耦合，范围过宽 | 后续独立评估 |
| 表达反馈提交 | transport 边界较窄 | 依赖详情曝光身份和反馈契约，不属于财务主线 | 后续独立评估 |

## 5. 建议范围

### 纳入

1. 建立 `PendingConfirmationUseCase` 或等价 Feature，接收已通过本地校验的确认命令，统一认证、同记录命令复用/冲突、generation/reset stale 和结果收敛。
2. `InboxRepository` 将 RPC 返回映射为结构化结果，至少保留 `recordType`、正式记录引用/DTO（支出或收入）、`idempotentRetry` 和服务端错误。
3. `confirmPendingRecord` 公开入口保持不变；AppState 负责旧页面的 busy、导航、消息、表达计划失效、账户/dashboard 刷新和词汇学习兼容投影。
4. 服务端 accepted 与后续刷新分层：确认已 accepted 后，账户或 dashboard 刷新失败不能重发确认，也不能把财务确认提示为失败。
5. 用户切换、退出或 `resetUserScopedState` 后，旧确认结果不得写入新会话的账户、dashboard、导航、提示、表达缓存或词汇列表，也不得启动后续刷新。
6. 保持 expense/income 两种表单字段和服务端参数映射；不把页面的金额、分类、账户选择逻辑搬进 Repository。

### 不纳入

- 不修改 `confirm_pending_transaction_with_account`、`save_transaction_with_account`、`save_income_with_account`、migration、Edge 或生产配置。
- 不复制数据库账户流水、余额、pending 删除、状态机或幂等规则。
- 不收拢正式记录手动保存/删除、记录详情读取、图片签名、表达反馈、表达规划器预取或截图还款。
- 不把词汇学习写入提升为财务事务；词汇失败不回滚已 accepted 的财务确认。
- 不改变待补全页面字段、确认弹窗、导航结构或批量交互设计，除非行为测试证明现有兼容入口无法表达结构化结果。
- 不执行生产迁移、部署、真实数据写入或 TestFlight。

## 7. 依赖方向

```text
PendingResolutionView / InboxView
  -> AppState.confirmPendingRecord 兼容入口
      -> PendingConfirmationUseCase
          └─ PendingConfirmationRepositoryProtocol
              └─ confirm_pending_transaction_with_account

accepted projection:
  AppState -> account/dashboard refresh
           -> expression cache invalidation
           -> optional finance vocabulary side effect
```

- Use Case 不依赖 SwiftUI、Supabase client、HTTP 或页面文案。
- Repository 只负责 RPC 参数、DTO 解码和稳定错误；不刷新账户、不写词汇、不操作导航。
- 数据库 RPC 仍是财务记录、账户流水、余额和幂等的唯一权威。
- AppState 只做现有公开入口的兼容投影和独立副作用编排。

## 8. 进入实现的门禁

1. 本评估先合并并登记 A4-IOS-009；实现分支必须从合并后的最新 `origin/main` 建立。

5. Windows 运行治理、架构、专项 Node 检查；Swift/XCTest 以 GitHub macOS 为权威。
6. 未通过 stale、失败保留、accepted/refresh 分层和词汇副作用隔离前，不进入下一片。

## 9. 明确不确定项

- 当前 RPC 返回的是 `jsonb`，支出和收入的正式记录字段结构不同；实现前必须建立 fixture 或服务端契约测试，不能把 `AnyCodable` 直接当成已验证 DTO。
- `idempotent_retry` 在部分服务端分支未显式返回 false；客户端应按“字段缺省 = false”处理，不能据此推断新写入失败。
- 词汇学习已有 generation guard，但它是 fire-and-forget 的独立写入；是否在本片抽成窄 `FinanceVocabularySideEffect` 需由红灯范围决定。
- `preserveInboxNavigation` 仍是页面兼容参数；Use Case 不应拥有 NavigationPath，也不应重写页面推进策略。
