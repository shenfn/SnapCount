# iOS 账户管理原子动作编排边界评估

> 任务：A4-IOS-004
>
> 阶段：A4 iOS 业务编排收拢
>
> 基线：`f93b6fb`（A4-IOS-003 收口合并提交）
>
> 状态：评估完成；本文件不修改 iOS 业务实现

## 1. 结论

下一片选择“账户管理原子动作编排”：把 iOS 的账户创建/编辑与归档/恢复接入主线已经存在的 `save_account` 和 `set_account_archived` canonical RPC，并把 `AppState` 当前的 session、busy、写入、列表刷新、详情刷新和消息投影收拢到独立的纯业务动作编排层。

这个选择不是因为账户页面最容易拆，而是因为它是当前三个候选中唯一仍然直接绕过已建立数据库权威的写路径：

- `AccountRepository.save` 目前是 REST `insert/patch`，随后再调用 `unsetOtherDefaults`；
- `AccountRepository.setArchived` 目前只 REST patch `is_archived`，不执行 canonical 归档时的自动扣款引用清理；
- iOS 当前写入没有使用 `save_account` 的跨资产/负债类型迁移阻断，也没有使用 `set_account_archived` 的归档默认清除和未来周期引用清理；
- `supabase/migrations/20260816160000_account_management_atomic_contract.sql` 已经在基线中提供上述数据库契约，因此本片可以只做 iOS 接线，不引入新的生产数据库变更。

截图还款已经通过 `InboxRepository.confirmStagingRepayment` 调用原子 RPC，虽然其 AppState 编排仍需后续拆分，但事务 transport 已经不再是旁路。账户读取则已有 `AccountDetailSectionResult` 的分区失败模型，主要问题是读取前隐藏调用 `ensureRepaymentCycles` 的副作用，适合在本片之后独立处理。

编号说明：早期 A4-IOS-001 钱包快照规格曾使用无后缀场景号 `A4-IOS-004`。该历史证据不改名；本任务是阶段任务 A4-IOS-004，后续新增行为场景必须使用 `A4-IOS-004A`、`A4-IOS-004B` 等带字母后缀的编号，避免测试追溯歧义。

## 2. 三候选只读比较

| 候选 | 当前事实 | 主要风险 | 范围判断 | 结论 |
|---|---|---|---|---|
| 截图还款候选与确认 | `InboxRepository.confirmStagingRepayment` 已调用 `confirm_staging_repayment`；`AppState` 仍混合候选读取、账期确保、收件箱导航、账户/dashboard 刷新 | accepted 与 refresh failure 未分层；候选读取包含 staging、账户、周期三类数据 | 跨收件箱、账户和账期，需同时处理候选快照与确认命令 | 后续独立切片 |
| 账户列表/详情读取副作用拆分 | `loadAccountDetail` 在读取前调用 `ensureRepaymentCycles`；`fetchDetail` 已把流水、周期、支付分区并行读取并记录局部错误 | “读取”会写数据库；周期确保失败与详情读取失败的语义尚未分离 | 可拆，但要同时处理账期初始化、快照来源读取和详情刷新耦合 | 后续独立切片 |
| 账户管理原子动作接线 | `save` 是 REST 写入加多步默认清理；`setArchived` 是单步 REST patch；canonical `save_account`/`set_account_archived` 已存在 | 部分成功、旧客户端旁路、跨家族类型变更、归档自动扣款引用不一致 | Repository transport + 两个动作 Use Case + AppState 兼容投影，边界可控 | **本片选择** |

## 3. 当前职责盘点

| 位置 | 当前职责 | 问题 | 目标归属 |
|---|---|---|---|
| `AppState.saveAccount` | session 获取、全局 `isSavingAccount`、Repository 写入、列表替换、详情读取、结果布尔值 | 没有 generation/user stale；accepted 与刷新失败被压成 `Bool`；页面状态和业务编排耦合 | `AccountManagementActionUseCase`；AppState 保留兼容入口 |
| `AppState.setAccountArchived` | session 获取、全局 busy、归档写入、列表替换、详情读取、结果布尔值 | 归档 transport 不是事务权威；恢复/归档没有命令级并发语义 | `AccountManagementActionUseCase`；AppState 保留兼容入口 |
| `AccountRepository.save` | 校验草稿、REST insert/patch、生成初始余额、清理其他默认、重新读取列表 | 多次提交；绕过 `save_account` 的类型和自动扣款校验 | Repository 只负责 RPC transport、参数、DTO 和稳定错误映射 |
| `AccountRepository.setArchived` | REST patch `is_archived` 后重新读取列表 | 绕过归档 RPC 的默认清理和自动扣款引用清理 | Repository 只负责 `set_account_archived` |
| `AccountRepository.fetchDetail` | 并行读取流水、周期、支付并记录分区错误 | 已有较清晰读取边界，不应被账户管理片顺手重写 | 保留；本片只通过 refresh 协作调用 |
| `AccountsView` / 账户表单 | 表单校验、确认门禁、归档/恢复入口 | 需要保留现有 UI 行为，不直接承担 RPC 或 stale 语义 | 继续调用 AppState 兼容入口 |

## 4. 本片范围

### 纳入

1. `AccountRepository.save` 改为调用 `save_account`，不再在 iOS 复制默认项清理或自行写 `accounts`。
2. `AccountRepository.setArchived` 改为调用 `set_account_archived`，返回 canonical account DTO。
3. 新增纯 Swift `AccountManagementActionUseCase`，不依赖 SwiftUI、HTTP、Supabase client 或页面类型。
4. 账户保存与归档/恢复的同命令 Task 复用；同一账户不同写命令在进行中时返回结构化冲突。
5. reset/user switch 的 generation 和 user identity stale 保护；stale 结果不得写入新用户列表、详情或消息。
6. RPC accepted 后先收敛 canonical account 到账户列表和当前详情；列表/详情刷新失败单独表达，不把 accepted 改写成失败。
7. `AppState.saveAccount`、`AppState.setAccountArchived`、`isSavingAccount`、`accountMessage` 等现有公开入口和 UI 行为保持兼容。
8. 新增专项 XCTest、源边界检查、场景执行记录、阶段索引和交接快照。

### 不纳入

- 不新增或修改 `accounts` migration、RPC、trigger、index 或生产数据库数据。
- 不修改账户余额、初始余额、历史流水、账单周期或还款记录的业务规则。
- 不处理截图还款候选/确认、手动还款确认/撤销、wallet 快照或账户读取整体重构。
- 不把 `ensureRepaymentCycles` 从详情读取中拆出；该问题另立 A4-IOS-005 或后续评估。
- 不改 `AccountsView` 的视觉设计、导航结构或确认文案，只保留既有交互并接收结构化结果。
- 不修改 PWA、Edge、Planner、迁移部署、生产配置或 TestFlight。

## 5. 目标行为契约

### 5.1 保存命令

保存命令携带表单已经确认的字段：账户 id（创建时为空）、名称、账户类型、机构、尾号、初始余额（仅创建有效）、账单日、还款日、自动扣款账户、自动确认标记和默认支出/收入标记。Repository 不自行读取用户 id；RPC 使用 `auth.uid()`。

编辑时不得修改初始余额或当前余额。有历史流水、账期、还款、扣款引用的账户跨资产/负债家族变更，必须返回 `account_type_transition_blocked`；无引用账户才由 canonical RPC 判断是否允许切换。

### 5.2 归档命令

归档/恢复命令携带账户 id 和目标归档状态。归档的事实由 `set_account_archived` 返回：账户进入归档、默认标记清除、受影响的未来自动扣款引用解除；历史流水、payment、entry、余额保持不变。恢复只取消归档，不自动恢复默认或自动扣款关系。

### 5.3 结果分层

| 结果 | 行为不变量 | AppState 行为 |
|---|---|---|
| `rejected/unauthenticated` | 无有效 session 时不发 RPC | 保留表单/当前页面并提示登录失效 |
| `rejected/invalid_input` | 本地命令校验失败时不发 RPC | 保留表单，可修正后重试 |
| `conflict` | 同一账户已有不同写命令时不发第二次 RPC | 保留当前状态，显示可重试提示 |
| `failed` | RPC 未 accepted 时不收敛 canonical account | 保留页面状态，不显示成功 |
| `stale` | generation 或用户不匹配时不收敛、不刷新、不显示旧用户消息 | 静默丢弃旧结果 |
| `accepted + refresh ok` | canonical account 是已接受事实；刷新成功 | 更新列表和当前详情，关闭表单并显示成功 |
| `accepted + refresh failed` | 刷新失败不撤销 accepted，不再发第二次写 RPC | 保留 canonical account，独立提示“已保存/归档但刷新失败” |

### 5.4 并发

- 同一用户、同一账户、同一命令 identity 共享一个 Task，不产生第二次 RPC。
- 同一账户的保存与归档/恢复交叉执行返回 `account_command_conflict`。
- 创建命令使用调用期生成的 command key 防止重复点击；两个不同表单不误判为同一个命令。
- reset 或用户切换提升 generation 并清理 in-flight；旧请求即使服务端已 accepted，也不得向新用户状态投影。

## 6. 跨端对应关系

本片复用 PWA-066A 至 PWA-066F 和 ADR-027 已确定的数据库行为，不复制 PWA Store/Feature 实现：

| PWA 契约 | iOS 对应 |
|---|---|
| PWA-066B canonical `save_account` / `set_account_archived` | `AccountRepository` 独占两个 RPC transport 和 DTO 解码 |
| PWA-066C Repository 边界 | iOS 不再 REST 写 `accounts`，不再调用 `unsetOtherDefaults` |
| PWA-066D command identity、复用、冲突、stale | `AccountManagementActionUseCase` 的纯 Swift 状态机 |
| PWA-066E accepted/refresh 分层 | Use Case 返回 canonical account 和 refresh 状态，AppState 做兼容投影 |
| PWA-066F 归档/恢复出口 | iOS 保留现有已归档列表和恢复按钮，不改变页面视觉范围 |

跨端共享业务含义和错误 reason，不共享 Swift/TypeScript 编排代码。实现阶段应补充同一组 JSON 场景 fixture，至少覆盖类型阻断、归档引用清理、accepted/refresh/stale 和冲突。

## 9. 完成定义

- iOS 保存和归档/恢复只通过 `save_account`、`set_account_archived` 两个 canonical RPC；源边界检查阻止旧 REST 写路径回归。
- 同命令不重复写入；冲突、失败、stale 均有明确出口。
- canonical account accepted 后同步账户列表和当前详情；refresh failure 不掩盖 accepted，也不诱导重复提交。
- 跨资产/负债类型迁移、归档默认清除和自动扣款引用清理由数据库契约负责，iOS 不复制规则。
- 页面现有创建、编辑、归档、恢复和确认门禁保持可用；未进入视觉或导航重构。
- 专项 XCTest、完整 macOS Build、治理/架构门禁和相关回归均有证据。
- diff 未进入截图还款、账户读取副作用、数据库迁移、PWA、Edge、Planner 或生产发布。
