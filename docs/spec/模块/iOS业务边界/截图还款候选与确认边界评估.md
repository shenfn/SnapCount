## 1. 结论

iOS 现有分层方向正确：View 通过 `AppState` 进入 Use Case，Repository 负责 transport 和 DTO，数据库 RPC 负责原子事务。本片不重做这套架构，也不把 PWA 的 Store/Feature 代码搬进 Swift。

下一片只收拢截图还款的跨边界编排：

1. `NativeRepaymentCandidateEngine` 保持纯函数，只接受中转记录、账户和开放账期快照；
2. `InboxRepository.confirmStagingRepayment` 保持截图还款 RPC transport 的唯一入口；
3. 新增窄的 Screenshot Repayment Use Case/Feature State，负责命令 identity、并发冲突、用户/generation stale、accepted 后投影和独立刷新；
4. `AppState` 保留现有公开入口和 UI 兼容投影，不再自己编排所有跨域副作用。

这属于“利用已有骨架收拢职责”，不是架构推倒重来。若实现 diff 需要修改数据库、PWA、Edge、Planner 或视觉页面，应暂停并重新评估范围。

## 2. 当前事实

| 位置 | 当前职责 | 风险 | 目标归属 |
|---|---|---|---|
| `NativeRepaymentCandidateEngine` | 从 staging、账户、账期生成确定性候选 | 纯规则容易被页面或读取流程复制 | 账户域纯函数，保持零 I/O |
| `AppState.loadInboxRepaymentCandidates` | prepare、账户/账期读取、候选生成和状态投影 | 读取前置与候选状态仍在同一入口 | A4-IOS-005 已处理 prepare；本片只消费快照 |
| `AppState.confirmStagingRepayment` | 确认框、RPC、移除 staging、写 processed、账户和 dashboard 刷新 | accepted、refresh failed、stale 可能被压成 Bool/页面状态 | Screenshot Repayment Use Case + AppState 兼容投影 |
| `InboxRepository.confirmStagingRepayment` | 调 `confirm_staging_repayment` | 不应管理数组、导航或页面提示 | 保持唯一 transport |
| `confirm_staging_repayment` | staging、账期、payment、entry、余额的数据库事务 | 客户端不能复制状态或金额规则 | 数据库继续作为最终事务权威 |

## 3. 与 PWA 契约的对应

本片复用已合并的 PWA-067 业务含义，但不复制 TypeScript 实现：

| PWA-067 | iOS 对应 |
|---|---|
| PWA-067A 候选纯规则 | `NativeRepaymentCandidateEngine` 的输入、开放状态、金额/账户/日期评分和稳定排序 |
| PWA-067C Repository transport | `InboxRepository` 独占 `confirm_staging_repayment` 调用；不把 RPC 放回 View/AppState 之外的页面层 |
| PWA-067D 命令并发/stale | 新的纯 Swift Use Case/Feature State |
| PWA-067E accepted/refresh 分层 | canonical cycle 先投影，再独立执行账户/中转/dashboard refresh |
| PWA-067F/G 已处理目标和页面出口 | iOS 维持收件箱当前导航语义；若目标缺失，显示明确不可用状态，不打开可编辑的错误详情 |

跨端共享的是行为不变量和脱敏场景，不共享 Swift/TypeScript 编排代码。

## 4. 本片范围

### 纳入

1. 为截图还款确认建立结构化输入和结果：`accepted`、`failed`、`rejected`、`conflict`、`stale`，以及独立的 refresh 状态。
2. 同一用户、同一 staging、同一 cycle、同一金额和扣款账户的 in-flight 命令复用 Task；同 staging 的不同命令返回冲突，不发第二次 RPC。
3. reset 或用户切换后，旧 RPC 结果不得投影到账户、staging、导航或当前用户提示。
4. accepted 后先应用数据库返回的 canonical cycle，再移除开放 staging、记录已处理目标，最后刷新账户和 dashboard；refresh 失败不能把 accepted 改写成失败。
5. 保留 `AppState.confirmStagingRepayment(_:)` 公开入口和现有人工确认门禁，通过兼容投影接入新编排层。
6. 增加纯 Swift XCTest、Repository 源边界检查和 iOS Build 证据。

### 不纳入

- 不修改 `confirm_staging_repayment`、账期状态、金额推导、余额方向或数据库 migration。
- 不修改 PWA、Edge、Planner、wallet snapshot、账户读取 prepare 或手动还款/撤销入口。
- 不创建或关联 wallet `data_records`，不把 staging UUID 伪装成 `evidence_record_id`。
- 不新增自动确认策略，不改变 `NativeRepaymentCandidateEngine` 的业务评分口径；如需修正规则必须另立跨端契约评估。
- 不做页面视觉、导航重设计；只修正成功/失败/刷新失败的状态出口。

## 5. 目标行为契约

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| A4-IOS-006A | wallet 已还款证据、活跃负债账户和开放账期才可生成候选；无合法金额或低于阈值返回空；候选不执行 I/O | Swift 纯函数 XCTest/源边界 |
| A4-IOS-006B | 同 identity 确认只发一次 RPC；不同 cycle/金额/扣款账户返回冲突 | Use Case XCTest |
| A4-IOS-006C | 未登录或非法输入不发 RPC；RPC 失败不修改当前 staging、账户或导航 | Use Case/AppState XCTest |
| A4-IOS-006D | reset、用户切换或 generation 变化使旧结果 stale，不调用 projection、refresh 或旧用户提示 | Use Case XCTest |
| A4-IOS-006E | accepted 先收敛 canonical cycle 和 staging 状态，再刷新账户/dashboard | Use Case/AppState XCTest |
| A4-IOS-006F | accepted + refresh failed 明确表达“已确认但刷新失败”，不诱导重复确认 | AppState 回归/XCTest |
| A4-IOS-006G | 取消、冲突、失败、stale 保留当前页面和记录，用户可重试 | AppState/页面源边界 |

## 6. 依赖方向

```text
InboxView / Account views
  -> AppState 兼容入口
      -> Screenshot Repayment Use Case
          -> candidate pure function (snapshot only)
          -> InboxRepositoryProtocol.confirmStagingRepayment
              -> SupabaseRemoteClient
```

Use Case 不依赖 SwiftUI、HTTP、Supabase client 或页面文案。Repository 不删除 staging 数组、不刷新页面、不管理导航。数据库 RPC 仍是 staging、cycle、payment、entry 和余额的一致性权威。
