# iOS 表达反馈动作编排边界评估

> 模块编号：A4-IOS-010
>
> 所属计划：CLEAN-001/A4
>
> 状态：只读评估完成
>
> 基线：`12db65e`（A4-IOS-009 状态收口合并提交）

## 1. 结论

下一片建议选择“表达反馈动作编排”，而不是把正式记录详情、保存/删除或图片签名一起收拢。

当前 `RecordRepository` 已经有窄的 `submitFeedback` transport，但 `AppState.submitRecordFeedback` 仍同时承担：

- 从当前选中详情和反馈 identity 选择可提交的事实；
- 防止同一时间重复提交；
- 获取当前 session 并调用 Repository；
- 把服务端结果投影为 `idle/submitting/submitted/failed`。

这个动作不创建或修改财务记录，不写账户流水，不刷新余额，不改变中转状态，也不负责表达文案生成。它适合做一个低风险的 Use Case 试点，同时能补上当前提交请求缺少的用户/代际隔离。

## 2. 现状证据

### 2.1 生产入口

- `ios/SnapCount/Repositories/RecordRepository.swift` 的 `submitFeedback` 已负责调用 `ingest-receipt` 的 `submit_expression_feedback`。
- 请求体只包含 `record_id`、`primary_choice`、`free_text`，有可选 `exposure_event_id`；Repository 不发送客户端 `user_id`。
- `ios/SnapCount/App/AppState.swift` 的 `submitRecordFeedback` 从 `selectedRecordDetail` 读取反馈，并直接管理提交状态。
- `RecordsView` 与 `InboxView` 都直接调用 AppState 入口，因此必须保留兼容门面，不能让页面直接持有 Repository。

### 2.2 当前缺口

- AppState 只用 `recordFeedbackState == .submitting` 防重，没有命令 identity；不同记录的反馈会被全局状态互相阻塞。
- 请求开始后没有捕获并校验 `userStateGeneration` 与 `currentUserId`；用户注销、切换账户或详情切换后，旧响应仍可能把当前状态写成 `submitted` 或 `failed`。
- 没有独立的 feedback Use Case、Repository 窄协议或专项 XCTest；现有测试主要覆盖反馈 payload 和表达策略，不覆盖提交编排的 stale/失败出口。
- 反馈提交成功不需要账户、dashboard、记录详情或表达计划刷新；把这些刷新带入本片会扩大范围并引入不必要耦合。

## 3. 候选比较

| 候选 | 当前耦合 | 失败/数据风险 | 本轮结论 |
|---|---|---|---|
| 表达反馈提交 | RecordRepository transport + AppState 选中详情/会话/状态 | 主要是旧响应污染当前 UI；不影响财务事实 | **首选 A4-IOS-010** |
| 正式记录详情读取与图片签名 | 月份读取、详情缓存、表达计划加载/确认、图片 URL hydration、导航生命周期 | 容易改变缓存与表达卡片行为；需跨页面回归 | 先不做，另立只读评估 |
| 正式记录保存 | canonical finance RPC、账户流水/余额、表达状态失效、dashboard/accounts/detail 刷新 | accepted 与 refresh failure 分层、金额和账户影响风险高 | 暂缓 |
| 正式记录删除 | Edge 删除动作、数据库清理队列、账户流水 void、表达上下文清理、导航 | 服务端清理和财务副作用不可在 iOS 复制 | 暂缓，必须保持服务端权威 |

## 4. 建议的 A4-IOS-010 边界

### 4.1 Use Case 负责

- 接收已选定的 `recordId`、反馈 identity、choice、free text、可选 exposure event id；
- 在 transport 前拒绝空记录 ID、无可提交反馈或非法 choice；
- 以 `userId + generation + recordId + feedbackIdentity` 作为命令身份；
- 同一命令复用 in-flight Task，不同记录互不阻塞；
- Repository 返回后检查 session/generation；旧结果返回 `stale`，不写当前 UI；
- 将服务端失败保持为结构化 failed，不把失败伪造成 submitted；
- `reset()` 清除本地 in-flight 引用并使已发出的旧请求 stale。

### 4.2 AppState 保留

- 根据当前详情和 `feedbackIdentity` 选择 `NativeAIFeedback`；
- 将 Use Case 结果投影为现有 `NativeAIFeedbackReviewState`；
- 页面提示和兼容入口 `submitRecordFeedback(...)`；
- 用户切换/注销时调用 Use Case reset。

### 4.3 明确不做

- 不修改 `submit_expression_feedback` Edge action、数据库表或 migration；
- 不改变 choice、free text、exposure identity 的业务含义；
- 不刷新记录详情、dashboard、账户、余额、钱包或中转列表；
- 不迁移表达计划生成、曝光确认、反馈策略或 UI 卡片渲染；
- 不把正式记录保存/删除、图片签名和导航重构并入本片。

## 5. 场景与验证映射

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| A4-IOS-010A | 未认证、无选中反馈或非法输入不调用 Repository | Use Case XCTest |
| A4-IOS-010B | 同一记录同一 feedback identity 的并发提交只调用一次；不同记录互不阻塞 | Use Case XCTest |
| A4-IOS-010C | choice、free text、exposure event id 原样传入 Repository；不增加 user_id 或 RPC 参数 | Repository/源边界 |
| A4-IOS-010D | 服务端失败保持 failed，不投影 submitted，不触发任何刷新 | Use Case/AppState XCTest |
| A4-IOS-010E | 用户切换、注销或 reset 后旧结果为 stale，不修改新会话状态 | Use Case XCTest |
| A4-IOS-010F | 成功只投影 submitted；不改变记录事实、账户或表达计划缓存 | AppState/副作用边界 |
| A4-IOS-010G | `RecordsView` 与 `InboxView` 继续通过 AppState 兼容入口，页面不直接依赖 Repository | 源边界脚本 |

## 6. 进入实现的门禁

只有在本评估合并后，才建立 A4-IOS-010 模块 Spec 和红灯分支。实现顺序固定为：

1. 先为 A4-IOS-010A-G 建立 XCTest 和源边界红灯；
2. 加入 `FeedbackSubmissionUseCase` 与窄 Repository Protocol；
3. 保留 AppState 兼容投影，接入 session/generation reset；
4. 以 GitHub macOS XCTest/iOS Build、PWA/Edge、治理和架构门禁为验证基线；
5. 收口阶段索引、执行记录和交接快照后，才选择下一片正式记录边界。
