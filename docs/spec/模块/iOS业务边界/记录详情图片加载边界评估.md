# iOS 记录详情图片加载边界评估

> 模块编号：A4-IOS-011
>
> 所属计划：CLEAN-001/A4
>
> 状态：只读评估完成
>
> 基线：`e865d49`（A4-IOS-010 收口文档合并提交）

## 1. 结论

下一片建议选择“记录详情图片签名与 hydration 动作编排”，不直接收拢完整记录详情读取。

当前图片链已经具备相对清晰的边界：

- `RecordRepository.hydrateDetailImage` 只负责向 `NativeDataService` 请求签名 URL 并返回详情副本；
- `SupabaseImageURLProvider` 负责签名 URL 缓存、批量签名和过期时间；
- AppState 的 `hydrateRecordDetailImageIfNeeded` 负责触发时机、当前记录/用户/代际检查和 `recordDetailCache`/`selectedRecordDetail` 投影。

因此可以用一个纯 Swift `RecordDetailImageUseCase` 收拢认证、请求隔离、stale 和结果分类，同时保留 Repository 与图片服务的职责。完整详情读取仍应独立冻结，避免把表达计划、反馈卡片、导航和缓存策略一次性重构。

## 2. 现状证据

### 2.1 已有窄 transport

- `RecordRepositoryProtocol` 已声明 `hydrateDetailImage(_ detail: NativeRecordDetail, accessToken: String)`。
- `NativeDataService.hydrateRecordDetailImage` 只根据 `imagePath` 获取签名 URL，并设置 `imageURL` 与 `imageLoadError`；不写业务表、不改变记录事实。
- `SupabaseImageURLProvider` 使用 `receipt-images` bucket，签名有效期 3600 秒、本地缓存约 3000 秒，失败会重试一次。

### 2.2 AppState 当前编排

- `loadRecordDetail` 在详情读取后异步调用 hydration；缓存命中时也会触发 hydration。
- `hydrateRecordDetailImageIfNeeded` 通过 `Task` 启动请求，返回后检查 `userStateGeneration`、`activeRecordReference`、登录状态和 user id，再更新两个详情投影。
- 当前没有独立 Use Case，也没有图片 hydration 的专项 XCTest；已有检查分散在详情读取流程中。

### 2.3 不应吸收的耦合

- 详情读取后还会调用 `prepareRecordExpressionPlan`，涉及 planner preview、曝光 identity 和反馈卡片；不能随图片 hydration 一并迁移。
- `recordDetailCache` 同时保存业务详情和表达反馈投影；图片 Use Case 只能返回结构化结果，不能拥有缓存或表达状态。
- 图片签名失败只能影响图片显示，不能把详情读取或记录事实标记为失败。

## 3. 候选比较

| 候选 | 当前耦合 | 风险 | 本轮结论 |
|---|---|---|---|
| 详情图片签名与 hydration | RecordRepository transport + AppState 当前记录/代际投影 | 旧 URL 或旧用户污染缓存；不影响财务事实 | **首选 A4-IOS-011** |
| 完整详情读取 | 月份/详情查询、缓存、图片、表达计划、导航 | 极易改变反馈卡片和加载失败行为 | 暂缓 |
| 详情读取与表达计划一起迁移 | RecordRepository + Edge planner + 曝光确认 | 跨服务契约和副作用过宽 | 禁止合并为一片 |

## 4. 建议的 A4-IOS-011 边界

### 4.1 Use Case 负责

- 输入 `NativeRecordDetail`、记录 reference、当前 session/context；无图片路径时返回 `notNeeded`；
- 认证后调用 `RecordRepository.hydrateDetailImage`；
- 以 `userId + generation + recordReference + imagePath` 作为请求 identity，同一请求复用；
- 返回后检查用户、代际、当前 active reference；旧结果返回 `stale`；
- 结构化区分 `hydrated(detail)`、`notNeeded`、`failed(message)`、`stale`；
- `reset()` 清理 in-flight，使已发出的请求不能投影到新会话。

### 4.2 AppState 保留

- 决定何时触发 hydration（详情读取后、缓存命中后或用户点重试）；
- 将 `hydrated(detail)` 合并既有表达反馈后写入 `recordDetailCache` 和 `selectedRecordDetail`；
- 图片失败只设置 `imageLoadError`/重试入口，不覆盖 `recordDetailMessage`，不清空详情；
- 继续负责详情读取、表达计划、反馈、导航和缓存生命周期。

### 4.3 明确不做

- 不改 `fetchDetail`、`fetchMonth`、详情 DTO、数据库、Edge、Planner 或签名 URL 参数；
- 不迁移 `SupabaseImageURLProvider` 的缓存算法；
- 不刷新 dashboard、账户、余额、钱包或中转列表；
- 不在图片失败时重发详情读取，不把图片失败当作业务记录失败；
- 不处理记录编辑/删除或完整详情 Use Case。

## 5. 场景与验证映射

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| A4-IOS-011A | 无 image path 不调用 Repository，返回 notNeeded | Use Case XCTest |
| A4-IOS-011B | 同一详情同一 image path 的并发 hydration 只调用一次 | Use Case XCTest |
| A4-IOS-011C | signed URL 由 Repository/图片服务返回，Use Case 不拼 storage URL | Repository/源边界 |
| A4-IOS-011D | 签名失败返回 failed，不清空详情、不刷新财务状态 | Use Case/AppState XCTest |
| A4-IOS-011E | reset、用户切换或详情切换使旧结果 stale，不更新新详情缓存 | Use Case XCTest |
| A4-IOS-011F | 成功只更新图片字段，表达反馈和 planner 状态保留 | AppState 特征测试 |
| A4-IOS-011G | 完整详情读取与表达计划入口保持原职责，未被图片 Use Case 吸收 | 源边界脚本 |

## 6. 进入实现的门禁

本评估合并后，才建立 A4-IOS-011 Spec 和红灯分支。实现顺序固定为：评估 → Spec → 红灯 XCTest/源边界 → `RecordDetailImageUseCase` → AppState 投影 → macOS 验证 → 文档收口。
