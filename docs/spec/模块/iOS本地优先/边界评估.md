# iOS 本地优先架构边界评估

> 评估编号：LOCAL-001
>
> 状态：已完成只读评估
>
> 基线：`origin/main@dc482ac`

## 1. 当前事实

- PWA 通过 Supabase 客户端、Repository 和 Feature 访问远端业务表与 RPC。
- iOS 通过 Repository、`NativeDataService` 和上传服务访问 Supabase REST/RPC/Edge。
- iOS 本地仅有认证 Keychain、Dashboard 快照和图片缓存，尚无业务事实数据库。
- `ingest-receipt` 当前负责图片接收、Storage、AI 识别、结构化写入、账户联动、表达和日志。
- 现有系统总规和跨端契约把 Supabase 数据库/RPC 视为业务权威，把登录视为使用入口。

因此，目标不是增加缓存，而是改变数据权威、身份入口、同步和 AI 数据边界。

## 2. 目标边界

| 关注面 | 当前 | 目标 |
|---|---|---|
| 首次使用 | 注册/登录后进入 | 免登录创建本地 profile，直接使用 |
| 业务写入 | 网络成功后成为事实 | 本地事务成功即成为当前设备事实 |
| 云端 | 唯一业务权威 | 可选同步、备份和跨设备协调 |
| PWA | 主动开发的云端客户端 | 维护型云端客户端 |
| AI | 服务端托管 Key 和编排 | Disabled / Hosted / BYOK 独立能力 |
| 图片 | 默认上传与签名访问 | 默认本地；Hosted/同步时按策略发送 |

## 3. 主要风险

### 关键风险

- 账户余额和还款不能用普通 CRUD 或最后写入覆盖实现同步。
- 现有云端用户升级需要一次性本地化迁移、去重和回滚。
- “本地保存”不等于“数据永不离开设备”；AI、同步、系统备份和诊断都需要准确披露。
- PWA 与 iOS 将暂时采用不同存储拓扑，必须共享业务契约，避免规则双实现。

### 实现风险

- 本地数据库 schema、迁移失败和低存储空间需要明确失败出口。
- iOS 本地匿名 profile 与后续登录账号的绑定可能产生重复或错误归属。
- BYOK 供应商未必允许安全直连，不能在验证前承诺请求一定不经过项目服务器。

## 4. 结论

方向可行且有明确产品价值，但属于跨身份、数据、同步、AI 和商业能力的重大架构变更。应终止 A4 的继续分片惯性，先进入 L0 规格与 Spike；不得从某个页面或 Repository 开始局部改造。
