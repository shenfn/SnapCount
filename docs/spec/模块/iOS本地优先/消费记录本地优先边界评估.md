# iOS 消费记录本地优先边界评估

> 评估编号：LOCAL-002-EVAL
>
> 状态：已完成，进入首批红灯
>
> 基线：`origin/main@f84a96a`

## 1. 当前事实

当前 iOS 的消费新增、编辑和删除仍是云端优先：

```text
ManualRecordSheet / RecordsView
  -> AppState
       -> validSession()
       -> RecordRepository
            -> NativeDataService / ingest-receipt
                 -> Supabase RPC
```

- `AppState.createManualRecord` 在保存前强制获取 Supabase session，并把 `userId`、`accessToken` 交给 Repository。
- `RecordRepository.create` 直接转发 `NativeDataService.createManualRecord`。
- 消费新增使用 `save_transaction_with_account` RPC；编辑使用同一 canonical RPC；删除调用 Edge `delete_record`。
- `NativeManualRecordDraft.amount` 是 UI 解析后的 `Double`，不适合作为本地数据库金额权威。
- `NativeAccount.currentBalance` 是云端读取模型字段；本地优先账户余额必须重新由本地流水派生。
- 当前 `DashboardSnapshotStore` 只是按用户保存 JSON 读取快照，不是业务数据库，也不能承担事务或 Outbox。

## 2. 不能采用的接线方式

### 在 AppState 内判断本地或云端

禁止把现有方法改成：

```text
if localMode { localRepository.save() } else { remoteRepository.save() }
```

这会把登录、套餐、网络、数据库和刷新策略继续堆进 AppState，并形成两套保存语义。目标结构必须是 Use Case 只依赖一个 Local-First Repository；同步由 Repository 之后的独立引擎处理。

### 直接复用 NativeManualRecordDraft 作为数据库模型

该类型属于表单输入，包含 `Double` 金额、展示默认值、通用域和图片字段。数据库层必须使用稳定 UUID、整数金额和明确日期字段，不能把 UI 草稿持久化为长期 schema。

### 把 Dashboard JSON 快照升级成权威存储

快照没有行级唯一约束、migration、关系完整性和多表事务。继续扩充会复制数据库职责，且无法可靠支持 Outbox、tombstone 和重复导入。

## 3. 首批切片

首批只建立生产本地数据库基础，不接页面：

- 本地 profile；
- 一个最小账户；
- 消费记录；
- 消费对应账户流水；
- 同事务 Outbox；
- 文件重启恢复；
- 从 opening balance 和有效流水派生余额。

首批不做：

- AppState、ManualRecordSheet、登录和路由接线；
- 编辑、删除、导出导入和同步发送；
- 图片、AI、收入、通用数据域；
- 云端老用户迁移和生产发布。

## 4. 目标依赖方向

```text
Local Expense Use Case（后续切片）
  -> LocalExpenseRepositoryProtocol
       -> LocalExpenseRepository
            -> LocalDatabase（GRDB）

Sync Engine（后续阶段）
  -> 读取 LocalDatabase Outbox
  -> Supabase
```

首批 Repository 构造器不接受 Supabase client、session、access token 或网络 Provider。

## 5. 首批 schema 约束

### `local_profiles`

- `id`：稳定 UUID 主键；
- `created_at`；
- `cloud_user_id` 可空；
- `sync_enabled` 默认 false。

### `local_accounts`

- `id`：稳定 UUID 主键；
- `profile_id` 外键；
- 名称、类型、币种；
- `opening_balance_minor` 为整数；
- 不保存可被直接覆盖的 `current_balance`。

### `local_expenses`

- `id`：稳定 UUID 主键；
- `profile_id`、可空 `account_id`；
- `amount_minor` 为正整数；
- 商户、平台、分类、支付方式；
- 本地日期和可空时间；
- `local_version` 从 1 开始；
- 创建、更新时间和可空删除时间。

### `local_account_entries`

- 稳定 UUID 主键；
- 账户、方向、整数金额、来源记录；
- 首批消费方向固定为 `out`；
- 来源消费与有效流水关系必须唯一；
- 后续编辑/删除通过冲销和替代流水扩展，不直接覆盖余额。

### `local_outbox_operations`

- 单调本地序号；
- 稳定 operation UUID 和幂等键唯一；
- aggregate kind/id、operation kind、aggregate version；
- pending/processing/failed/sent 状态与重试字段；
- 首批只写 pending，不发送网络。

## 6. 首批测试映射

| 场景 | 红灯 | 预期实现 |
|---|---|---|
| LOCAL-002A1 | 无 session、token、remote client 时无法创建本地 profile/账户/消费 | 纯本地 Repository API |

## 7. 风险

- 现有 UI 和远端 DTO 普遍使用 `Double`，Local Domain 需要明确转换边界和舍入规则。
- 上海本地日期与 UTC 时间不能互相替代，数据库必须同时保留用户日期语义和可选精确时间。
- 最小账户若自动创建，会影响产品交互；首批测试先显式创建账户，不提前决定自动默认账户。
- 首批只证明本地事实基础，不代表免登录 UI 已可发布。
