# iOS 消费记录本地优先垂直切片规格说明

> 规格编号：LOCAL-002
>
> 状态：LOCAL-002-DB2 编辑删除红灯进行中

## 1. 目标

用消费记录验证完整 Local-First 生命周期，而不是先迁移所有数据域。首片必须证明免登录、本地事务、重启恢复、导出导入和网络闸门可用。

## 2. 范围

包括：

- 本地 profile；
- 消费记录的新增、读取、编辑和删除；
- 一个支持消费归属的最小本地账户；
- 本地事务和 outbox 数据结构；
- JSON 版本化导出与导入；
- 本地/待同步状态展示；
- 后续云同步接线所需的稳定 ID。

不包括：

- 图片识别、Hosted AI 和 BYOK；
- 收入及其他生活数据域；
- 多设备自动冲突合并；
- PWA 本地数据库；
- 生产数据迁移和发布。

## 4. 依赖方向

```text
SwiftUI View
  -> AppState
  -> Expense Use Case
  -> Expense Repository Protocol
  -> Local Repository
  -> Local Database
```

Supabase、HTTP、Keychain 和具体数据库框架不得进入 Domain Model。Sync Engine 不由页面直接调用。

## 5. 红灯顺序

1. 本地数据库重启后不能恢复记录。
2. 业务写入成功但 outbox 缺失或反之。
3. 重复导入产生第二条记录。
4. 本地模式仍触发 Supabase 业务请求。
5. 消费记录通过直接余额覆盖而不是可审计流水影响账户。

## 5.2 LOCAL-002-DB2 编辑与删除语义

| 场景 | Given / When / Then | 行为不变量 |
|---|---|---|
| LOCAL-002C1 | 已存在版本 1 的消费；编辑非金额字段；返回版本 2 | 业务记录与 `upsert` Outbox 同事务提交，原有效流水不变 |
| LOCAL-002C2 | 已存在消费；编辑金额；提交成功 | 旧流水保留并写 `voided_at`，新增替代流水，余额只由有效流水派生 |
| LOCAL-002C3 | 已存在消费；改绑同一 profile 的另一账户；提交成功 | 旧账户余额恢复，新账户扣减；不直接覆盖任何账户余额 |
| LOCAL-002C4 | 客户端携带陈旧 `expectedVersion` 编辑 | 明确返回版本冲突，不覆盖较新记录，不新增流水或 Outbox |
| LOCAL-002D1 | 已存在消费；执行删除；提交成功 | 业务行写 `deleted_at` 和版本递增，默认查询不可见，有效流水被冲销，写 `delete` Outbox |
| LOCAL-002D2 | 编辑或删除复用已存在的 operation UUID | Outbox 唯一约束失败时，业务记录、流水、tombstone 和版本整体回滚 |
| LOCAL-002B2 | 完成金额编辑或删除后释放数据库对象并重开文件 | 新版本、流水历史、派生余额和 tombstone 保持一致 |

DB2 采用以下确定语义：

- `local_expenses.deleted_at` 即本地删除 tombstone，不额外建立第二张删除事实表；同步引擎后续从 tombstone 和 `delete` Outbox 读取删除事实。
- 编辑和删除命令必须携带 `expectedVersion`。只允许命中当前有效版本，成功后 `local_version + 1`；陈旧版本返回显式冲突。
- 金额或账户变化时，原流水只允许冲销，不允许原地改金额、账户或删除；替代流水继续以同一消费稳定 UUID 作为来源。
- 仅商户、分类、平台、支付方式、日期、时间或备注变化时，不制造无意义的替代流水。
- 已删除记录默认读取和计数均不可见；专用 tombstone 读取只服务后续同步、导出和恢复验证。
- 重复 command 不采用静默覆盖。重复 operation UUID 由 Outbox 唯一约束拒绝并触发整笔事务回滚；重复业务命令由版本检查拒绝。
- DB2 仍不发送 Outbox，不接 AppState、页面、登录、远端 Repository 或 Supabase。
