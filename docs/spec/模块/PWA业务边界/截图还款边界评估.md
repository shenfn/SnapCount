# PWA 截图还款边界评估

> 任务：CLEAN-001/A3、PWA-067
>
> 基线：`b2e5644`（PWA 账户管理实现收口 PR #103 合并提交）
>
> 状态：只读评估完成，待文档 PR 验证

## 1. 结论

PWA-067 不能只把 `confirm_staging_repayment` 从 `useStore` 移进 Repository。当前链路同时存在候选规则重复、客户端强制账单状态、截图还款目标类型缺失、会话 stale 和 accepted/refresh 混合等问题；只迁 transport 会把错误语义固化到新边界。

下一实现片应保留现有人工确认产品入口，但按三层收拢：

1. 纯候选规则负责从中转记录、活跃负债账户和开放账期生成确定性建议，不执行 I/O，也不自动确认。
2. Account Repository 独占 `confirm_staging_repayment` transport，并复用已有 canonical repayment cycle DTO。
3. 独立 Screenshot Repayment Feature 负责命令并发、用户/generation stale、跨中转与账户状态收敛，以及 accepted/refresh 分层。

数据库仍是最终事务权威：锁定中转记录和账期、更新 payment/entry/balance/cycle、归档 staging、写入显式 `repayment_cycle` 目标类型必须在同一事务完成。PWA-068 wallet 快照创建、关联和余额校准继续独立冻结。

## 2. 当前调用链与目标归属

| 职责 | 当前实现 | 当前问题 | 目标归属 |
|---|---|---|---|
| 加载账户与账期 | `useStore.loadData` 调 Account Repository | 读取边界已存在，可复用 | Account Repository + Store 加载编排 |
| 候选生成 | `useStore.buildRepaymentCandidateForStaging` | 与 iOS 重复且行为已漂移；无 PWA 测试 | 账户域纯候选函数 |
| 确认 transport | `useStore` 直接 `sb.rpc` | 绕过 Repository，返回 cycle 被忽略 | Account Repository |
| 写命令编排 | `runLockedAction` | reset 不使请求 stale；只有页面锁，无结构化结果 | Screenshot Repayment Feature |
| 事务权威 | migration `071_confirm_staging_repayment.sql` | 无 PostgreSQL 行为 fixture；仍信任客户端 `p_status` | 新增幂等 migration + PostgreSQL fixture |
| 已处理目标 | staging 写 `target_record_id=cycle.id` | `target_kind` 只允许三种正式记录，历史按钮进入未知目标 | `repayment_cycle` 显式目标 + 页面出口 |
| 页面反馈 | `PagePending` + Store flash | accepted 与刷新失败混合，候选原因不可验证 | Store/Page 兼容接线 |

## 3. 只读发现

### B-26：PWA 与 iOS 候选规则已经漂移

两端都有近似相同的基准分、账户名、金额和日期评分，但 PWA 会把归档账户作为候选，iOS 会排除归档账户；PWA 使用的文本字段和日期入口也与 iOS 不完全相同。当前 PWA 没有候选规则测试，iOS 只有一个成功样例，无法证明拒绝、歧义和稳定排序。

首片应固定 PWA 的确定性输入/输出和拒绝边界，并使用 PWA-067 场景编号记录跨端含义。A3 不修改 Swift；A4 再让 iOS 读取或镜像同一组脱敏 fixture，不能继续以“MatchesPWA”测试名代替真实对账。

### B-27：客户端可以把部分金额强制写成“已还清”

PWA 与 iOS 都向 `confirm_staging_repayment` 传 `p_status='paid'`。RPC 又把该值传给 `set_repayment_cycle_paid_amount`；后者在金额小于账单时仍会把 `remaining_amount` 强制清零。候选只要账户名匹配即可越过当前显示阈值，因此金额明显不一致也可能被用户确认成已还清。

截图确认 RPC 必须保留旧签名兼容现有客户端，但不再把调用方的 `p_status` 当成权威。账单状态由已验证金额、账单剩余和最低还款规则推导；没有金额时，候选可显式回退为当前剩余金额。部分金额必须得到 `partial_paid` 或 `minimum_paid`，不得静默归零。

### B-28：截图还款没有可表达的已处理目标类型

RPC 将 archived staging 的 `target_record_id` 指向 `account_repayment_cycles.id`，但 `staging_records.target_kind` 及 PWA mapper 只允许 `expense/income/data`。因此已处理列表仍显示“查看并编辑”，点击后却只能得到“归档目标类型未知”。

实现片必须把 `repayment_cycle` 加入数据库 check、保守回填既有 `resolved_action='liability_repayment_confirmed'` 行，并在成功事务中写 `target_kind='repayment_cycle'`、`resolved_domain_key='wallet'`。PWA 已处理列表要么打开对应账户/账期，要么在目标缺失时提供明确失败出口，不得显示必然失败的按钮。

### B-29：写命令没有会话 stale 与 accepted/refresh 分层

`runLockedAction` 只锁当前页面 key。`resetUserData` 清空动态锁后，旧 RPC 仍可返回并删除新会话的中转数组、刷新账户和显示旧成功提示。RPC 已提交后若账户刷新失败，当前实现仍统一返回 `true`，页面无法区分“写入失败”和“写入成功但刷新失败”。

独立 Feature 必须复用项目已有的 generation 模式：相同命令共享 Promise，冲突命令不发第二次 transport，reset/用户切换使旧结果 stale；accepted 先收敛 canonical cycle 和 staging 状态，再独立执行刷新，刷新失败不得诱导重复确认。

### B-30：数据库原子性只有实现，没有可执行契约

Release Validation 的还款 fixture 只覆盖手动 `set_repayment_cycle_paid_amount` / `revoke_liability_payment`；安全 fixture 只证明 `confirm_staging_repayment` 的 anon 权限，没有执行真实函数。跨用户拒绝、同一 staging 幂等重试、不同账期冲突、payment/entry/balance/source、staging 归档和目标类型均未被 PostgreSQL 证明。

实现必须新增独立 fixture，并在 PostgreSQL 17 中连续执行目标 migration 两次。Node mock 或静态正则不能替代该事务证据。

### B-31：候选与确认的职责边界不清

候选依赖 staging 输入，也依赖账户和账期，但它不是 Staging Repository 的读取映射职责；确认 RPC 返回 canonical repayment cycle，也不应在 Staging Repository 中复制 Account Repository 的 cycle DTO。将全部逻辑塞入任一 Repository 都会制造反向依赖或第二份映射。

候选保持纯函数；确认 transport 归 Account Repository；Feature 通过 hooks 显式协调 `repaymentCycles`、`stagingRecords`、`processedStagingRecords` 和刷新。这是跨边界命令，不是把两个 Repository 合并。

### B-32：截图证据不能伪造为 `evidence_record_id`

cycle/payment 的 `evidence_record_id` 外键指向 `data_records`，当前待确认截图仍是 `staging_records`。PWA-067 不应把 staging UUID 写入该外键，也不应为补一个字段顺手进入 PWA-068 的 wallet snapshot 创建流程。

首片以 archived staging 到 `repayment_cycle` 的显式反向目标保留证据关系；将截图提升为正式 wallet data record、再写 `evidence_record_id` 属于 PWA-068 的原子关联设计。

## 4. 目标依赖方向

```text
PagePending / useStore
  ├─ 人工确认、页面 busy、提示和数组写入
  ├─ 账户域纯候选函数（零 I/O）
  └─ Screenshot Repayment Feature
       ├─ staging/cycle command identity、并发与 stale
       ├─ accepted 后跨状态收敛与 refresh 分层
       └─ Account Repository
            └─ confirm_staging_repayment transport + canonical cycle DTO

数据库 RPC
  └─ staging + cycle + payment + entries + balances 原子权威
```

Staging Repository 继续拥有中转通用读取、重试、归档和丢弃，不复制账户账期 DTO；Account Repository 不读取或改写 Vue 数组；Feature 不依赖 Vue、Supabase 或页面文案。

- 不创建/关联 wallet `data_records`，不修复 snapshot balance，不写 `evidence_record_id`，不进入 PWA-068。
- 不新增自动确认策略；现有 `auto_confirm_repayment` 的产品启用另开场景。
- 不重写手动还款 Feature，不改变撤销还款入口，不审计无消费者流水 helper。
- 不执行生产查询、migration、部署、真实数据写入或 TestFlight。
