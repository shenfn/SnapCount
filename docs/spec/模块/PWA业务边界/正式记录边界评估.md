# PWA 正式记录边界评估

> 任务：CLEAN-001/A3、PWA-051
>
> 基线：`74628a3`（PWA-047 至 PWA-050 PR #81 合并提交）
>
> 状态：只读评估完成，待文档 PR 门禁

## 1. 结论

正式记录不能收拢成一个同时负责交易、收入、通用域、账户和删除的“大 Repository”。当前代码实际包含四条不同的权威链：

1. 正式记录读取：`transactions`、`income_records`、`data_records` 的查询参数和 DTO 映射仍在 `useStore`。
2. 财务记录保存：`save_transaction_with_account` 和 `save_income_with_account` 已是记录与账户流水的数据库原子权威。
3. 通用域与钱包快照：普通 `data_records` 保存仍是客户端直写；wallet 快照还会联动 `accounts`、账户流水和还款周期，不能并入普通记录 transport。
4. 删除：三类正式记录统一经过 `ingest-receipt` 的 `delete_record` 动作，服务端负责账户流水失效、表达清理和图片清理排队。

下一实现切片应先收拢正式记录读取 transport 和 DTO 映射，保留 `loadData` 的并发编排、current user/run guard、页面数组和派生读模型。保存、删除、账户、钱包快照和中转归档继续冻结，分别在后续评估。

## 2. 已核对证据

| 位置 | 当前行为 | 边界判断 |
|---|---|---|
| `useStore.loadData` | 直接查询月度支出、待补全支出、月度收入、最近收入、通用记录和账户 | 正式记录查询与 DTO 映射可下沉；账户查询不应并入 Record Repository |
| `mapTransaction` / `mapIncomeRow` / `mapDataRecordRow` | 数据库列到 PWA 读模型的映射留在 Store | 映射应随对应 Repository 迁移，避免创建/读取分别维护 DTO |
| `loadUnboundRecords` | 再次直接查询未绑定支出和收入，并重复月份、排序和映射规则 | 属于财务记录读取候选，但账户推荐和绑定仍属于账户边界 |
| `openProcessedStagingRecord` | 本地未命中时并行探测三张正式表 | 缺少显式目标类型；应由正式记录读取边界按类型读取，不应继续扩大并行探测 |
| `confirmExpense` / `confirmIncome` | 直接调用两个保存 RPC，成功后刷新账户并更新本地数组 | RPC 是财务事务权威；后续可加 transport wrapper，但不得退回客户端分步写入 |
| `confirmUniversalRecord` | 中转来源调用原子归档 RPC；手动创建/编辑直写 `data_records` | 两条路径语义不同；中转归档继续归 Staging，普通通用记录另行评估 |
| wallet 快照关联 | 直接读写 `accounts`、`account_entries`、`data_records` 并刷新还款周期 | 跨表且影响余额，必须归账户/钱包用例，不能作为通用记录 CRUD 顺手迁移 |
| `confirmDelete` | 三类记录都调用 Edge `delete_record`，再收敛本地状态 | 删除是独立服务端用例；不与读取切片混做 |

## 3. 关键风险

### B-04：读取规则和 DTO 多处重复

`loadData`、`loadUnboundRecords` 和 `openProcessedStagingRecord` 分别直接查询正式表。月份过滤、排序、上限、错误处理和映射散落，后续任一字段或时间口径变化都可能只修一处。

### B-05：已处理中转目标缺少显式类型

已处理列表 DTO 只保留 `targetRecordId`，没有把数据库返回的目标引用或已确认类型固化为读取参数。页面本地未命中后会同时探测三张表。下一读取边界应要求调用者提供 `expense`、`income` 或 `data` 类型；无法确定类型时返回结构化失败，不靠查询顺序猜测。

### B-06：读取失败语义不一致

支出查询失败会中断整次 `loadData`；收入、通用域和账户失败则被降级为空数组并继续。Repository 不能擅自统一成“失败即空数组”，否则会把数据缺失伪装成真实空态。Store 仍需决定哪些失败阻断主页面、哪些允许局部降级。

### B-07：保存与账户影响被错误抽象的风险

财务保存 RPC 已同时维护正式记录、账户绑定和账户流水。如果为了“统一 Repository”把它拆回多个客户端调用，会重新引入余额半状态。Repository 只能包装权威 RPC，不拥有余额计算或流水补偿规则。

### B-08：通用记录和钱包快照不是同一写边界

普通运动、睡眠、饮食等记录是单表保存；wallet 记录可能创建或更新账户、采用期初余额、生成还款周期并回写关联字段。两者共用 `data_records` 表不代表它们属于同一个用例。

## 4. 候选实施顺序

### 第一片：正式记录读取

建议使用 PWA-052 至 PWA-056：

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| PWA-052 | 月度支出与待补全支出的过滤、排序和 DTO 映射由 Record Repository 唯一持有 | Repository 行为 |
| PWA-053 | 月度收入与最近收入的查询、限制和 DTO 映射由 Repository 唯一持有 | Repository 行为 |
| PWA-054 | 月度通用记录按上海时间边界查询，`occurred_at` 缺失时保留 `created_at` 兜底 | Repository 行为 |
| PWA-055 | 未绑定财务记录复用同一 DTO 和月份规则，不复制账户推荐、绑定或余额逻辑 | Repository/源契约 |
| PWA-056 | 已处理中转目标按显式记录类型读取；未知类型不并行探测三张表 | Repository/Store 行为 |

`useStore` 继续负责 Promise 并发、current user/run guard、局部降级策略、数组写入、`transportRecords`、`unboundRecords` 和页面提示。账户列表读取暂留原位，避免把账户与正式记录绑定成一个 Repository。

### 第二片：财务保存 transport

- 为两个权威保存 RPC 建立 Record Repository wrapper 和 Feature 结果结构。
- 固定重复点击、用户切换、写成功后刷新失败和本地读模型收敛。
- 不修改数据库 RPC，不在客户端复制流水写入或余额计算。

### 第三片：通用域保存

- 只处理普通 `data_records` 手动创建与编辑。
- 中转来源继续调用 Staging 原子归档，不迁入 Record Repository。
- wallet 域另开账户/钱包 Spec，先证明跨表原子性再改实现。

### 第四片：统一删除 transport

- 包装现有 Edge `delete_record`，固定认证、accepted/failed/stale 和刷新失败语义。
- 删除后的账户刷新和本地数组收敛仍由 Feature/Store 编排。

## 5. 非目标

- 本评估不修改业务代码、数据库迁移、Edge、iOS 或生产配置。
- 不把 `accounts`、还款周期、图片签名、表达缓存失效或钱包快照塞入 Record Repository。
- 不替换 `save_transaction_with_account`、`save_income_with_account`、`archive_staging_record` 或 `delete_record` 权威入口。
- 不把 `loadData` 一次性删除或拆成多个互相写状态的 Store。
- 不执行生产查询、真实数据修复、迁移或部署。

## 6. 进入实现的门禁

1. 先建立 PWA-052 至 PWA-056 的中文 Spec 和 Repository/Store 特征测试。
2. 红灯必须证明查询参数、DTO 或显式目标类型仍在 Store，而不是环境或 mock 错误。
3. 第一片只允许新增正式记录读取 Repository、测试和 `loadData`/未绑定/已处理目标的兼容接线。
4. 图片签名、账户、保存、删除和钱包快照出现任何必要改动时暂停并重新评估范围。
5. 本地专项、PWA build、治理、安全和架构检查通过后再创建实现 PR。
