# PWA 中转生命周期边界评估

> 任务：CLEAN-001/A3、PWA-026
>
> 基线：`39f4af8`（PWA-018 PR #70 合并提交）
>
> 状态：只读评估完成；下一片候选为 REC-009 重试上限与人工出口

## 1. 结论

中转生命周期适合继续按 `useStore` 兼容门面渐进收拢，但不应把“中转读取、重试、归档、丢弃、还款截图和待补全账单”一次性抽成一个大服务。下一片只锁定 REC-009：达到三次 AI 重试上限后，PWA 仍必须保留人工归档、人工修复和丢弃出口；第四次重试由服务端拒绝，记录不能从队列消失。

当前评估发现一个不能顺手修复的高风险差异：PWA 的 `archiveStagingRecord` 先写正式记录/账户 RPC，再直接更新 `staging_records`，与记录生命周期规格声明的原子 `archive_staging_record` 入口不一致。它可能在第二步失败时留下“正式目标已创建但中转仍未归档”的半状态，必须另开数据库/生命周期契约任务，不混入 REC-009。

## 3. 当前证据

| 位置 | 现状 | 判断 |
|---|---|---|
| `useStore.loadData` | 直接读取开放 `staging_records`，并另行读取 `archived/discarded` | 读取、映射、图片签名和已处理列表仍混在 Store |

## 4. 风险与差异

### B-02：归档跨表非原子（阻断完整生命周期收拢）

记录生命周期规格要求 `archive_staging_record` 负责锁定、去重、写正式目标、更新中转状态并返回统一引用；当前 PWA 的实现是多步客户端编排。REC-009 不修复该问题，但任何“中转生命周期完成”或生产发布前必须先建立服务端事实测试和恢复策略。

### M-06：重试上限的人工出口未由 PWA 行为固定

规格要求 `retry_count >= 3` 时隐藏可点击重试，并保留人工归档、修复和丢弃。当前裁决台的重试入口由页面统一展示，是否按上限禁用/隐藏需要以行为测试固定，不能只依赖 Edge 第四次返回错误。

### M-07：动作结果和本地队列收敛不统一

重试、归档、丢弃和还款确认各自直接修改本地数组、提示消息和页面导航；写入成功但刷新失败时，页面没有统一的“业务已成功、读取待重试”结果模型。重复点击与超时重试的入口也需要按动作 ID/记录 ID 明确。

### M-08：中转、待补全账单和已处理列表的边界过宽

`PagePending` 把 `transactions.status = pending` 与 `staging_records` 合并为一条视觉队列，但两者权威动作、状态机和账户影响不同。下一片不能把两种实体合并成一个 Domain 状态；应先保留 source/type 维度，再统一队列展示模型。

### M-09：历史终态孤儿问题仍未解决

`assigned`、`confirmed` 缺少 `target_record_id` 的历史行仍是规格评审中的阻断项。当前只做读模型评估，不审计或修复生产历史数据。

## 5. REC-009 首片范围

### 目标

验证并收拢以下单一闭环：

1. 记录首次识别后 `retry_count` 的含义不变，首次识别不计入三次重试。
2. 第 1 至第 3 次重试可以提交原 `staging_record_id`，结果结构化返回。
3. 第 4 次重试由服务端拒绝，PWA 不重复提交、不移除记录、不伪造成功。
4. 达到上限后仍能进入人工选择域、字段修复/归档和丢弃。
5. 原图缺失或重试失败时记录继续可见，保留已提取字段和恢复出口。
6. 用户切换或退出后，旧重试响应不能写入新用户队列。

### 非目标

- 不修复 `archiveStagingRecord` 的跨表原子性；另立数据库/生命周期任务。
- 不重写所有中转查询、账户还款、待补全交易和通用域归档。
- 不修改 `staging_records` schema、RLS、Edge 重试规则或生产数据。
- 不删除 `useStore` 兼容 API，不一次性重写 `PagePending` 视觉层。
- 不处理 `assigned/confirmed` 历史孤儿数据，不新增埋点。

## 6. 目标边界

```text
PagePending
    ↓
useStore 兼容门面
    ↓
Staging Feature（队列状态、动作状态、generation、人工出口）
    ↓
Staging Repository（session、Edge/RPC、DTO、错误）
    ↓
ingest-receipt / staging lifecycle RPC
```

`transactions.status = pending` 继续由正式记录/待补全边界负责；Staging Feature 只消费其规范化队列项，不把两个实体的状态机混成一套。
