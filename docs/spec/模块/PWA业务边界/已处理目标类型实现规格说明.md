## 2. 范围

- 新增后续迁移，追加 `staging_records.target_kind` 与 `staging_records.resolved_domain_key`。
- 更新归档包装 RPC，在 legacy 权威成功后同事务写入目标类型，并让幂等分支按实际目标自愈。
- 新增保守历史回填函数/迁移逻辑，只接受实际目标表唯一匹配。
- 扩展 `stagingRepository` DTO 与 `recordRepository` 的按 kind 单条读取。
- 将 `openProcessedStagingRecord` 改为本地/单表读取和结构化失败。
- 新增 PostgreSQL、Repository、Store 特征测试并挂入 Release Validation。

## 3. Store 保留职责

- current user/run guard、页面加载和导航。
- 本地已加载记录的 kind 匹配、提示和打开详情。
- unknown、not found、service error、stale 的用户可观察出口。
- 图片签名、账户读取、保存、删除、wallet 和表达缓存失效。

Repository/数据库负责目标类型事实和单表 transport；Store 不猜测类型，不执行跨表探测。

## 4. 数据库契约

- `target_kind` 为空表示 unknown，非空只能是 `expense`、`income`、`data`。
- `resolved_domain_key` 保存最终归档域，不覆盖 `detected_domain_key`。
- `target_record_id + target_kind` 是导航引用；`target_reference` 只作为 RPC 响应派生字段。
- 归档目标创建、staging 状态、目标类型和反馈必须保持同一事务语义。
- 历史回填不删除、不修改目标记录；无法唯一证明时保留 unknown。

## 5. Repository/Store 契约

- Staging DTO 暴露 `detectedDomainKey`、`resolvedDomainKey`、`targetKind`、`targetRecordId`、`targetReference`。
- `getRecordByTarget({ targetKind, targetRecordId })` 只访问对应的一张正式表，并复用已有 DTO 映射。
- `targetKind` 缺失、非法或 ID 缺失时，Repository 返回 rejected 且不调用 Supabase。
- `openProcessedStagingRecord` 的本地和远程路径都必须经过显式 kind；未知类型不打开、不三表查询。
- 当前 `domainKey` 兼容字段暂保留，但最终域优先使用 `resolvedDomainKey`，识别域使用 `detectedDomainKey`。

## 6. 非目标

- 不修改既有已部署迁移文件，不执行生产迁移或生产审计。
- 不修改 `save_transaction_with_account`、`save_income_with_account`、`delete_record` 或账户流水规则。
- 不改普通通用记录保存、wallet 快照、图片签名、iOS、Edge、Planner 或真实数据。
- 不把 `user_routing_feedback` 变成导航权威，不增加常规 SECURITY DEFINER 列表 RPC。

## 7. TDD 顺序与完成定义

1. 先写迁移/fixture 红灯：字段、回填、RPC 自愈和跨用户行为缺失时失败。
2. 再写 Repository/Store 红灯：DTO 缺字段、单表读取缺失、三表探测仍存在时失败。
3. 最小实现后跑同一专项绿灯，再跑中转/正式记录/安全/治理/架构/build 回归。
4. PostgreSQL fixture 必须至少执行两次迁移；实现不执行生产迁移。
5. 执行记录和交接快照必须记录红灯原因、远程门禁和 unknown 风险。
