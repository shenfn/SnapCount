# PWA 财务保存 transport 边界评估

> 任务：CLEAN-001/A3、PWA-057
>
> 基线：`81e0ed6`（PWA-056 收口 PR #86 合并提交）
>
> 状态：只读评估完成，待文档 PR 门禁

## 1. 结论

下一切片应收拢“手动新建/编辑支出与收入”的客户端 transport 和异步状态，不修改数据库保存规则。

- `save_transaction_with_account` 与 `save_income_with_account` 继续是记录、账户绑定和账户流水的原子权威。
- `recordRepository` 增加两个明确保存方法，负责 RPC 参数映射、错误分层和复用现有正式记录 DTO。
- 新增 `Finance Save Feature`，负责同一保存请求合并、用户/代际隔离和写后刷新结果分层。
- `useStore` 保留表单校验、时间与账户选择、词表学习、页面数组、详情导航和用户提示。
- staging 模式继续走 Staging 原子归档；待补全确认、账户补绑、普通通用记录、wallet 和删除仍是独立用例。

这不是把 `sb.rpc` 换个文件放置。完成标准是：旧会话结果不能污染新用户，RPC 返回行成为本地收敛的唯一 DTO 输入，写入成功不能因刷新失败被误报为保存失败。

## 2. 已核对证据

| 位置 | 当前行为 | 边界判断 |
|---|---|---|
| `confirmExpense` / `confirmIncome` | Store 直接组装两个保存 RPC 的新建与编辑参数 | transport 和错误映射应下沉；表单与账户选择保留在 Store |
| `runLockedAction('expense'/'income')` | 同一进程内阻止第二次调用，但重复调用返回 `null`，不共享结果 | Feature 应持有 inflight Promise；UI action state 只负责禁用和展示 |
| `resetUserData` | 会重置 Staging Feature 和 action state，没有财务保存 generation | 旧用户 RPC 返回后仍可能继续刷新账户、关闭新会话 modal 或写页面数组 |
| 编辑成功路径 | 忽略 RPC 返回行，手工修改部分字段 | `accountId`、`occurredAt`、图片/source 等字段可能保持旧值 |
| 新建收入路径 | 手工构造收入 DTO | 未复用 `mapIncomeRow`，账户绑定等字段可能在本地表现为未绑定直至重载 |
| 新建支出路径 | 使用 `mapTransaction(newRow)` | 这是应统一保留的返回行收敛模式 |
| `refreshAccountsFromDB` / `loadUnboundRecords` | 保存后串行刷新；失败多为 warn/flash，返回值不能区分成功与失败 | 保存 accepted 与 refresh failed 必须分层，不能诱导用户再次保存 |
| 两个 canonical RPC | `SECURITY DEFINER`、`auth.uid()`、行锁、账户流水替换/作废后返回正式行 | 数据库事务权威已存在，首片不改 RPC 或流水算法 |
| `bindRecordToAccount` | 再次直接调用两个保存 RPC，且对象字面量各有重复 `p_occurred_at` key | 属账户补绑用例；另开切片迁移，不能夹入 modal 保存首片 |
| 现有测试 | PostgreSQL 固定时间和部分账户事实；PWA 只覆盖读取与 staging 归档 | 没有财务保存 Repository/Feature、用户切换、写后刷新失败或本地 DTO 收敛测试 |

## 3. 关键风险

### B-09：写入成功后污染新会话

`runLockedAction` 只锁按钮，不捕获 `currentUserId` 或 generation。保存请求期间切换账号时，数据库会按请求时会话写入旧用户，但后续账户刷新、modal 关闭和数组更新可能落到新用户状态。Finance Save Feature 必须像 Staging Feature 一样在 Repository 返回后先检查用户和 generation；stale 结果不得执行调用方收敛回调。

### B-10：写入成功被刷新结果掩盖

账户或未绑定列表刷新发生在 RPC 成功之后。刷新失败不等于保存失败，客户端不得保留 modal 并鼓励重试。Feature 返回应保留 `status: accepted`，同时附带 `refreshStatus: failed` 与错误；Store 应用 RPC 返回 DTO、关闭 modal，并提示“已保存，列表刷新失败”。

### B-11：手工 DTO 导致账户和时间状态漂移

编辑支出/收入忽略 RPC 返回行，新建收入另写一份 DTO。保存 RPC 可能校正上海日期、保留 canonical `occurred_at`、改变账户绑定或保留图片字段；手工补丁无法完整复现。Repository 保存成功必须使用 `mapTransaction` / `mapIncomeRow` 返回统一 DTO，Store 以 ID upsert。

### B-12：客户端并发锁不等于数据库幂等

Feature 可以让同一会话的并发点击共享一个请求，但当前 create RPC 没有 client operation ID；网络超时后人工重试仍可能创建两行。首片不得把“并发合并”描述成端到端幂等。若要覆盖不确定网络重试，需要后续独立数据库契约和迁移。

### B-13：用例混合会扩大账户风险

modal 保存、staging 归档、待补全确认和账户补绑都可能产生财务记录，但权威 RPC、状态机和用户出口不同。首片只处理 manual/edit modal；其余调用不为了“消灭所有直连”被强行并入。

## 4. 目标依赖方向

```text
Modal / useStore
  ├─ 表单校验、时间/账户选择、页面状态与提示
  └─ Finance Save Feature
       ├─ inflight / generation / stale / refreshStatus
       └─ Record Repository
            ├─ save_transaction_with_account
            ├─ save_income_with_account
            └─ mapTransaction / mapIncomeRow

数据库 RPC
  └─ 正式记录 + 账户绑定 + 账户流水原子权威
```

禁止反向依赖：Repository 不读取 Vue ref，不选择默认账户，不学习词表，不刷新页面数组；Feature 不计算余额或复制 SQL 事务规则。

## 5. 候选实现切片

建议实现范围使用 PWA-058 至 PWA-062，PWA-063 保留为后续账户补绑切片：

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| PWA-058 | Repository 只调用对应 canonical 保存 RPC，不发送 `user_id`，成功后复用正式记录 DTO | Repository 行为 |
| PWA-059 | 同一 kind + create/edit ID 的并发保存共享一个请求；不同记录互不阻塞 | Feature 行为 |
| PWA-060 | 用户切换或 reset 后，旧保存结果返回 stale，不执行本地收敛与刷新 | Feature 行为 |
| PWA-061 | RPC accepted 后刷新失败仍保持 accepted，并返回独立 `refreshStatus/refreshError` | Feature 行为 |
| PWA-062 | Store 的 manual/edit 分支委托 Feature，以 RPC 返回 DTO upsert；不再直接调用两个保存 RPC或手工拼收入 DTO | Store 源契约/行为 |
| PWA-063 | 账户补绑复用保存 transport，移除重复参数和重复 key，但继续由账户用例编排刷新 | 后续 Repository/账户 Feature |

## 6. Store 保留职责

- 金额、必填字段和 modal mode 校验。
- 上海时间 occurrence 计算和默认/自动账户选择。
- staging 模式分流到 `archiveStagingRecord`。
- accepted 后的数组 upsert、详情刷新、词表学习、modal 关闭和文案。
- 账户/未绑定列表刷新回调及 `refreshStatus` 的用户提示。

Store 不再为 manual/edit 直接组装保存 RPC，不再手工维护第二份正式记录 DTO。

## 7. 非目标

- 不修改两个数据库保存 RPC、账户流水、余额方向、时间契约或生产迁移。
- 不处理 staging 归档、`confirm_pending_transaction_with_account`、账户补绑、批量补绑、wallet、普通通用域或删除。
- 不声称 create 已具备网络重试幂等。
- 不执行生产查询、真实数据修复、迁移、部署或 TestFlight。
- 不以减少 `useStore` 行数作为完成标准。

## 8. 进入实现的门禁

1. 先建立 PWA-058 至 PWA-062 实现 Spec、执行记录和交接快照。
2. 先用现有 Store 源契约固定 staging/待补全/账户补绑不进入本切片。
3. 红灯分别证明 Repository 保存缺失、Feature 会话隔离缺失和 Store manual/edit 仍直连 RPC。
4. 更新 PWA-052 至 PWA-055 的“Repository 不写”测试时，只允许放开两个明确保存 RPC；账户、staging、删除和任意其他写入仍禁止。
5. 本地 Repository/Feature/Store 专项、财务时间契约、staging 回归、治理、架构和 PWA build 通过后再创建实现 PR。
