# PWA 账户管理边界评估

> 任务：CLEAN-001/A3、PWA-066
>
> 基线：`06dde1b`（PWA 账户读取实现收口 PR #99 合并提交）
>
> 状态：已完成，PR #100 已合并（`e0ef559`）

## 1. 结论

PWA 的账户创建、编辑、默认项和归档不能只从 `useStore.js` 平移到 Account Repository。当前默认账户保存是“先写目标账户，再清其他默认”的多次客户端写入；后续写入失败时，PWA 仍显示成功并在本地清空其他默认标记。数据库没有唯一约束或归档默认约束，iOS 也在执行同类多步 REST 写入，因此只修 PWA 会继续留下跨端竞态。

PWA-066 应建立一个兼容存量客户端的数据库原子契约：

1. 数据库 trigger/约束保护默认账户互斥、归档账户非默认和并发写入；旧版 PWA/iOS 继续直写时也不能制造多默认。
2. 新客户端通过 canonical save/archive RPC；Account Repository 只负责 RPC 参数与 DTO，Account Management Feature 负责 command identity、并发、user/generation stale 和 accepted/refresh 分层。
3. 归档是唯一产品删除语义。本片不新增单账户物理删除；历史流水、记录、还款和余额继续保留。
4. PWA 必须增加已归档账户入口和恢复出口；恢复不自动恢复默认项或自动扣款关系。

## 2. 当前职责矩阵

| 职责 | 当前入口 | 当前事实 | 目标归属 |
|---|---|---|---|
| 创建/编辑账户 | `saveAccount` | Store 直写 `accounts`；创建显式发送 `user_id` | Account Repository 调 canonical RPC |
| 默认支出/收入 | `unsetOtherDefaults` | 保存目标后再清其他账户；失败只 warning | 数据库事务、trigger 与唯一约束 |
| 归档/恢复 | modal 的 `isArchived`、未被调用的 `archiveAccount` | 归档保留默认标记；PWA 无稳定归档列表/恢复入口 | archive RPC + Account Management Feature + 归档列表 |
| 当前列表收敛 | `accounts.value` 局部替换/插入 | 默认清理失败仍修改本地；写后不重新读取 canonical 列表 | Feature 的 accepted convergence + 独立 refresh 结果 |
| 当前详情收敛 | `selectedAccount` | 保存只更新列表项，详情仍持有旧对象 | Store 兼容门面同步 canonical account |
| 会话与并发 | `runLockedAction('account')` | 只锁按钮；reset/用户切换不能使旧写结果 stale | Account Management Feature |
| 类型与负债设置 | modal 表单 | 客户端清空非负债字段；数据库不约束跨资产/负债迁移 | RPC/数据库验证，页面显示结构化失败 |
| iOS 同类动作 | `AccountRepository.save/setArchived` | 有归档列表，但默认项仍为多次 REST 写入，AppState 保存无 generation guard | A4 复用同一数据库契约 |

## 3. 已确认的现状

### 3.1 默认账户不是原子事实

- PWA 创建或编辑时先把目标行写成默认，再分别调用 `unsetOtherDefaults('expense'/'income')`。
- 清理其他默认账户失败时只记录 console warning，函数仍更新本地列表、关闭 modal 并显示“账户已创建/更新”。
- 两个并发客户端可以分别写出默认账户；`accounts` 表没有 partial unique index、互斥 trigger 或归档默认 check。
- `defaultAccountIdForKind` 只取排序后的第一个活跃默认项，所以数据库若已有多个默认，实际选择依赖列表顺序而非明确权威。
- iOS `AccountRepository.save` 也先保存目标行再清其他默认；第二步失败会报整体失败，但第一步已经提交，仍可能留下部分成功。

### 3.2 归档状态没有完整出口

- modal 可把 `is_archived` 和两个默认标记一起写成 true；独立 `archiveAccount` 也只改变 `is_archived`，不清默认项。
- PWA wallet 页面、账户选择器和推荐逻辑都过滤归档账户；`archiveAccount` 在产品代码中没有调用方。
- PWA 没有已归档账户列表。归档后离开当前详情，用户没有稳定恢复入口。
- 保存后只替换 `accounts` 中的元素，不同步 `selectedAccount`；详情页可能继续显示旧名称、旧类型或旧归档状态。
- iOS 已有“已归档”列表和恢复按钮，可作为跨端产品语义参考，但其数据库写入仍不是原子契约。

### 3.3 会话、失败和结果分层缺失

- `runLockedAction('account')` 只阻止当前页面重复点击，不记录 user/generation 或 command identity。
- reset 会清空锁和账户数组，但已经发出的保存仍可在返回后写入新会话的列表、关闭 modal 并显示旧用户提示。
- 保存返回 `data/null`，归档返回 `undefined`；没有 `accepted/failed/stale/conflict`，也无法表达“数据库已接受但列表/详情刷新失败”。
- PWA 没有账户管理专项测试。现有 `test:account-read` 只保护纯读取边界。
- iOS 保存和归档也缺少 `userStateGeneration` 的写后 guard；数据库契约必须跨端共享，端侧 stale 仍分别在 PWA A3 和 iOS A4 修复。

### 3.4 类型与引用关系

- 账户初始余额只在创建时写入，PWA 编辑表单禁用该字段且 update body 不修改余额；这一不变量应保留。
- 资产转负债或负债转资产目前没有数据库迁移规则。已有账户可能持有流水、账单周期、还款记录或被其他负债账户作为自动扣款账户，直接改类型会使既有数据语义与页面可见性漂移。
- 归档一个自动扣款资产账户时，`accounts.auto_debit_account_id` 和开放账单周期仍可能指向它；现有还款 RPC 只校验账户归属，不校验是否归档或是否为资产账户。
- 历史交易、收入和快照引用使用 `on delete set null`，流水、账单和还款对账户使用 cascade；因此本片继续采用软归档，不开放单账户物理删除。

## 4. 数据库原子契约

### 4.1 默认项兼容策略

不能只增加 partial unique index。存量 iOS/PWA 会先把新账户写成默认、再清旧默认；直接启用唯一索引会让这些客户端在第一步失败。

实现片应同时提供：

- 在迁移中先清理已有归档默认标记；若同一用户已有多个活跃默认，保留现有列表排序实际会选中的第一项（`sort_order`、`created_at`、`id`），清除其余项。
- `before insert or update` trigger 在同一用户范围串行化默认变更；目标设为默认时先清同类其他默认，目标归档时强制清除两个默认标记。
- 两个 active partial unique index 作为最终并发兜底；归档默认 check 防止旁路写入。
- canonical `save_account` RPC 不接收 `user_id`，使用 `auth.uid()`，并返回 canonical account row。

这样旧客户端直写仍保持兼容，新客户端不再复制多步默认逻辑。

### 4.2 归档语义

- canonical `set_account_archived` RPC 在一笔事务中归档/恢复并返回账户行和必要结果元数据。
- 归档清除默认支出/收入标记，不自动选择替代默认账户。
- 归档自动扣款资产账户时，必须在同一事务中解除未来自动扣款设置与开放周期引用；历史 payment/entry 不改写。
- 恢复只改变 active 状态，不恢复默认标记或自动扣款关系。
- 不删除账户，不修改初始余额、当前余额、历史流水或正式记录绑定。

### 4.3 类型变更

- 同一资产家族内、同一负债家族内的类型调整保持允许。
- 已有流水、账单、还款或自动扣款引用的账户不得通过普通编辑跨资产/负债家族迁移；返回结构化 `account_type_transition_blocked`。
- 空且无引用的账户可以跨家族修改；转为资产时由 RPC 清空负债专属设置。
- 若以后需要迁移有历史的账户类型，应建立独立迁移场景，不把它伪装成资料编辑。

## 5. 目标依赖方向

```text
ModalAccount / wallet 页面 / useStore 兼容门面
  └─ Account Management Feature
       ├─ command identity + Promise 复用/冲突
       ├─ user/generation stale
       ├─ accepted account 收敛 + refresh 分层
       └─ Account Repository
            ├─ saveAccount -> save_account RPC
            └─ setAccountArchived -> set_account_archived RPC

数据库
  ├─ canonical RPC
  ├─ default normalization trigger
  ├─ active default unique indexes/check
  └─ 账户、默认项、归档和未来自动扣款引用的事务权威
```

Repository 不拥有 Vue、modal、确认文案、当前选中账户或推荐规则。Feature 不直接调用 Supabase。Store 保留现有公开 API，页面不直接依赖 Repository。

## 6. 主要风险

### B-32：默认项部分成功与并发多默认

目标账户保存和清理其他默认项是多次提交；失败或多端并发会留下多个默认。必须由数据库事务和约束保护，不能只在 Feature 排队。

### B-33：页面成功提示与数据库事实不一致

PWA 忽略默认清理失败并修改本地列表。新 Feature 必须只收敛 canonical 返回；RPC accepted 与后续读取刷新分开表达。

### B-34：归档账户没有恢复出口

PWA 所有账户列表都过滤归档项，独立恢复函数没有调用方。实现片必须提供已归档列表和恢复动作，否则归档是事实上的单向状态。

### B-35：旧会话写结果污染新用户

保存/归档没有 user/generation guard。旧请求返回后可能更新新用户列表、详情和提示。Feature 必须在 transport 后、收敛前和 refresh 后检查 identity。

### B-36：列表与当前详情分叉

保存只更新 `accounts`，不更新 `selectedAccount`。用户可在详情页继续看到旧资料。accepted canonical row 必须同时按 id 收敛列表与当前详情。

### B-37：类型切换破坏历史语义

普通资料编辑可以把有账单/流水的负债账户改成资产，隐藏既有周期并保留负债数据。跨家族变化必须由数据库检查，而不是只靠 modal。

### B-38：只修 PWA 会被 iOS 再次破坏

iOS 仍会执行存量多步 REST 写入。trigger 与约束必须兼容旧客户端；A4 再把 iOS transport 和 AppState 接到相同 RPC 与 stale 语义。

## 8. 明确非目标

- 不新增单账户物理删除，不修改用户整号删除契约。
- 不处理 wallet 快照创建、关联、余额 repair、截图还款或流水补偿 helper。
- 不修改还款金额、状态、溢缴或历史 payment/entry。
- 本评估不新增 migration/RPC，不修改 PWA/iOS/Edge/Planner 业务代码，不连接生产数据。
- PWA-066 实现片不修改 iOS；iOS 在 A4 使用相同场景与数据库契约复核。
