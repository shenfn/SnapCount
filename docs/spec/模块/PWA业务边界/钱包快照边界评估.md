# PWA 钱包快照边界评估

> 任务：CLEAN-001/A3、PWA-068
>
> 基线：`c66e0a3`（PWA-067A 至 PWA-067G 收口 PR #106 合并提交）
>
> 状态：只读评估完成，待文档 PR 验证

## 1. 结论

PWA 的 wallet 快照创建账户、关联既有账户、生成账期和校准余额不能只从 `useStore.js` 平移到 Repository。当前一次用户动作最多跨越 `accounts`、`data_records`、`account_repayment_cycles`、`liability_payments` 和 `account_entries`，但这些写入由客户端逐步提交；部分失败会留下可见中间态，重试也无法稳定判断上一轮已经写到哪一步。

后续实现应由一个数据库原子命令承接整条业务事务，并在客户端按三层收拢：

1. 数据库锁定并验证同一用户的钱包记录和目标账户，原子完成创建或关联、快照元数据、可选账期/还款证据、流水和校准水位。
2. Account Repository 独占 RPC transport，并复用账户与还款周期的 canonical DTO；Store 不再直写相关表。
3. 独立 Wallet Snapshot Feature 负责命令身份、重复请求、冲突、用户/generation stale，以及 accepted 与 refresh 分层。

金额语义必须先收紧：资产余额、负债账单金额、当前总欠款和已还金额不是同一个事实。旧 `liability_snapshot` 默认只能证明账单金额；只有明确的“当前总欠款”证据才能校准账户余额，`status=paid` 必须形成可追踪的还款证据，不能把账户当前欠款直接设成截图金额。

## 2. 当前调用链与目标归属

| 职责 | 当前实现 | 当前问题 | 目标归属 |
|---|---|---|---|
| 创建账户 | `useStore.createAccountFromWalletSnapshot` 直接查询/插入 `accounts` | 查重、创建、记录关联和账期分多次提交 | 数据库原子命令 + Account Repository |
| 关联账户 | `useStore.linkWalletSnapshotToAccount` 直写账户与记录 | 账户先成功、记录后失败时无回滚 | 数据库原子命令 |
| 开账余额 | `shouldAdoptSnapshotAsOpeningBalance` | 只在客户端读计数后判断，存在并发窗口 | 数据库锁内判定 |
| 负债账期 | `upsertRepaymentCycleFromWalletSnapshot` 直接 upsert | 可覆盖已有付款状态和高价值证据，失败仅 warning | 数据库证据优先级与状态规则 |
| 余额校准 | `reconcileLiabilityAccountFromWalletSnapshot` | 客户端先算 delta；流水失败仍更新校准时间 | 数据库锁内计算与写入 |
| 历史 repair | `repairEmptyAccountSnapshotBalances` | 当前只有定义无调用；历史 WIP 曾在读取时自动写 | 独立显式修复命令或迁移 |

## 3. 只读发现

### B-39：创建和关联都可能留下部分成功

创建流程先插入账户，再更新 `data_records`，最后 upsert 账期。记录关联失败时，代码明确提示“账户已创建，但关联快照失败”；账期失败则只写 console warning。关联既有账户时又先更新账户快照字段，再更新记录，之后才写账期、调整流水和校准时间。

这些都不是可由 Repository 隐藏的普通 transport 细节。必须由数据库事务统一提交或回滚，并返回 canonical 结果。

### B-40：截图 upsert 可以破坏还款权威

`upsertRepaymentCycleFromWalletSnapshot` 对 `(account_id, cycle_month)` 使用无条件 upsert，并直接写 `statement_amount`、`paid_amount`、`remaining_amount`、`status` 和 `source`。它没有保护既有 manual/screenshot 高优先级事实，也没有检查 `liability_payments`。

因此一条 `unpaid` 快照可能把已部分还款或已还清账期重置为 pending；一条 `paid` 快照又可能把账期标为已还清，却没有对应 payment 和还款流水。后续命令必须复用 PWA-064/PWA-067 的金额与状态规则，并让 `evidence_record_id` 指向正式 `data_records` 证据。

### B-41：同一个金额被当成三种不同事实

当前 `amountFromWalletSnapshot` 将 `snapshot_balance` 或 `amount` 同时用于账户 `snapshot_balance`、账期 `statement_amount` 和负债账户余额校准目标。Prompt 对 liability 的定义是“待还/应还金额”，并不保证它等于账户当前总欠款；对于 `status=paid`，它更可能是账单或已还金额。

目标语义应为：

- 资产快照金额可作为新账户 opening balance；关联非空账户时只更新观测快照，不无条件改写账本。
- 未还负债快照默认是 statement evidence，可生成或增强账期，但不能默认覆盖当前总欠款。
- 已还负债快照是 repayment evidence；只有匹配到同用户同账户账期后，才按 canonical repayment 规则生成 payment/entry 并减少欠款。
- 只有显式的 current-total 证据才允许执行账户余额 reconciliation。

### B-42：RLS 不能替代跨表同用户约束

`accounts`、`data_records`、`account_repayment_cycles` 和 `liability_payments` 都有基于 `auth.uid() = user_id` 的 RLS，但外键只验证 UUID 存在，不验证关联对象属于同一用户。当前客户端还会显式提交 `user_id`、`account_id` 和 `evidence_record_id`。

知道另一用户 UUID 的调用方理论上可以创建“自己的账期指向别人的账户”或“自己的记录指向别人的账户”；RLS 会隐藏对方行，却不会自动约束外键租户一致性。原子 RPC 必须从 `auth.uid()` 推导用户，并显式验证记录、账户、账期、payment 和 evidence 的所有权一致。

### B-43：流水失败仍可能被标为已校准

`upsertAccountEntry` 在 RPC 失败时只 `console.warn`，不抛错也不返回结构化失败。`reconcileLiabilityAccountFromWalletSnapshot` 随后仍更新 `accounts.last_reconciled_at` 并返回 `true`。

这会产生“余额没有变化，但系统认为该时间之前的流水已经完成校准”的状态，进而影响 `ensure_liability_repayment_cycles` 对历史流水的筛选。新命令必须在同一事务内写 adjustment 和单调递增的 `last_reconciled_at`；任一步失败全部回滚。

### B-44：幂等和时间顺序只在客户端近似处理

创建流程用本地集合、预查询和 `uq_accounts_source_record` 降低重复账户概率，但并发请求仍可能在预查询后竞争唯一索引，第二个请求只得到普通失败。关联流程没有锁定 `data_records`，也没有 compare-and-set 保证“未关联或已经关联到同一账户”。

同时旧快照可以覆盖更新的 `snapshot_at` 或把 `last_reconciled_at` 向过去移动。原子命令必须锁定记录/账户，以 `record_id + operation + target_account_id` 定义命令身份：同目标重试返回既有结果，不同目标返回稳定 conflict；旧快照可以保留为历史证据，但不得回退当前快照或校准水位。

### B-45：历史 repair 不能重新接入读取链

当前 `repairEmptyAccountSnapshotBalances` 只有定义，没有调用者；账户读取测试也明确要求读取边界没有隐藏 repair 写。历史 `codex/账户快照关联修复` WIP 曾把它接入 `loadData` 和 `refreshAccountsFromDB`，但该 worktree 已落后主线 184 个提交，不能直接吸收。

如果确有存量空余额需要修复，应先用只读 fixture 确认可证明集合，再通过一次性 migration 或显式用户命令处理。普通列表加载不得产生余额写入，repair 也不能只改账户而遗漏记录、流水、账期或审计证据。

### B-46：PWA 与 iOS 会话和失败语义仍会漂移

PWA 只有页面级创建集合；没有 user/generation stale、命令冲突或 accepted/refresh 分层。`PageDomainDetail` 在 Store 返回后无条件收起账户选择器。iOS 同样用多步 REST，但把账期和校准失败包装成 warnings，并且该写流程没有 `userStateGeneration` guard。

数据库原子契约必须先跨端共享；A3 只接 PWA 的 Repository/Feature/Store，A4 再让 iOS 使用同一 RPC 和同一组场景。不能继续让两端各自维护一次跨表事务。

## 4. 数据库原子契约

后续正式 Spec 应把一个 canonical wallet snapshot command 固定为以下事务边界：

1. 使用 `auth.uid()`，拒绝未登录；锁定 wallet `data_records`，验证记录属于当前用户、金额非负、类型可识别。
2. `p_account_id` 为空时创建来源账户；非空时锁定并验证同用户、未归档且账户家族与快照兼容。
3. 记录未关联时完成绑定；已关联同一账户时作为幂等重试；已关联其他账户时返回稳定 conflict。
4. 在锁内判断空账户是否可以采用 opening balance；非空账户只写观测快照，除非存在可验证的 current-total 证据。
5. liability statement 按证据优先级 upsert cycle，不覆盖已有 payment、终态或更高优先级事实。
6. `status=paid` 时以正式 record 作为 evidence，按 canonical repayment 规则创建可幂等 payment/entry；无法唯一匹配账期时返回 `needs_confirmation`，不伪造已还清。
7. adjustment、账户余额和 `last_reconciled_at` 在同一事务内更新，校准时间只能单调前进。
8. 返回 account、record link、可选 cycle/payment 和 operation result；任何一步失败全部回滚。

数据库还需要为活跃 `liability_payments.evidence_record_id` 提供幂等约束，避免同一正式快照被重复确认为两次还款。具体索引和兼容回填只能在 PostgreSQL fixture 先建立后确定。

## 5. 目标依赖方向

```text
PageDomainDetail / useStore 兼容门面
  └─ Wallet Snapshot Feature
       ├─ command identity + Promise 复用/冲突
       ├─ user/generation stale
       ├─ accepted 收敛 + refresh 分层
       └─ Account Repository
            └─ canonical wallet snapshot RPC + account/cycle DTO

数据库 RPC
  └─ data_record + account + cycle/payment + entry/balance 原子权威
```

Feature 不依赖 Vue 或 Supabase；Repository 不读写 Store 数组；Record Repository 继续负责正式记录读取，不复制账户和账期 DTO。若返回需要完整 record DTO，应先抽取纯 mapper，不能让 Repository 相互依赖。

## 7. 明确非目标

- 本评估不新增 migration、RPC、Feature、Repository 方法或页面代码。
- 不修改 iOS、Edge、Planner、生产配置或真实数据；A4 再接 iOS。
- 不把 `repairEmptyAccountSnapshotBalances` 重新接入加载链，不直接吸收历史 WIP。
- 不进入 PWA-069 通用流水 helper，也不顺手重写手动还款或截图还款 Feature。
- 不执行生产查询、migration、部署、TestFlight 或远端清理。

## 8. 进入实现的门禁

1. 本评估、ADR-029、执行记录和交接快照通过文档 PR 门禁并合并。
2. 从合并后的最新 main 建立独立 `feature/PWA钱包快照原子边界` worktree。
3. 先提交 PWA-068A 至 PWA-068J 正式 Spec，明确金额语义、账期匹配、幂等键和稳定失败原因。
4. 先建立 PostgreSQL fixture 和 Repository/Feature/Store 红灯，再写 migration 和客户端接线。
5. PostgreSQL fixture 必须连续执行 migration 两次，并覆盖回滚、跨用户、并发重试、证据优先级、paid payment/entry 和时间单调性。
