# PWA 已处理目标类型边界评估

> 任务：CLEAN-001/A3、PWA-056
>
> 基线：`090bd17`（PWA-052 至 PWA-055 PR #83 合并提交）
>
> 状态：只读评估完成，待文档 PR 门禁

## 1. 结论

已处理中转记录的目标类型必须成为中转解析结果的一部分，不能从识别结果、查询顺序或可变反馈推断。推荐在 `staging_records` 持久化两个可空字段：

- `target_kind`：只允许 `expense`、`income`、`data`，决定唯一目标表；
- `resolved_domain_key`：保存用户最终归档域，如 `expense`、`income`、`sport`，用于列表展示和审计。

`target_record_id + target_kind` 是正式记录导航的规范化引用。归档 RPC 可以继续返回 `target_reference` 作为命令响应便利字段，但客户端只在前两者完整且合法时派生引用，不把字符串前缀作为第二份持久化事实。

历史记录只能根据实际目标表中同时匹配 `target_record_id`、`staging_record_id` 和 `user_id` 的唯一记录回填。无法证明或出现多表歧义的记录保持 `target_kind = null`，客户端显示不可导航状态，不并行查询三张表。

## 2. 当前事实

| 证据 | 当前行为 | 判断 |
|---|---|---|
| `staging_records` | 持久化 `target_record_id`，通用域可有 `target_domain_id`，没有目标表类型 | UUID 本身无法表达目标表；财务记录的 `target_domain_id` 固定为空 |
| `archive_staging_record` | 返回 `expense/<id>`、`income/<id>` 或 `data/<id>`；新域不一致重试会校验真实目标 | 命令响应当次可靠，但 `target_reference` 未写回中转行，刷新后丢失 |
| `user_routing_feedback` | 归档成功时写 `corrected_domain_key`；RLS 按用户隔离 | 适合审计与学习；一对多、可包含 retry/discard，且不是中转行的解析状态，不应成为导航运行时权威 |
| `stagingRepository.listProcessed` | 只读取 `staging_records.*`，DTO 的 `domainKey` 来自 `detected_domain_key` | 用户纠正域后，刷新会把识别域误当成最终域 |
| `rememberProcessedStaging` | 当次归档后临时写入用户选择的 `domainKey` | 未刷新时看似正确，刷新后行为漂移 |
| `openProcessedStagingRecord` | 本地未命中后并行查询 `transactions`、`income_records`、`data_records` | 以查询结果猜类型，违反 ADR-021；三次请求也无法解释 unknown/已删除/失败差异 |

## 3. 候选方案比较

| 方案 | 优点 | 根本问题 | 裁决 |
|---|---|---|---|
| 列表嵌套读取最新 `user_routing_feedback` | 不新增中转字段 | 一对多排序和历史缺行复杂；反馈是审计事实而非解析状态；客户端必须理解 action 过滤 | 不采用为运行时权威 |
| 只持久化 `target_reference` | 客户端解析直观 | 与 `target_record_id` 重复，字符串前缀和 ID 可能漂移；缺少最终业务域 | 不采用为唯一事实 |
| 新增已处理列表 RPC，运行时联查三张目标表 | 可兼容历史 | 每次列表读取承担跨表判断；目标删除后类型再次丢失；扩大 SECURITY DEFINER 表面 | 不作为常规路径 |
| 持久化 `target_kind + resolved_domain_key` | 单行可恢复、列表和导航职责清晰、可在归档事务内写入 | 需要新迁移、回填和数据库 fixture | 采用 |

## 4. 推荐数据库契约

### PWA-056A：字段与约束

- 新迁移追加 `target_kind text null`，检查值仅为 `expense`、`income`、`data`。
- 新迁移追加 `resolved_domain_key text null`，保存归档请求通过服务端校验后的最终域。
- 首轮保持可空，避免历史异常行因强制非空阻塞迁移；完成只读审计后再决定是否为新归档增加更强约束。
- 不修改历史迁移文件，不把 `detected_domain_key` 覆盖成最终域。

### PWA-056B：原子写入与幂等

- 新迁移替换当前 `archive_staging_record` 包装函数，不直接改已部署迁移。
- 首次归档调用 legacy 权威后，在同一数据库事务内写入：
  - `target_kind = expense`，当最终域为 `expense`；
  - `target_kind = income`，当最终域为 `income`；
  - 其他已验证域统一为 `target_kind = data`；
  - `resolved_domain_key = p_domain_key`。
- 已归档幂等分支继续从实际目标表及 `staging_record_id + user_id` 校验真实类型，并自愈缺失字段；不得根据本次请求拼接类型。
- RPC 返回的 `target_reference` 必须和持久化 `target_kind + target_record_id` 一致。

### PWA-056C：历史回填

对每个 `status = archived` 且有 `target_record_id` 的中转行：

1. 在三张目标表分别要求 `id = target_record_id`、`staging_record_id = staging.id`、`user_id = staging.user_id`。
2. 只有恰好一张表命中时回填 `target_kind`。
3. 财务记录的 `resolved_domain_key` 固定为 `expense` 或 `income`；通用记录取实际 `data_records.domain_key`。
4. 零命中或多表命中保持 null，并由迁移 fixture/审计查询报告，不使用 `detected_domain_key` 或任意 feedback 猜测。

`user_routing_feedback` 可用于人工对账，但不能覆盖实际目标关系的结论。

## 5. 推荐客户端契约

### PWA-056D：已处理 DTO

`stagingRepository.listProcessed` 映射：

- `detectedDomainKey`：保留识别域；
- `resolvedDomainKey`：最终归档域；
- `targetKind`：目标表类型；
- `targetRecordId`：目标 ID；
- `targetReference`：仅在 kind 与 ID 均合法时派生。

现有 `domainKey` 兼容字段需要在实现 Spec 中明确退场或只作为 UI 兼容门面，不再同时承载识别域和最终域。

### PWA-056E：单表读取与失败出口

- Record Repository 增加按 `targetKind` 读取单条正式记录的只读方法；一次调用只允许访问一张表并复用现有 DTO 映射。
- Store 先按 `targetKind` 查本地数组，未命中时只调用对应 Repository 方法。
- `targetKind` 缺失/非法：不发请求，提示“目标类型待恢复”，返回结构化 rejected。
- 目标不存在：提示“归档后的记录已不存在”；读取失败：保留服务错误；用户/session 已变化：结果标记 stale，不打开旧用户记录。
- 删除三表并行探测；不得用 `resolvedDomainKey` 将任意通用域名当成表名。

## 7. 非目标

- 本评估不创建或执行迁移，不修改 RPC、PWA、iOS、Edge 或生产数据。
- 不修复生产历史 unknown 行，不读取真实用户反馈或记录。
- 不改变正式记录保存、删除、账户、wallet、图片签名或 Planner。
- 不把 feedback 表改成导航 Repository，也不新增常规列表 SECURITY DEFINER RPC。

## 8. 实现进入门禁

1. 先建立 PWA-056A 至 PWA-056E 实现 Spec、PostgreSQL fixture 和 Node 红灯。
2. 红灯必须证明字段/原子写入/单表读取缺失，不得以数据库未安装或环境错误冒充。
3. 数据库迁移在本地 fixture 双次执行通过后，才允许接线 Repository 与 Store。
4. 任何生产迁移、线上审计或数据修复仍需用户在对应任务中明确授权。
