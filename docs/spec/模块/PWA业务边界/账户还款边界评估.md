# PWA 账户还款边界评估

> 任务：CLEAN-001/A3、PWA-064
>
> 基线：`85882db`（PWA 账户补绑收口 PR #92 合并提交）
>
> 状态：只读评估完成，待文档 PR 门禁

## 1. 结论

“账户还款”不是一个可一次迁移的单模块。当前 Store 中至少混合了五类具有不同事务和失败语义的职责：手动还款事务、账户资料与详情读写、截图还款、wallet 快照跨表关联、正式记录流水补偿。它们必须分片收拢。

第一实现片只处理 `set_repayment_cycle_paid_amount` / `revoke_liability_payment`：先用 PostgreSQL 特征测试固定事务权威，再由 Account Repository 封装 transport，由独立 Repayment Feature 处理并发、generation、用户切换、accepted 与 refresh 分层。账户 CRUD、截图还款、wallet 快照关联和旧流水 helper 均不进入首片。

## 3. 数据库权威边界

- `set_repayment_cycle_paid_amount` 在单一事务内锁定 cycle 与账户，作废旧 payment/entry，写入新 payment、负债流水和可选扣款流水，再返回 canonical cycle。
- `revoke_liability_payment` 作废 payment 与关联流水，按仍有效 payment 重算 cycle；重复撤销返回当前 cycle，不重复修改余额。
- `confirm_staging_repayment` 锁定 staging，并委托 `set_repayment_cycle_paid_amount`，最后原子归档 staging；已按同一 cycle 归档时返回已有结果。
- `account_entries` 触发器负责余额增减；客户端不得复制余额计算或把 RPC accepted 后的刷新失败解释为事务失败。
- 当前 Release Validation 没有针对上述事务的 PostgreSQL 行为 fixture。安全检查只证明部分权限声明存在，不能证明金额、重新确认、撤销和余额联动正确。

## 4. 主要风险

### B-19：旧还款请求污染新会话

PWA 只使用 `runLockedAction` 锁按钮。reset 会清空页面锁，却不会使已发出的 RPC 结果 stale；旧请求返回后仍可能更新新用户的 cycle、刷新详情并显示旧成功提示。Feature 必须在 Repository 返回、accepted 收敛和刷新后检查 generation 与用户。

### B-20：accepted 与 refresh 混为布尔结果

还款 RPC accepted 后，账户列表和详情刷新可能失败。当前函数忽略刷新结构化结果并返回 `true`。新契约必须保留 canonical cycle 与 accepted 事实，同时单独返回 `refreshStatus` / `refreshError`，不得建议重复还款。

### B-21：wallet 快照关联存在可见中间态

现有流程依次更新或创建 account、更新 data record、upsert cycle、写 adjustment、刷新列表。任一步失败都可能留下单边关联、旧余额或缺失 cycle。Repository 抽取不会自动获得原子性；该片必须先设计数据库 RPC 和迁移 fixture。

### B-22：账户默认项不是原子操作

账户保存成功后才调用 `unsetOtherDefaults`，且失败只打印 warning；客户端仍会把本地其他默认项清空。数据库与页面可能出现不同事实。账户 CRUD 不得与手动还款首片一起迁移，后续需先裁决是否新增原子保存 RPC。

### B-23：读取流程包含写副作用

`loadData` 在加载列表时调用 `ensure_liability_repayment_cycles`，`refreshAccountsFromDB` 又可能调用 `repairEmptyAccountSnapshotBalances` 写账户余额。后续 Repository 必须把查询与“确保周期/修复余额”分成显式方法，不能让 `listAccounts` 暗中写数据库。

### B-24：端侧还款状态规则重复

PWA 页面和 iOS `NativeRepaymentCalculator` 都计算 `paid` / `minimum_paid` / `partial_paid` 与溢缴金额，数据库又接受客户端传入的 `p_status`。首片必须固定 PWA 行为场景；A4 需让两端测试引用同一组共享 fixture，避免一端改变阈值后静默漂移。

### B-25：流水 helper 的实际调用范围不清晰

`upsertAccountEntry` 仅由 wallet 负债快照校准调用；`voidAccountEntries` 在产品代码中未发现调用，但仍由 Store 暴露。它们不是手动还款 transport，不能为追求“统一账户 Repository”直接搬入或删除；必须先做消费者与迁移兼容审计。

## 5. 首片目标依赖方向

```text
PageAccountDetail / useStore
  ├─ 金额模式、确认交互、页面状态与提示
  └─ Repayment Feature
       ├─ command 校验与同事务并发保护
       ├─ generation / user stale
       ├─ accepted cycle 收敛与 refresh 分层
       └─ Account Repository
            ├─ confirmRepayment
            └─ revokePayment

数据库 RPC
  └─ payment + cycle + account entries + balances 原子权威
```

Repository 只拥有 RPC 参数、返回 DTO 与传输错误；不计算推荐扣款账户、还款金额、状态、余额方向或页面提示。Feature 不直接依赖 Vue。Store 保留兼容 API。

## 6. PWA-064 后续实现场景

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| PWA-064A | PostgreSQL fixture 固定确认、重新确认、撤销、重复撤销、负债/扣款流水、余额和跨用户拒绝；不改生产迁移 | 数据库特征测试 |

| PWA-064C | 同一事务的重复请求共享 Promise；同一 cycle 的不同确认命令或确认/撤销交叉操作返回 `repayment_conflict`，撤销同一 payment 也不得重复发写入 | Repayment Feature |
| PWA-064D | reset 或用户切换使旧结果 stale；stale 不收敛 cycle、不刷新、不提示当前用户 | Repayment Feature |
| PWA-064E | RPC accepted 后先收敛 canonical cycle；刷新失败仍为 accepted，并返回独立刷新结果 | Feature/Store 行为 |
| PWA-064F | 页面保留全额/部分金额、最低还款、溢缴和扣款账户预览；Store 只提交已确认 command，失败可重试，accepted 不诱导重复写入 | Page/Store 源边界与回归 |

## 8. 非目标

- 本评估不修改业务代码、数据库迁移、RPC、账户余额或生产数据。
- PWA-064 首片不迁移账户列表、详情、CRUD、默认账户、周期生成、截图还款或 wallet 快照。
- 不以 iOS 已有 Repository 为理由复制其 AppState 编排；PWA 与 iOS 共享业务语义，但各自修复会话隔离。
- 不承诺网络超时后的端到端 exactly-once；数据库行锁与重新确认替换规则不等于客户端 operation ID。
- 不执行生产查询、部署、真实数据写入或 TestFlight。
