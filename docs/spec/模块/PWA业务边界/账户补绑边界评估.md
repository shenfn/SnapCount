# PWA 账户补绑边界评估

> 任务：CLEAN-001/A3、PWA-063
>
> 基线：`564bd20`（PWA 财务保存边界收口 PR #89 合并提交）
>
> 状态：已完成，PR #90 已合并

## 1. 结论

账户补绑应复用 `recordRepository.saveExpense` / `saveIncome` 的 canonical transport，但必须使用独立的 Account Binding Feature 编排，不复用 modal 的 Finance Save Feature，也不修改数据库 RPC。

- 两个 `save_*_with_account` RPC 继续是正式记录、账户绑定和账户流水的原子权威。
- Account Binding Feature 负责单笔并发、冲突账户、generation、用户切换、批量停止条件和结构化逐项结果。
- Store 保留推荐账户计算、确认交互、页面数组收敛、表达计划失效和用户提示。
- 推荐算法、默认账户策略和余额方向不在本片修改；Feature 只接收已明确确认的 `accountId`。
- 批量补绑是多次独立数据库事务，不得描述成原子批处理或端到端幂等。

这不是删除两处重复参数键即可完成的修复。当前实现会丢弃 RPC 返回 DTO、混淆写入与刷新结果，并且旧批量循环在用户切换后仍可能继续运行。

## 2. 已核对证据

| 位置 | 当前行为 | 边界判断 |
|---|---|---|
| `bindRecordToAccount` | Store 分别组装两个保存 RPC，且两个参数对象都重复声明 `p_occurred_at` | transport 应复用 Record Repository；重复键当前由后一个同值覆盖，虽未改变运行值，但会隐藏后续修改错误 |
| canonical RPC | 使用 `auth.uid()`、记录行锁并原子替换账户流水，返回更新后的正式记录 | 数据库权威正确，PWA-063 不改 RPC、迁移、余额或流水规则 |
| RPC 返回处理 | 只读取 `error`，丢弃返回的正式记录 | Store 中的 `accountId`、时间和其他 canonical 字段可能保持旧值 |
| 单笔刷新 | RPC 后刷新账户、未绑定列表和可选详情；刷新函数默认吞掉错误 | 写入已 accepted 时仍可能显示统一成功，页面却保留旧列表，缺少 `refreshStatus` |
| `runLockedAction` | 只锁页面 action；重复调用返回 `null`，不共享请求结果 | 不能作为业务并发或会话隔离机制 |
| `resetUserData` | 清空 action state，但没有账户补绑 generation | 旧单笔或批量请求不会因 reset 自动失效 |
| 批量补绑 | 顺序调用单笔 `silent` 路径，最后只返回 `success > 0` | 丢失逐项错误；部分成功、全失败和刷新失败没有稳定契约 |
| 批量用户切换 | reset 可解除页面锁，但旧循环没有用户检查或停止条件 | 后续旧记录会在新会话下继续尝试 RPC，并可能刷新新用户页面、显示旧任务结果 |
| 推荐与预览 | Store 根据已绑定、支付线索或默认账户生成推荐，页面默认全选候选 | 属账户选择产品策略；本片保持现状，只固定为 Feature 外部输入 |
| 现有测试 | 财务保存 16 项、正式记录读取 14 项和发生时间契约通过 | 尚无账户补绑 Feature、批量部分失败、用户切换或刷新失败测试 |

## 3. 关键风险

### B-14：旧补绑结果污染新会话

补绑请求期间切换用户时，数据库会按请求时认证信息保护数据，但客户端没有 generation。旧循环仍可能继续调用、刷新当前用户页面并显示旧任务结果。实现必须在每次 Repository 返回后和批量下一项开始前检查用户与 generation；stale 结果不得收敛页面或提示。

### B-15：accepted 事实被刷新状态掩盖

账户与未绑定列表刷新发生在数据库事务之后。刷新失败不能把已生成的账户流水描述为补绑失败，也不能诱导用户重复补绑。结果必须保留 canonical record，并独立返回 `refreshStatus` / `refreshError`。

### B-16：批量部分成功不可追溯

批量补绑不是单一事务。每一项都必须返回 `accepted`、`failed` 或 `stale` 结果；顶层明确区分全部成功、部分成功、全失败和会话失效。成功记录应先用权威 DTO 本地收敛，之后只做一次写后刷新。

### B-17：同记录不同账户并发竞态

同一用户、kind 和 record ID 的相同账户请求可以共享 Promise；同一记录正在补绑时又提交不同账户，必须返回结构化 conflict，而不是让两个 RPC 竞争最后写入。

### B-18：默认账户推荐不等于证据匹配

当前批量候选包括默认账户推荐，页面打开预览时默认全选。这是既有产品策略，不应在 transport 收拢时静默改变。实现测试只固定“推荐在 Feature 外计算、用户确认后传入明确 accountId”，推荐阈值和默认全选另行产品评审。

## 4. 目标依赖方向

```text
PageUnboundRecords / useStore
  ├─ 推荐、选择、确认、页面 DTO 收敛与提示
  └─ Account Binding Feature
       ├─ 单笔 inflight / conflict / generation / stale
       ├─ 批量顺序、停止条件、逐项结果与一次刷新
       └─ Record Repository
            ├─ saveExpense
            └─ saveIncome

数据库 canonical RPC
  └─ 正式记录 + 账户绑定 + 账户流水原子权威
```

禁止反向依赖：Repository 不读取账户列表或 Vue 状态；Feature 不计算推荐账户、余额方向或 SQL 补偿；Store 不再组装 RPC 名与 `p_*` 参数。

## 5. 后续实现场景

PWA-063 作为账户补绑总任务，后续实现按以下子场景追踪：

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| PWA-063A | 补绑复用 Record Repository 的两个保存方法和正式记录 DTO；Store 不再直接调用保存 RPC，参数中只有一个 canonical `occurredAt` 来源 | Repository/Store 源边界 |
| PWA-063B | 同用户、kind、record 和 account 的并发补绑共享 Promise；同记录不同 account 的并发请求返回 conflict | Account Binding Feature |
| PWA-063C | reset 或用户切换使旧单笔结果 stale；批量在下一项开始前停止，且不刷新或提示当前会话 | Account Binding Feature |
| PWA-063D | RPC accepted 后以 canonical record 收敛；刷新失败仍保持 accepted，并返回独立刷新结果 | Feature/Store 行为 |
| PWA-063E | 批量顺序执行并返回逐项结果、成功数和失败数；部分成功不伪装成全成功，全部写入后只刷新一次 | Feature 行为 |
| PWA-063F | 页面保留推荐、预览和用户确认；成功项从未绑定集合移除，失败项可重试，stale 不显示旧任务提示 | Store/Page 边界 |

## 6. 非目标

- 不修改两个保存 RPC、数据库迁移、账户流水、余额方向或发生时间规则。
- 不修改推荐算法、默认账户、候选阈值、预览默认全选或账户匹配文案。
- 不修改 manual/edit、staging、待补全、wallet、删除、图片签名、iOS、Edge 或 Planner。
- 不承诺批量原子性、网络重试幂等或与 modal 编辑跨 Feature 的全局串行化。
- 不执行生产查询、真实数据写入、迁移、部署或 TestFlight。
