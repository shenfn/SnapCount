# A3 PWA 业务边界评估

> 任务：CLEAN-001/A3、PWA-001
>
> 基线：`2dd9cba`
>
> 状态：只读评估完成；后续实现进度以阶段索引和 PWA-001 执行记录为准

## 1. 评估结论

PWA 已有纯展示 adapter、`time-core` 和架构 ratchet 骨架，不需要重写。当前主要问题是 `src/composables/useStore.js` 约 4,400 行，同时承担会话、查询、事务编排、页面状态和错误提示；24 个 Vue 组件通过 `inject('store')` 消费同一大对象，4 个组件仍直接依赖 Supabase。

目标是保留 `useStore` 作为兼容门面，内部按业务边界逐片抽出 Feature State、Use Case 和 Repository。页面不一次性改写，业务规则不搬进 Repository，纯领域模块继续禁止依赖 Vue、HTTP 和 Supabase。

## 2. 当前证据

| 证据 | 当前状态 | 判断 |
|---|---|---|
| `src/composables/useStore.js` | 约 4,400 行，公开大量 ref、modal 和 action | 是兼容门面和多业务编排的混合体 |
| Store 网络访问 | 12 个不同 RPC 名称、13 张表/资源入口 | Repository 边界尚未形成 |
| 页面直连 | `AuthPage`、`ModalWelcome`、`PageAiVisionSettings`、`PageSettings`；架构基线为 5 个 import/fetch 键 | 只能逐项 ratchet 收缩，不能一轮清零 |
| 组件消费 | 24 个组件注入同一个 Store | 一次性替换会造成高回归面 |
| `src/domains` | 无 Vue、HTTP、Supabase 依赖 | 依赖方向正确，应继续保护 |
| Domain adapter | 多个函数直接接收整个 `store` | 虽无框架 import，输入边界仍过宽，后续改为显式只读数据 |
| 测试 | 未发现 `useStore` 直接行为单测；已有 finance/time 和表达交付源契约测试 | 首切片必须先补可执行特征测试 |

## 3. 目标依赖方向

```text
Vue Page / Component
        ↓
useStore 兼容门面（只组合和转发）
        ↓
Feature State（Vue 响应式与页面工作流）
        ↓
Use Case（业务编排，框架无关）
        ↓
Repository Protocol / Adapter（HTTP、RPC、DTO）
        ↓
Supabase / Edge

Use Case → 纯 Domain
Domain 不得反向依赖 Vue、Feature State、Repository 或网络
```

Repository 只负责请求参数、响应解码和传输错误，不计算金额、时间、账户影响或状态出口。服务端 RPC 仍是事务与余额事实的权威来源。

## 4. 业务边界

| 边界 | 现有职责 | 初始归属 |
|---|---|---|
| 认证会话 | `App.vue` 会话监听、`AuthPage` 注册登录、用户切换清理 | session Feature + auth Repository |
| 正式记录 | 收入、支出、通用记录的加载、保存、编辑、删除 | records Feature + records Repository |
| 中转生命周期 | 待处理确认、归档、丢弃、重试、批处理 | staging Feature + staging Repository |
| 账户还款 | 账户、流水、还款周期、绑定与钱包快照 | accounts Feature + accounts Repository |
| 数据域读模型 | 首页、日视图、报告、域详情的纯聚合与展示 | 纯 Domain/adapter，改为显式输入 |
| 设置与隐私 | `user_configs`、原图保留、导出、模型与陪伴设置 | settings Feature + settings Repository |
| 表达计划与反馈 | plan load/ack、缓存失效、曝光绑定、反馈 | expression Feature + expression Repository |
| 页面壳状态 | 导航、弹窗、flash、滚动和图片预览 | App shell，保留在门面或独立 UI composable |

边界之间通过明确事件协作。例如记录保存成功后触发表达缓存失效；不能让 records Repository 直接导入 expression Feature。

## 5. 迁移顺序

1. 首片迁移“表达计划与反馈”。它位于 Store 尾部、传输入口集中，且已有缓存失效、曝光身份和反馈绑定契约测试。
2. 迁移“设置与隐私”，逐步消除 `PageSettings`、`PageAiVisionSettings` 和 `ModalWelcome` 的 Supabase 直连。
3. 迁移“认证会话”，统一 App/AuthPage 的会话写入，保持用户切换清理不变量。
4. 迁移“中转生命周期”和“正式记录”，以服务端 RPC 为事务权威，不复制账户规则。
5. 最后迁移“账户还款”，其金额、流水和快照规则风险最高，必须使用数据库契约与特征测试。
6. 数据域 adapter 逐步从“接收整个 Store”改为显式输入；只改调用形状，不重写统计口径。

## 6. 风险与门禁

- `useStore` 返回对象是 24 个组件的事实 API；每片必须保持兼容导出，直到消费者逐步迁移。
- 用户切换必须清空所有 feature state、缓存和 in-flight request；不能只清数组。
- 写入成功、刷新失败与写入失败必须区分，不能通过重试制造重复事务。
- 页面直连采用 ratchet：新增立即失败，移除后同步收紧基线。
- 当前测试多为源契约，首片必须增加针对抽出模块的行为测试，不能只修改正则以适配新文件路径。
- `governance:arch` 中“A2 先确定 expression-core”提示已陈旧，应在首个 A3 实现切片同步改为当前架构目标，但不属于本只读文档切片。

## 7. 非目标

- 不引入 Pinia 或新的状态框架。
- 不按七个数据域机械拆成七个 Store。
- 不改页面视觉、导航、保存、删除、账户或确认行为。
- 不修改数据库、RPC、Edge、iOS、部署或 TestFlight。
- 不以文件行数下降作为阶段完成标准。
