## 1. 目标

首切片把表达计划加载、曝光确认、反馈提交和缓存状态从 `useStore` 内部抽到独立 expression Feature 与 Repository，同时保持 `useStore` 的公开 ref/action 和所有页面行为不变。

建议落点：

```text
src/repositories/expressionRepository.js
src/features/expression/useExpressionPlanState.js
src/features/expression/__tests__/
src/composables/useStore.js            # 兼容组合与转发
```

## 2. 场景与不变量

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| PWA-001 | `useStore` 继续暴露 `recordExpressionPlanCache`、load、ack、submit，现有组件无需同时改写 | 兼容契约 + PWA build |
| PWA-002 | 同一记录请求去重；强制刷新先失效旧 revision；旧 in-flight 成功或失败都不能覆盖新状态 | Node 行为测试 |
| PWA-003 | 只有 plan token、candidate id 和渲染身份完整时才能进入 ready/acknowledged；曝光 ID 必须来自 ack 响应 | Node 行为测试 + 既有表达契约 |
| PWA-004 | 用户切换或退出清空缓存、请求、revision 和版本；旧用户响应不能写入新用户状态 | Node 行为测试 |
| PWA-005 | 正式记录、中转、账户绑定或删除只有在服务端成功后才失效相关表达缓存 | 既有 mutation 契约 + 新兼容测试 |
| PWA-006 | Repository 只处理鉴权、HTTP action、DTO 和传输错误；Feature 不直接拼 Supabase URL/key | 静态依赖检查 + Repository 测试 |
| PWA-007 | Planner/fallback、候选、评分、渲染与曝光业务规则不在 PWA 重实现 | 架构检查 + 人工评审 |

## 3. 输入输出契约

- Repository 输入为 action、结构化 payload、`keepalive` 和 `AbortSignal`，输出为已解析响应或明确传输错误。
- Feature State 输入为 Repository 与当前用户生命周期事件；输出为与现有 Store 相同的缓存 ref 和 action。
- `recordKind` 仍只接受 `expense`、`income`、`data`，`universal` 只在门面处兼容映射为 `data`。
- 缓存键、request key、revision、ack 去重和反馈 exposure binding 语义不变。

## 4. 非目标

- 不修改 Edge action、数据库表、RPC、Planner 或表达文案。
- 不迁移 records/staging/accounts/settings/session 边界。
- 不更改 PageRecordDetail、ModalPending 或 AiFeedbackCard 的布局与交互。
- 不删除 `useStore` 或要求 24 个消费者同步迁移。
- 不在首片清理全部页面 Supabase 直连。

## 5. TDD 顺序

1. 把现有缓存与曝光不变量转成针对新 Feature/Repository 的行为测试，先证明目标模块缺失的红灯。
2. 实现 expression Repository 的 transport contract。
3. 实现 expression Feature State，并让 `useStore` 组合和转发现有 API。
4. 运行新行为测试、现有 PWA expression 契约、finance occurrence、架构检查和 PWA build。
5. 更新 `page_supabase_access`/提示基线时只移除真实已消除项，不预先宣告清零。
