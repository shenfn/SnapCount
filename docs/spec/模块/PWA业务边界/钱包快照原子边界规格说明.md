## 2. 快照事实模型

### 2.1 规范化输入

数据库从正式 `data_records` 读取并规范化，不信任客户端重复发送业务事实：

- `record.id/domain_key/user_id/occurred_at/created_at/payload_jsonb`
- kind：优先 `account_snapshot_kind`，回退 payload；只允许 `asset/liability`
- amount：优先顶层 `snapshot_balance`，回退 payload `snapshot_balance/amount`；必须非负
- snapshot time：优先顶层 `snapshot_at`，回退 `occurred_at/created_at`
- account metadata：`account_name/account_type/institution/last4/bill_day/payment_due_day`
- statement identity：只接受显式 `cycle_month/statement_month/bill_month`，或完整 `due_date` 的年月；paid 自动确认不得只用截图发生月份猜账期
- status：`paid` 才是还款证据，其余值按未还或未知处理
- balance scope：只有 payload `balance_scope='current_total'` 表达既有负债账户总欠款；legacy liability snapshot 默认只是 statement

客户端 command 只发送 `recordId` 和可空 `accountId`。账户创建资料由记录事实推导；后续如需人工覆盖账户名或类型，应建立独立确认场景。

### 2.2 账户金额语义

- 创建新账户或关联“初始余额=0、当前余额=0、无活跃非初始化流水”的空账户时，用户动作等同建立账本章节；可以采用快照金额作为 opening balance，并写 `snapshot_initialization` 审计标记。金额为 0 时不写零金额流水。
- 已有业务流水或非零余额的账户不得因普通快照改写 `initial_balance/current_balance`。
- 资产快照只更新 `snapshot_balance/snapshot_at`，不生成 adjustment。
- legacy liability snapshot 只建立或增强账期，不校准既有账户总欠款。
- liability `balance_scope=current_total` 才允许在账户锁内计算 delta、写 `data_records` 来源的 adjustment，并在成功后推进 `last_reconciled_at`。
- `last_reconciled_at` 与 `snapshot_at` 只能保持或向未来推进，旧快照可关联但不得回退当前观测和校准水位。

### 2.3 来源与关联

- 新账户的 `source_record_table='data_records'`、`source_record_id=record.id` 表示“由该快照创建”。
- 关联既有账户只写 `data_records.linked_account_id` 和账户 snapshot 字段，不覆盖账户既有 `source_record_*`。
- record 未关联时可绑定；已绑定同账户是幂等重试；已绑定其他账户返回 `snapshot_link_conflict`。
- asset 快照只能关联资产账户，liability 快照只能关联 `credit_card/credit_line`；归档账户拒绝。

## 3. 数据库原子命令

新增后续 migration，不修改历史 migration。canonical RPC：

```text
apply_wallet_snapshot(p_record_id uuid, p_account_id uuid default null) -> jsonb
```

事务顺序：

1. 拒绝 anon；按 `auth.uid()` 锁定 wallet record。
2. 规范化 kind、amount、snapshot time、statement identity 和账户资料；非法事实返回稳定错误。
3. 若 `p_account_id` 为空，复用同用户同 source record 的既有账户或创建新账户；否则锁定并验证目标账户。
4. 执行同目标幂等/异目标冲突判断，原子更新 record 顶层字段与 payload link 元数据。
5. 在账户锁内判断 opening adoption、观测快照单调更新和可选 current-total reconciliation。
6. liability unpaid 按第 4 节处理 cycle；liability paid 按第 5 节处理 cycle/payment/entry。
7. 返回 canonical JSON；任何 SQL 异常回滚整笔命令。

成功响应至少包含：

```json
{
  "outcome": "created|linked|replayed|needs_confirmation",
  "record_id": "uuid",
  "linked_account_id": "uuid",
  "account": {},
  "cycle": null,
  "payment": null,
  "balance_changed": false,
  "review_required": false
}
```

稳定数据库错误至少映射：`not_authenticated`、`wallet_snapshot_not_found`、`invalid_wallet_snapshot`、`account_not_found`、`account_archived`、`account_kind_mismatch`、`snapshot_link_conflict`、`repayment_evidence_conflict`。

## 4. 未还负债与账期优先级

- 无显式 statement identity 时，账户/记录关联仍可 accepted，但返回 `needs_confirmation`，不创建猜测月份账期。
- 无既有 cycle 时创建 screenshot cycle：statement/original/remaining 使用 amount，paid=0，source=`screenshot`，evidence 指向 record，priority=90。
- 既有 cycle 只有在 source=`system`、无有效 payment、paid=0 且状态属于 `draft_estimated/pending/due_today/overdue_unconfirmed` 时，才可由截图提升 statement、due date、source、evidence 和 priority。
- manual、有效 payment、`partial_paid/minimum_paid/paid/ignored/carried_over/reconciled/replaced/reopened` 或 priority>90 的 cycle 保持金额与状态；命令可以保留关联并返回 `needs_confirmation`。
- 同 record 同 cycle 重试不重复写，不把较旧 due/snapshot 证据覆盖较新证据。

## 5. 已还快照与付款证据

- paid 自动确认必须有显式 statement identity，并只能命中同账户该月份唯一 cycle；没有或冲突时返回 `needs_confirmation`。
- 若 cycle 已有同 record 的有效 payment，返回 replayed；不得新增 payment/entry。
- 若 cycle 已有其他有效 payment 或不可覆盖终态，返回 `needs_confirmation`，不得自动重新确认或作废旧付款。
- 无冲突时复用 canonical repayment 金额/状态规则；客户端与 wrapper 不传 `paid` 强制状态。
- 新建 payment 必须改为 `source='screenshot'`、`evidence_record_id=record.id`；liability/debit entries 继续以 payment 为 source。
- 新增活跃 evidence 唯一约束：同一 `evidence_record_id` 最多对应一个非 voided liability payment；迁移前只做保守去重或阻断，不猜测合并不同付款。
- 对新建或空账户，先建立 opening chapter，再应用 payment；对非空账户由 canonical repayment 规则限制有效负债减少和 overpayment，不能产生负余额。

## 6. Repository 契约

扩展 `createAccountRepository({ client })`：

- `applyWalletSnapshot({ recordId, accountId })` 调 `apply_wallet_snapshot`；不接收 `userId` 或快照业务字段。
- accepted 响应复用 `mapAccountRow`、`mapRepaymentCycleRow`、`mapLiabilityPaymentRow`，并保留 `recordId/linkedAccountId/outcome/reviewRequired/balanceChanged`。
- `outcome=needs_confirmation` 仍表示关联事务 accepted，但 `reviewRequired=true`；页面不得重发相同写入来“修复”。
- RPC error 映射为稳定 reason；空 account、record id 不一致或畸形 payload 返回 `invalid_response`。
- Repository 不写 Vue ref、不刷新列表、不显示文案。

## 7. Wallet Snapshot Feature

新增 `createWalletSnapshotFeature({ repository, getCurrentUserId })`：

- command identity 为 `userId + recordId`；signature 包含 operation（create/link）和目标 account id。
- 同一 identity/signature 复用 Promise；同 record 的不同目标或 create/link 冲突返回 `wallet_snapshot_conflict`，不发第二次 transport。
- 未登录、缺 record id、link 缺 account id在 transport 前 rejected。
- `reset()` 提升 generation 并清空 inflight；旧请求返回后为 stale，不执行 `onAccepted` 或 `refresh`。
- accepted 先调用 `onAccepted(result)` 收敛 account/record/cycle/payment，再独立 refresh；刷新失败保留 accepted 并返回 `refreshStatus='failed'`。
- Feature 不依赖 Vue、Supabase、页面文案或确认框。

## 8. Store 与页面

- `createAccountFromWalletSnapshot` / `linkWalletSnapshotToAccount` 保留公开函数名，改为组装 command 并委托 Feature。
- Store 不再直写 `accounts/data_records/account_repayment_cycles/account_entries`，不再调用旧的 cycle/reconcile helper。
- accepted 时先收敛返回账户和可选 cycle；把 record 的 payload link 字段更新为 canonical account id，再执行账户/正式记录刷新。
- reset 必须调用 Wallet Snapshot Feature `reset()`。
- `PageDomainDetail` 只展示未关联 wallet record，账户选择器过滤归档和不兼容家族；action busy 时禁用同记录动作。
- 只有 accepted 才关闭选择器。`needs_confirmation` 显示“账户已关联，账期/还款需要确认”；refresh failed 显示“已关联但刷新失败”；conflict/failed/stale 保留当前选择与重试出口。
- 普通 `loadData`、账户列表和详情读取不得调用 repair helper。

## 12. 完成定义

- PWA-068A 至 PWA-068J 均有自动化证据。
- 一次 wallet snapshot 命令跨表全成或全败，同目标重试无重复，异目标稳定冲突。
- statement/current-total/paid amount 不再由客户端混用；paid 有正式 payment/entry evidence。
- Store/Page 不再直写快照事务表，旧会话结果不污染新用户。
- 账户读取无隐式 repair；历史 WIP、PWA-069、iOS、Edge、Planner 均未进入 diff。
- GitHub PostgreSQL 17 实际执行 migration 两次并通过行为 assertions。
