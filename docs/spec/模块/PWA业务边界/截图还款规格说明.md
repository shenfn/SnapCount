## 2. 候选纯规则

- 输入只包含规范化 staging DTO、accounts 和 repayment cycles；不得读取 Vue ref、Supabase 或当前用户全局状态。
- staging 必须是 wallet 域，payload 必须表达 liability snapshot/repayment 且状态为 `paid`。
- 只考虑未归档的负债账户，以及 `pending/due_today/overdue_unconfirmed/partial_paid/minimum_paid/carried_over` 账期。
- 金额优先取已识别正数；缺失或非正数时回退账期剩余金额，再回退账单金额。
- 保留现有账户、金额、日期评分口径作为特征基线；同分时按 due date、cycle month、cycle id 稳定排序，不依赖数组偶然顺序。
- 返回值包含 cycle、account、amount、score、reason；低于阈值或无合法金额时返回 null。
- 候选仅供人工确认，不读取或启用 `auto_confirm_repayment`。

## 3. 数据库原子契约

新增后续 migration 覆盖现有 `confirm_staging_repayment`，不得修改历史 migration `071`。

- 保留七参数签名，兼容尚未迁移的 iOS/PWA 客户端。
- 使用 `auth.uid()`，锁定当前用户 staging；拒绝跨用户 staging/cycle/debit account。
- archived 且 target cycle/action 相同返回 canonical cycle，不新增 payment/entry；archived 到其他目标、discarded 或非法终态拒绝。
- 调用 `set_repayment_cycle_paid_amount` 时不把 `p_status` 作为权威；由 paid amount、statement/minimum 规则推导 `paid/partial_paid/minimum_paid`。
- 更新有效 payment 与 cycle 的 `source='screenshot'`；不把 staging UUID 写入 `evidence_record_id`。
- 同事务把 staging 写为 archived、`resolved_action='liability_repayment_confirmed'`、`target_record_id=cycle.id`、`target_kind='repayment_cycle'`、`resolved_domain_key='wallet'`。
- `staging_records_target_kind_check` 扩展为 `expense/income/data/repayment_cycle`。
- 对历史 `liability_repayment_confirmed` 行，仅在同用户 cycle 存在时回填 `repayment_cycle/wallet`；其他 unknown 保持 null。
- migration 连续执行两次无重复对象或数据漂移。

PostgreSQL fixture 至少证明：全额、部分、最低还款、扣款账户、余额方向、source、同目标幂等、不同目标冲突、discarded 拒绝、跨用户拒绝、anon 不可执行、历史保守回填和 migration 双次执行。

## 4. Repository 契约

扩展 `createAccountRepository({ client })`：

- `confirmStagingRepayment(command)` 调 `confirm_staging_repayment`。
- command 只含 `stagingId/cycleId/paidAmount/paidAt/debitAccountId/note`；不含 `userId`，不要求页面传 status。
- 为兼容旧数据库签名可发送 `p_status: null`，但不得发送 `paid`。
- RPC 成功必须映射并返回 canonical cycle；空响应返回 `invalid_response`。
- Repository 不删除 staging 数组、不刷新账户、不显示提示。

## 5. Screenshot Repayment Feature

新增独立 `createScreenshotRepaymentFeature({ repository, getCurrentUserId, now })`：

- command identity 包含 user、staging、cycle、amount、debit account；同 identity 复用 Promise。
- 同一 staging 已有不同写命令时返回 `screenshot_repayment_conflict`，不得发第二次 transport。
- `reset()` 提升 generation 并清空 inflight；旧 transport 即使 accepted 也返回 stale，不调用 `onAccepted` 或 `refresh`。
- accepted 先调用 `onAccepted(result)`，再调用 `refresh(result)`；任一刷新错误只写 `refreshStatus='failed'`，不改变 accepted 事实。
- 结果区分 `accepted/failed/rejected/stale`；Feature 不依赖 Vue、Supabase、页面或确认框。

## 6. Store、Repository DTO 与页面

- `useStore.buildRepaymentCandidateForStaging` 改为调用纯候选函数；不保留第二份评分实现。
- `confirmStagingRepayment` 保留公开函数名和人工确认框，组装 command 后委托 Feature。
- accepted 时按 id 收敛 `repaymentCycles`，从 `stagingRecords` 移除，并写入 `processedStagingRecords`：`targetKind='repayment_cycle'`、`resolvedDomainKey='wallet'`、`targetRecordId=cycle.id`。
- reset 调 Screenshot Repayment Feature 的 `reset()`。
- Staging Repository mapper 接受 `repayment_cycle` 并生成 `repayment_cycle/<id>` reference。
- `openProcessedStagingRecord` 遇到 repayment cycle 时，从已加载 cycle 找到 account 并进入账户详情；cycle/account 缺失时显示明确不可用提示。
- PagePending 只有 `result.status==='accepted'` 才推进队列；取消/失败/冲突/stale 保持当前项。
- accepted 且 refresh failed 显示完成但刷新失败；普通失败可重试，不伪装成功。

## 10. 完成定义

- PWA-067A 至 PWA-067G 均有自动化证据。
- Store 不再直接调用 `confirm_staging_repayment`，候选评分只有一份 PWA 生产实现。
- 客户端不能强制金额不一致的账期变为 paid。
- archived screenshot repayment 有明确 `repayment_cycle` 目标和可达页面出口。
- 旧会话结果不污染新用户；accepted 与 refresh failure 可区分。
- diff 未进入 iOS、PWA-068、Edge、Planner 或生产发布。
