# PWA 账户读取边界评估

> 任务：CLEAN-001/A3、PWA-065
>
> 基线：`2c5b205`（PWA-064 收口 PR #95 合并提交）
>
> 状态：已完成，PR #96 已合并

## 1. 结论

PWA 的账户读取不能只靠把三段 Supabase 查询搬进 `accountRepository.js` 完成。当前实现同时混合了纯查询、DTO 映射、当前账户选择、详情并发、图片签名、周期生成和余额修复写入；如果整体平移，旧请求污染、空数据与失败混淆以及隐藏写副作用都会被带进新抽象。

后续实现应拆成两层：

1. Account Repository 只负责账户、流水、还款周期和还款记录的 transport、DTO 与结构化失败；查询依赖 RLS，不接收或发送 `user_id`。
2. Account Detail State/Feature 负责当前 account identity、user/generation、相同请求复用、分区 loading/error、stale 丢弃和刷新结果；来源快照由 Record/Wallet Snapshot 读取边界提供，Account Repository 不直接依赖 `data_records` 或图片签名。

`repairEmptyAccountSnapshotBalances` 必须从账户列表读取成功路径中移出。它实际会查询快照和流水并更新余额，属于 wallet 快照修复/对账副作用；PWA-065 只解除隐藏调用，不重写其业务规则或把它包装成“读取”。

## 2. 当前职责矩阵

| 职责 | 当前入口 | 当前问题 | 目标归属 |
|---|---|---|---|
| 账户列表 | `loadData`、`refreshAccountsFromDB` | 两份直接查询；失败语义不一致；成功后暗中修复余额 | Account Repository `listAccounts` + 列表状态 |
| 账户 DTO | `mapAccountRow` | 已在 domain adapter，边界可复用 | Account Repository 复用 `accountAdapter` |
| 账户流水 | `loadAccountEntries` | Store 直查、错误变空数组、旧请求可覆盖新账户 | Account Repository `listAccountEntries` |
| 还款记录 | `loadAccountPayments` | Store 直查；缺表与普通失败都最终表现为空 | Account Repository `listAccountPayments`，保留 unavailable/failed 区分 |
| 还款周期 | `loadData` 内 ensure + list | 生成周期写副作用伪装成加载的一部分 | Repository 分开 `ensureRepaymentCycles` 与 `listRepaymentCycles`，Feature 显式编排 |
| 来源快照 | `loadAccountSourceSnapshot` | 直查 `data_records` 并签图片；错误、无记录和签名失败都趋向 `null` | Record/Wallet Snapshot Read Repository；详情状态只编排 |
| 当前详情选择 | `openAccountDetail`、`refreshAccountDetail` | 无 account/user/generation guard，无统一结果 | Account Detail State/Feature |
| 快照余额修复 | `repairEmptyAccountSnapshotBalances` | 读取路径中查询两张表并更新 `accounts` | Wallet Snapshot Repair/Reconciliation 后续切片 |
| 页面展示 | `PageAccountDetail.vue` | 只有流水 loading，不能展示 section partial error | 页面消费详情状态，不直连 transport |

## 3. 已确认的现状

### 3.1 列表读取

- `loadData` 通过整体 `loadDataRunId + expectedUserId` 拦截旧批次，但仍直接查询 `accounts`。
- `loadData` 的账户查询失败会把 `accounts` 清空；`refreshAccountsFromDB` 失败则保留旧值并返回 `failed`，同一事实源存在两套失败语义。
- 两个入口在查询成功后都会调用 `repairEmptyAccountSnapshotBalances`，所以“列表读取成功”并不是纯读完成点。
- `walletAdapter.getAccountSections` 直接消费 `store.accounts`。兼容接线必须保持页面模型，不要求页面一次性重写。

### 3.2 详情读取

- `openAccountDetail` 和 `refreshAccountDetail` 并行加载流水、还款记录和来源快照，但没有统一请求身份。
- 快速从账户 A 切换到 B 时，A 的任一旧请求都可能最后写入全局 `selectedAccount*`；用户 reset/切换也没有让这些请求 stale。
- `loadAccountEntries` 和 `loadAccountPayments` 失败时写入空数组，`loadAccountSourceSnapshot` 失败时保留 `null`。页面无法判断“真实为空”“服务端失败”“表不可用”或“图片签名失败”。
- 详情刷新没有结构化返回值，因此 PWA-064 Repayment Feature 只能知道刷新 Promise 是否抛错，不能准确区分 accepted 后的完整刷新、部分刷新、失败和 stale。

### 3.3 隐藏写副作用

- `ensure_liability_repayment_cycles` 是写命令，不属于 `listRepaymentCycles`。负债详情可以显式 ensure 后再读取，但调用方必须知道这一动作可能失败。
- `repairEmptyAccountSnapshotBalances` 查询 `account_entries` 与 `data_records`，随后更新 `accounts.initial_balance/current_balance`。
- 该修复函数没有独立 generation/expected-user guard。用户在查询和逐账户更新之间切换时，旧任务仍可能继续写旧用户的账户；RLS 与 `.eq('user_id', currentUserId.value)` 不能替代客户端任务身份，因为 `currentUserId` 本身已经可能变化。
- PWA-065 不改变快照采纳条件、余额方向或数据库结构，只把副作用从纯读取边界中剥离并登记后续治理任务。

### 3.4 iOS 参考边界

- iOS `AccountRepository` 已有 `fetchAccounts` 和聚合 `fetchDetail`，并用 `loadErrors` 保留 entries/cycles/payments 的分区失败。
- iOS `AppState.loadAccounts/loadAccountDetail` 有 `userStateGeneration` guard，来源快照通过独立 `walletSnapshotRepository` 获取。
- 这些实现可作为职责形状参考，但不是 PWA 并发语义或跨端一致性已经完成的证据。PWA 仍需以自己的 Feature 测试固定 account identity、Promise 复用、stale 与刷新结果。

## 4. 目标依赖方向

```text
PageAccountDetail / wallet 页面 / useStore 兼容门面
  ├─ Account List State
  │    └─ Account Repository.listAccounts
  └─ Account Detail State/Feature
       ├─ account identity + user/generation + request reuse
       ├─ section loading/error + refresh result
       ├─ Account Repository
       │    ├─ listAccountEntries
       │    ├─ listAccountPayments
       │    ├─ listRepaymentCycles
       │    └─ ensureRepaymentCycles（显式命令）
       └─ Record/Wallet Snapshot Read Repository
            └─ source snapshot + image signing

Supabase RLS
  └─ 根据当前认证会话隔离用户；Repository 不拼 user_id
```

Account Repository 不管理 Vue ref、当前页面、选中账户、图片签名、快照修复、余额写入或提示文案。Account Detail State 不复制 DTO 映射和 Supabase 查询。

## 5. 状态与结果契约

### 5.1 账户列表

- 首次加载失败时可见 rows 为空，但必须同时保留 `failed`，不能把失败描述成“没有账户”。
- 已有成功 rows 的刷新失败不得清空旧数据；返回 `failed` 与 error，页面可继续展示最后成功值。
- reset 或用户切换使旧结果 `stale`；stale 不更新 rows、错误或当前用户提示。

### 5.2 账户详情

- 请求身份至少包含 user identity、account id 和 generation。
- 同一身份的并发详情请求复用同一个 Promise；不同 account id 的请求可以开始，但旧身份结果不得写入当前详情。
- 每个 section 独立返回 `accepted`、`failed` 或兼容性 `unavailable`；一个 section 失败不清空其他成功 section。
- 刷新整体结果至少区分：`accepted`（全部成功）、`partial`（部分成功）、`failed`（无分区成功）和 `stale`（身份已失效）。
- RPC 写入已经 accepted 后，详情刷新 `partial/failed` 仍不得诱导重复提交还款命令。

### 5.3 来源快照

- 无来源记录、来源查询失败和图片签名失败是不同状态。
- 来源快照不进入 Account Repository DTO；Account Detail State 通过独立 collaborator 编排。
- 本切片不改变 wallet 快照的创建、关联、校准或余额修复规则。

## 6. 主要风险

### B-26：旧账户详情覆盖当前账户

当前三个 loader 分别写全局 selected 状态。账户 A 的慢请求可以在账户 B 打开后写回，造成流水、还款或来源截图串账户。必须在统一详情状态层按 account/user/generation 丢弃旧结果。

### B-27：失败被伪装成空数据

当前 entries/payments/source failure 分别落为 `[]` 或 `null`。页面会把服务故障显示成“没有记录”，也无法给用户局部重试出口。Repository 和详情状态必须保留分区错误。

### B-28：读取路径暗中修改余额

列表刷新成功后调用的 repair 会更新账户余额。把它原样搬入 `listAccounts` 会破坏 Repository 的读契约，并使重试读取产生写入。PWA-065 必须解除隐藏调用，后续由 wallet 修复切片明确触发与验证。

### B-29：周期生成与周期读取混合

ensure RPC 失败目前只 warning，随后仍查询 cycles。新边界必须把 ensure 作为显式命令并将其失败作为独立 section/预处理状态，不得让纯查询方法暗中写库。

### B-30：列表双入口失败语义漂移

`loadData` 与 `refreshAccountsFromDB` 分别决定是否清空账户。若只迁移其中一个入口，首页、wallet 页面和写后刷新仍会表现不同。实现片必须让两者通过同一 Account Repository 和列表收敛规则。

### B-31：来源快照跨域污染 Account Repository

来源快照属于 `data_records`，还包含图片签名和 record detail cache。把它放进 Account Repository 会形成账户域反向依赖记录域。详情 State 可以编排两类 Repository，但不能合并它们的所有权。

## 7. 后续实现场景

| 场景 | 行为不变量 | 测试层 |
|---|---|---|
| PWA-065A | Account Repository 独占账户列表 transport 和 `mapAccountRow`；RLS 隔离用户，不接收/发送 `user_id`；刷新失败保留最后成功 rows | Repository/列表状态 |
| PWA-065B | 流水、还款记录和周期查询进入 Account Repository；ensure cycle 保持独立显式命令；来源快照继续走 Record/Wallet Snapshot 读取边界 | Repository/源边界 |
| PWA-065C | Account Detail State 用 user/account/generation 判定身份；同身份 Promise 复用；账户切换、reset 和用户切换使旧结果 stale | Feature/State |
| PWA-065D | section 独立失败且不清空成功 section；详情刷新返回 accepted/partial/failed/stale，并可供 Repayment Feature 正确分层 | Feature/Store 行为 |
| PWA-065E | `loadData`、`refreshAccountsFromDB`、`openAccountDetail`、`refreshAccountDetail` 通过兼容门面接线；页面显示 loading/partial error/重试，不新增 Supabase 直连 | Store/Page 源边界与回归 |

## 8. 明确非目标

- 不修改账户创建、编辑、默认项、归档、还款 RPC、截图还款或流水补偿 helper。
- 不重写 `repairEmptyAccountSnapshotBalances` 的判断规则，不执行余额校准，不新增数据库迁移。
- 不把 `data_records`、图片签名或 wallet 快照写入 Account Repository。
- 不修改 iOS、Edge、Planner、生产配置或部署状态。
- 不以“文件变小”作为完成标准；必须由 stale、partial error 和纯读取契约测试证明边界成立。
