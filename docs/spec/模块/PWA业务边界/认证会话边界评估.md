# PWA 认证会话边界评估

> 任务：CLEAN-001/A3、PWA-018
>
> 基线：`21e011b`（PR #68 合并提交）
>
> 状态：只读评估完成；未修改认证业务代码

## 1. 评估结论

认证会话目前由三处共同编排：`App.vue` 负责 auth session 事件和初始恢复，`AuthPage.vue` 负责登录/注册请求及注册同意 metadata，`useStore.js` 负责用户状态、数据加载和 reset。当前没有必要引入新的状态框架；下一片应建立轻量 Auth Repository/Session Feature，由 App 保留唯一 session 事件入口，AuthPage 只提交认证动作和展示结果，Store 继续作为兼容门面。

本片不能把注册同意、`user_configs` 建行、用户切换清理和数据加载一次性塞进一个“认证服务”。它们分别受服务端 trigger、RLS、客户端 session 生命周期和数据加载竞态约束，失败模型不同。

## 2. 当前证据

| 位置 | 当前行为 | 风险判断 |
|---|---|---|
| `src/App.vue` | `getSession` 后订阅 `onAuthStateChange`，`applySession` 设置 Store 并调用 `loadData`；退出时 reset | 是 session 事件事实入口，但订阅未保存 unsubscribe；异步 applySession 没有会话 generation |
| `src/components/pages/AuthPage.vue` | `signUp`/`signInWithPassword` 后手动写 `currentUserId`、`currentUserEmail`、`isLoggedIn` 并调用 `loadData` | 与 App auth 事件重复编排，可能重复加载或交错加载；注册时直接 upsert `user_configs` 与服务端 trigger 重叠 |
| `src/composables/useStore.js` | `resetUserData` 清理多个 feature state；`loadDataRunId` 只保护补充图片/还款加载 | 主查询 Promise 完成后没有统一 current-user/run guard，切换用户时旧查询可能覆盖新用户数组 |
| `supabase/migrations/008_user_configs.sql` | `auth.users` after-insert trigger 创建 `user_configs` 默认行 | AuthPage 的配置 upsert 不是注册同意权威，且可能在无 session/邮件确认时失败；不应由客户端重复承担默认建行 |
| `supabase/migrations/009_rls_multi_user.sql` | 业务表按 `auth.uid() = user_id` 保护 | Repository/Feature 必须以当前 session 用户为边界，不能接受组件传入任意 user id 做认证动作 |
| 注册同意迁移与安全契约 | trigger 校验 terms/privacy/sensitive consent 并写 server timestamp | 客户端只提交当前版本和用户选择；不得伪造时间、绕过 trigger 或把同意状态放进 Settings |

## 3. 目标边界

```text
AuthPage
   ↓ submit login/register/refresh
Auth Session Feature
   ↓
Auth Repository（Supabase auth transport）
   ↓
Supabase Auth + server consent trigger

App.vue
   ↓ 唯一订阅 auth state changes
useStore 兼容门面
   ↓ reset/load orchestration
records/settings/staging features
```

- Auth Repository 只负责 `signUp`、`signInWithPassword`、`signOut`、`getSession` 和 DTO/错误归一化。
- Session Feature 负责 session generation、登录/退出/切换状态和一次性数据加载编排；不负责金额、记录查询或设置字段映射。
- App 保留唯一 `onAuthStateChange` 订阅；AuthPage 不再直接写 Store 用户字段或调用 `loadData`。
- 注册同意 metadata 仍由认证动作提交，服务端 trigger 是版本、时间和敏感数据同意的权威。
- `user_configs` 默认行由数据库 trigger 创建；客户端若保留显式 upsert，只能作为明确的兼容补偿并有错误契约，不能与 Settings Feature 混为配置读取。

## 4. 后续实现范围

首片只处理 session 生命周期与重复编排，不迁移所有数据请求：

1. 为 App/AuthPage/useStore 的现有行为补 session 特征测试和最小 Auth Repository/Session Feature。
2. 将登录、注册和登出动作改为 Feature 返回结构化结果；页面只负责输入、同意复选框和展示错误。
3. 让 App 的 session event 成为唯一用户状态写入入口，移除 AuthPage 手动 `currentUser*`/`isLoggedIn`/`loadData`。
4. 为 `applySession` 与 `loadData` 增加用户 generation/run guard，保证旧账号查询不能写入新账号 state。
5. 验证注册同意服务端契约、PWA build、已有 settings/expression 回归和架构 ratchet。

## 5. 非目标

- 不修改注册同意迁移、RLS policy、数据库 trigger 或 Edge Function。
- 不重写 `loadData` 的所有 Repository，不把正式记录、中转、账户查询一轮抽完。
- 不迁移 `user_configs` 配置字段；PWA-008 已建立 Settings Feature，认证只负责会话边界。
- 不改变登录/注册视觉、文案、邮箱确认产品策略或密码策略。
- 不修改 iOS、部署、生产配置、TestFlight 或历史用户数据。
