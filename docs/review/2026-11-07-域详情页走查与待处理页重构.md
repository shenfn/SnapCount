## 1. 域详情页：确认成立的问题

三个域共用 `NativeDomainDrillView` + `NativeDomainPageView(isDrillDown: true)`，所以问题是同一份代码，三个域都存在。

### D-01（P0）「当前待处理候选」与所选日期无关，且是全量倾倒

- 选 2026-11-02，页面底部列出的是 2026-06-18 ~ 2026-08-25 的 73 条候选。它自己在副标题里也写了「最新候选，不是所选历史日期的快照」。
- 这些记录和上方「支出 ¥99.62 / 商户排行」没有任何关系，读起来像页面数据错乱。
- 位置：`NativeDomainPageView.swift` 原 `currentCandidates`（`isDrillDown` 分支）。
- 处置：**整块删除**。未确认候选只属于收件箱，不在明细页重复第二遍。

### D-02（P1）候选行有「空标题」的空白行

- 同一列表里出现只有日期和金额、没有商户名的行（`2026-06-27 · 待确认支出 · ¥50.14`）。`merchant_name` 为空时直接渲染空字符串，没有任何兜底文案。
- 随 D-01 一起消失；如果以后别处再有用到 `pendingExpense.title`，要补「待补全消费」兜底。

### D-03（P2）顶部域切换只有三个域

- `NativeDomainDrillView` 里写死 `[.expense, .sleep, .sport]`。饮食、钱包、阅读在首页有入口，进了明细页却切不过去。

### D-04（P2）图表纵轴没有单位

- 「金额 · 按时间」右侧刻度是 0 / 25 / 50 / 75，没有 ¥；横轴 0–24 也没写「时」。
- 同一页「商户排行」的金额带 ¥，两种口径并存。

### D-05（P3）明细页标题与首页重复

- 顶部 `支出 · ¥99.62` 与首页 hero 的「当日支出 ¥99.62」是同一个数字的两种写法，进明细页后仍占一屏最贵的位置。

## 2. 待处理页：和 PWA 的真实差异

对照 `src/components/pages/PagePending.vue` + `src/styles/pages/pending.css`。

| 维度 | PWA | 重构前 iOS |
|---|---|---|
| 结构 | 页头（范围切换）→ 状态 chips → 日期分组的**双列胶片网格** → 已处理 | 大标题 → 12 张「未完成的图片」大卡 → 分段控件 → 小标题 → chips → 单列卡片 |
| 首屏信息量 | 一屏能看到 4–6 条候选 | 一屏只能看到 1 张图片卡 |
| 卡片 | 3:4 视觉区（原图 / 横线纸事实说明）+ 状态胶囊 + 记录/上传双时间 | 48pt 缩略图 + 标题 + 状态胶囊 + 类别标签 |
| 时间 | 记录时间与上传时间分开显示 | 只有一个时间，且多数显示「上传时间未知」 |
| 账单 | 平台 / 分类 / 支付三件事做成小标签，缺失项变黄 | 只有标题和金额 |
| 空态 | 轨道圈 + 两句说明 | 系统 ContentUnavailableView |

### D-06（P0）「未完成的图片」把列表挤到十几屏之后

12 张待处理图片，每张都是 150pt 高的大图 + 三个按钮，共约 12 屏。用户要滑十几屏才能看到第一条候选。
处置：改成一条可展开的横幅（默认只报数量），展开后是 52pt 缩略图的紧凑行，动作按钮缩到 mini 尺寸。

### D-07（P0）「今天」为什么一直是空的——它不是 bug，但文案错了

- 口径：`scope == .today` 只匹配**发生日期**等于今天（和 PWA 一致）。
- 本机数据：73 条候选的发生日期在 2023-09 ~ 2026-10，12 张图片上传于 11-06。今天（11-07）确实没有任何一条。
- 真正的问题是空态写「今天没有这类记录 / 切换到全部可以查看更早的待处理记录」——把「范围问题」说成了「筛选问题」，用户以为是坏了。
- 处置：
  - 范围切换上直接显示今天的条数（`今天 0`），一眼能看出是 0 条而不是加载失败。
  - 空态改成说明真实原因，并给一个「查看全部 73 条」的按钮。

### D-08（P1）顶部右上角那个空方块

`InboxView` 的 toolbar 里是个「单列 / 双列」切换按钮，图标本身是空心矩形，在浅色背景上几乎看不见，被当成渲染 bug。
处置：PWA 固定双列，这个开关删掉。

### D-09（P1）导航标题叫「待确认」，但页面里还有「待确认」这个筛选

标题和筛选同名，用户分不清「我在待确认页」还是「我在待确认筛选」。
处置：标题改为「待处理」，筛选顺序按 PWA 排：全部 → 待分类 → 待确认 → 需重试 → 待修补 → 账单补全。

### 2.1 复测时又抓到的四点（D-10 ~ D-13）

改完版式跑起来对着 PWA 逐屏比，又发现四处「改了一半」的地方：

| 编号 | 问题 | 处置 |

## 2.2 详情页的对比区块：从文字堆叠改成卡片组

### D-14（P1）「与前一天比较」是三段纯文字，没有容器、没有层级、没有可视化

改前这一块长这样（明细页）：

```
与前一天比较
金额
当天 ¥20.78
前一天 ¥52.77
笔数
当天 3 笔
前一天 2 笔
最高一笔
当天 -¥14.78 · 粥员外（杭州鑫都汇店）
前一天 -¥29.90 · 问剑电竞（中赢康康台店）
```

问题不在文案，在于它没有「形状」：九个句子同一个字号、同一个颜色、同一个间距，读者要逐行读才知道哪行是当天、哪行是前一天；差额是多少、差得多不多，全靠心算。放在一屏里有图表、有排行、有明细的页面里，它看起来就是一段没排完的日志。

参照物是系统天气的分组卡，它把一块数据固定拆成四层：**分组卡壳 → 小字标题 → 大数字 → 一条可视化 + 一句说明**。同一套骨架既能放「风」这种多行表，也能放「紫外线指数」这种单指标。

处置：新增组件族 `DesignSystem/JieziCompare.swift`，按三层复用：

| 组件 | 用途 |
|---|---|
| `JieziComparePanel` | 宽卡：标题 + 右上对照日期 + 内容，承载主指标 |
| `JieziCompareTile` | 双列小卡：图标标签 + 中号数字 + 说明 + 可视化 |
| `JieziCompareBars` | 两条等基线对比条，长度按两期最大值取比例 |
| `JieziMeterRow` | 单值占比条（「占当日支出 40%」） |
| `JieziDeltaPill` | 差额胶囊：箭头 + 「多花 / 少花 ¥x」，涨跌各有语气色 |

落到页面上的结果：

- **记账明细页**：主卡报金额（大数字 + 差额胶囊 + 当天/前一天双条），下面两张小卡报笔数（双条）和最高一笔（当天 + 分隔线 + 前一天）。
- **记账首页**：原来并列的「与前一天比较」「最高一笔」两张纯文字卡，换成同族小卡，四层结构一致，底边齐平。

配色语义：支出变多用赭红（`scene.dataAccent`），变少用墨绿（`scene.accent`），持平走中性灰。这与中文语境里「涨红跌绿」的方向一致，但色值仍取自各域 scene，不新造颜色。

容器上有一处有意偏离其它卡：对比卡的底用**实心 `scene.surface` + 0.8pt 弱描边**，而不是页面里其它卡的 `0.66~0.78` 半透明。原因是详情页背景本身就是米白纸，半透明 surface 叠上去只差 5~8 个色阶，框根本立不起来；用户的诉求正是「用组件框起来」，所以这里宁可牺牲一点玻璃感。

## 2.3 明细列表的时间列：从「—」和折行到总有时间可读

### D-15（P1）「收支明细」左列大半是「—」，唯一有值的那行还折成两行

改前 11-02 的四条支出：

```
11:30:0    小象超市-滨兴站     -¥15.68
0
—          中国电信           -¥28.94
—          巡面（杭州滨江江陵路店） -¥15.00
—          新派杨姐麻辣烫       -¥40.00
```

两个独立问题叠在一起：

1. **数据侧**：本机 `local_expenses` 里 4 条只有 1 条有 `transaction_time`，其余是 NULL；而 `LocalExpenseReadModel.groups` 把 `transactionTime` 原样当 `timeLabel`，NULL 就落到界面兜底字符「—」。
2. **格式侧**：唯一有值的那条存的是 `11:30:00`，带秒。时间列固定 42pt，`caption2` 等宽下装不下 8 个字符，于是「11:30:0 / 0」折行。

处置分三层：

- **取值**：`NativeLocalDate` 新增 `clockKey(_:)` 与 `listTimeLabel(recordTime:uploadedAt:)`。有发生时刻就用它并把秒裁掉（`11:30:00` → `11:30`）；没有就退回上传时刻，输出 `上传 HH:mm`，由界面标成推断值；两者都没有才返回 nil。四个本机读模型（`LocalExpenseReadModel` / `LocalIncomeReadModel` / `LocalRecordReadModel` / `LocalFactReadModel`）统一走它，所以睡眠、运动、饮食的「当日记录」也一起不再出现「—」。
- **版式**：时间列仍是 42pt，但只放「时刻」这一行；`上传 ` 前缀不占正文宽度，折成下面一行 9pt 的小字标注。这样真实时间与兜底时间在视觉上一眼可分，又不会把列撑宽。
- **排序**：新增 `listTimeSortKey(_:)`，把「是不是兜底值」编进排序键（真实时刻 `1`、兜底 `0`、无时间空串）。原先各处按 `timeLabel` 裸字符串比较，`上传 18:58` 因为中文前缀排在纯数字之后，descending 时被顶到最前，看起来像「18:58 花得比 11:30 晚」。现在真实发生时间排前、兜底排后，`chronologicalOrder`、`mergeRecordGroups`、`NativeHomeDashboard`、`NativeDataService.dayRecordGroups` 一并换成这个键。

改后：

```
11:30     小象超市-滨兴站       -¥15.68
18:58     中国电信             -¥28.94
上传
18:58     巡面（杭州滨江江陵路店） -¥15.00
上传
```

关于口径：兜底时间标的是「这条记录是什么时候进的库」，不是「这笔钱几点花的」。日期分组仍按 `transaction_date`，卡片上另有一处「发生时间优先；缺失时使用标明来源的记录或上传时间」的说明，两者不冲突。如果同一批数据是历史迁移进来的，`上传` 会集中在迁移那一刻——这恰好也把「时间不可信」这件事显性化了，比留一个「—」更诚实。

## 4. 没做的事（避免误解）

- **批量选择/批量归档/批量销毁没做**。PWA 有「选择」，iOS 目前只能逐条进裁决台；这是一块独立功能，不在本次版式对齐范围内。
- **对比组件只落在记账域**。睡眠/饮食/运动/阅读的指标卡仍是旧样式，替换是机械工作，但四个域要各自核一遍数字口径，单独一轮做更稳。
- **「已处理」区块没做**。本地没有对应的已处理列表读模型（PWA 读的是 staging 的 resolved 行）。
- 域切换补全（D-03）、图表单位（D-04）、明细标题重复（D-05）只记录，未改。

## 5. 构建与复测：已在本机跑通

### 5.1 环境阻断与绕法（留给下一个会话，不要重踩）

`xcodebuild` 一开始在 SwiftPM 解析阶段就失败：

```
Could not resolve package dependencies: sandbox-exec: sandbox_apply: Operation not permitted
```

问题不在代码，而在会话沙箱无法应用 SwiftPM 的 deny 型 profile。两步绕开：

```bash
# 1) 关掉 manifest 沙箱（否则包图一直解析失败）
defaults write com.apple.dt.Xcode IDEPackageSupportDisableManifestSandbox -bool YES
# 2) 宏插件（@State / @TaskLocal）自己的 sandbox 也要关，否则报 malformed response
cd ios && xcodebuild -project SnapCount.xcodeproj -scheme SnapCount \
  -configuration Debug -destination 'platform=iOS Simulator,name=iPhone 17e' \
  -derivedDataPath /tmp/sc-dd OTHER_SWIFT_FLAGS='-disable-sandbox' build
```

`** BUILD SUCCEEDED **`，模拟器 iPhone 17e（iOS 27.2）安装启动正常。

顺手补了一个工程配置缺口：`SnapCountTests` 既没有 `INFOPLIST_FILE` 也没开自动生成，`xcodebuild test` 直接卡在
`Cannot code sign because the target does not have an Info.plist file`。在 `project.yml` 的测试 target 加
`GENERATE_INFOPLIST_FILE: YES` 后测试能跑。

测试结果：**617 条用例，1 条失败**——`testEXP012NativeUploadRequestsStructuredResultAndPreservesFoodVoice`，
报 `SupabaseRemoteError.missingConfig`。原因是本机构建的 Info.plist 里 Supabase URL / anonKey 为空（走的是
环境变量注入），与本轮改动无关；其余 616 条全绿，其中包含本地记账、判重、历史迁移等回归。
